# 模块：界面与交互

## 本章导读

本章定义 ATeam 的界面层：用户如何看见、理解并控制多个 Agent 的工作。它不是一份视觉稿说明，也不是前端实现教程，而是把「本地优先的多 Agent 开发驾驶舱」翻译成可评审、可测试、可排期的产品约束。

阅读本章时请把握三个前提。第一，ATeam 的主界面不是聊天窗口，而是任务、运行与证据的控制台；Agent 的输出必须落到 Task、Run、Workspace、Artifact、Evidence 这些对象上，界面才有可治理的抓手。第二，M0 只完成了骨架：四个一级页面、看板拖拽、创建 Task 与 Agent、轮询式 Run 日志；diff 评审、证据面板、审批门、Inbox、权限与多人协作都尚未实现，本章会逐项标注阶段，不把计划写成现状。第三，界面必须服务于「人工评审门」这一产品主张：高风险动作不能在视觉上被弱化成一次普通点击，证据也不能藏在二级页面深处。

本章的功能需求统一使用 UI- 前缀，覆盖导航、看板、Task 详情、运行时间线、Agent 编辑器、Inbox、状态反馈、交互模式、视觉规范、可访问性、响应式与 Settings。每个需求都给出可验证的验收要点。涉及 Task、Agent、Run、Workspace、Artifact、Evidence、权限与 API 的细节，以对应模块文档为准，本章只描述界面消费方式与交互契约。

## 1. 目的与范围

### 1.1 目的

界面层的核心目的不是「好看」，而是降低多 Agent 并行的认知负担，并让治理动作发生在正确的位置。具体拆解为六个目标。

1. **状态可见**：开发者在任意时刻能回答四个问题——哪些 Task 在等待、哪些 Run 在跑、哪个 Run 需要我评审、哪个动作被审批门拦住。答案必须在一次导航内可见，而不是靠记忆或翻日志。
2. **上下文连续**：从 Board 到 Task 到 Run 到 Diff 到 Evidence 到 Review，用户不应丢失「我在看哪个任务、哪个 Agent、哪个分支」的上下文。页面标题、面包屑、URL 与选中态共同承担这一责任。
3. **证据先行**：任何「完成」「合并」「批准」的入口，都必须能在同一屏或一次点击内看到支撑证据：diff 统计、测试结果、截图、Artifact 列表、Run 摘要。界面不能用一句「Completed」替代证据。
4. **高风险动作显式化**：合并、推送、部署、删除工作区等动作必须触发显式确认或审批对话框（M1 为合并确认，M2 起为审批门），展示影响范围与证据摘要，并要求明确确认。常规动作保持轻量，高风险动作保持笨重，这是有意的设计不对称。
5. **并行可辨识**：同时运行 3 至 5 个 Agent 时，用户能通过角色、Agent 名称、Task 标题、状态色与运行指示区分彼此，避免把 A 任务的 diff 当成 B 任务的成果。
6. **本地诚实**：断线、服务未启动、Runtime 不可用、权限不足、Workspace 缺失等状态必须显式呈现，不能以空白页或静默失败掩盖。ATeam 的信任来自「知道本机发生了什么」。

### 1.2 范围

本章覆盖以下内容：

- 应用外壳：侧边栏、页头、内容区、全局反馈层。
- 信息架构与一级导航：Board、Task、Agents、Runs、Crew、Inbox、Skills、Templates、Settings、M3 团队页面与 M4 自动化页面。
- 页面规格：每个页面的目标、关键元素、主操作、当前实现与计划差异。
- Task 详情：运行入口、运行列表、日志、diff、证据、评审、审批。
- Agent 编辑器：基本信息、指令、技能、权限、限制、预览。
- 运行详情与时间线：事件分类、日志查看、Artifact、错误处理。
- 全局状态：空状态、加载、错误、权限不足、离线、冲突。
- 交互模式：拖拽、快捷键、确认、toast、焦点管理。
- 视觉规范：深色主题、排版、间距、状态色、图标、动效。
- 可访问性：键盘、对比度、焦点、语义、读屏。
- 响应式：桌面优先与窄屏降级。
- 用户故事、功能需求、指标、依赖与风险、里程碑映射。

### 1.3 不覆盖的内容

Task 字段与状态机、Agent 配置语义、Run 生命周期、Workspace 隔离机制、Artifact 与 Evidence 的存储格式、审批策略引擎、API 合约、安全模型、非功能指标，分别在对应模块文档中定义。本章在需要时引用其结论，不重复展开。

### 1.4 设计原则

| 原则 | 含义 | 界面体现 |
|---|---|---|
| 状态先于内容 | 用户先要知道「发生了什么」，再决定「读什么」 | 页头固定展示状态与主操作；看板列头显示数量；Run 卡片显示状态与耗时 |
| 一屏一主操作 | 每个页面只有一个视觉权重最高的动作 | Board 是 New task；Task 详情是 Run 或 Review；Agent 编辑器是 Save |
| 证据先于结论 | 完成与合并必须可追溯到证据 | Review 面板并列展示 diff 统计、测试、截图与 Artifact |
| 渐进披露 | 默认只显示决策所需信息，细节按需展开 | 日志默认跟随尾部；diff 按文件折叠；权限高级项收在折叠区 |
| 可逆优先 | 可撤销的动作不打断，不可撤销的动作强确认 | 状态拖拽可回滚；删除、合并、覆盖工作区必须确认 |
| 键盘等价 | 核心路径不依赖鼠标 | 状态变更提供菜单替代拖拽；模态框焦点陷阱；全局快捷键 |
| 深色优先 | 长时间盯盘降低眩光 | 以深色为唯一正式主题，浅色不作为 M1 至 M3 目标 |
| 本地诚实 | 不伪造在线、不隐藏失败 | 连接状态、Runtime 可用性、离线横幅、错误详情均为显式组件 |
| 角色可辨 | 多 Agent 场景下角色是第一识别维度 | Agent 卡片与 Run 行优先展示角色与名称，而非仅显示 runtime |
| 不阻塞 | 长任务不占用界面主线程与用户注意力 | Run 启动后立即返回；列表可继续操作；通知进入 Inbox |

### 1.5 术语与阶段标记

本章统一使用以下术语，避免「评审」「审批」「确认」混用，也避免把 M2 的 Approval 实体与 M1 的合并确认混为一谈。

| 术语 | 含义 | 使用阶段 |
|---|---|---|
| Review（评审） | 对 Run 的 diff、测试与证据作出的 approve / changes_requested 结论，不可修改、只能追加 | M1 |
| Approval（审批） | 独立门禁实体，记录请求人、证据快照、决定与过期时间；与 Review 不是同一对象 | M2 起 |
| confirm（确认） | M1 合并对话框中的显式确认，不产生 Approval 实体；请求携带 `confirm=true`、reviewId 与 expectedHeadCommit | M1 |
| Inbox（收件箱） | 需要人处理的条目队列，不是聊天收件箱 | M2 |
| Evidence（证据） | 可引用的 Artifact 及其校验、来源与评审依据 | M1 基础，M2 扩展 |
| Task 详情 | 页面名称统一写作「Task 详情」，不使用「任务详情」 | M0 起 |
| 角色 Agent | UI Design、Frontend、Backend、DevOps 等可复用工作配置 | M2 |

阶段标记统一使用：`M0 已实现` 表示仓库代码可验证；`M0 部分` 表示只有部分行为；`M1` 至 `M4` 均为计划，不得在发布说明中描述为已具备。凡本文与模块文档冲突之处，以模块文档的权威定义为准，并在第 16 节登记待统一项。

## 2. 非目标

以下内容明确不在本模块的近期范围内，避免界面无限扩张。

- 不做完整的项目管理套件：里程碑、甘特图、工时、报表、客户管理不进入 ATeam 主界面。
- 不做移动端原生应用：M1 至 M4 以桌面与桌面浏览器为主，窄屏只保证可读与可完成关键操作，不追求移动端完整体验。
- 不做多 Agent 自由聊天的群聊界面：角色协作通过任务 DAG、交付物契约与审批门表达，界面不提供「让几个 Agent 互相聊天」的会话面板。
- 不做可自由拖拽布局的仪表盘：页面结构固定，避免用户配置成本与测试矩阵爆炸。
- 不做浅色主题与高对比主题切换：M1 至 M3 只维护深色主题；若后续支持浅色，必须作为独立设计任务重新验证对比度。
- 不做富文本所见即所得编辑器：Task 描述与 Agent 指令使用 Markdown 源文编辑与只读渲染，避免转义与粘贴污染。
- 不做第三方产品的界面复刻：所有组件、图标语义、文案与布局均为原创实现。
- 不做内置模型调用计费界面：ATeam 不转售模型，界面只展示本地 Runtime 的可用状态与用户自带的配置状态。
- 不做实时多人光标与协同编辑：M3 团队模式只提供共享数据与审计，不提供同屏协同编辑。
- 不做营销官网与 onboarding 动画：首次使用引导以最小可用的空状态与检查清单完成。

## 3. 角色与场景

### 3.1 界面角色

| 角色 | 描述 | 主要使用页面 | 引入阶段 |
|---|---|---|---|
| 本地用户（Operator） | 单机使用者，同时运行 3 至 5 个 Agent；M0-M2 中创建、启动、评审、合并由同一人完成，操作者记为本地用户 | 全部页面 | M0 起；M1 增加评审与合并，M2 增加审批门 |
| 组织 Owner | 组织所有者：组织设置、成员与角色、Runner、全部 Team Workspace | Access、Machines、Audit、Board | M3 |
| 组织 Admin | 管理员：成员、Runner、共享 Agent、审计与安全设置 | Access、Machines、Audit、Settings | M3 |
| Workspace Admin（workspace_admin） | Team Workspace 管理员：本 Workspace 的 Task、Agent 与成员；审批合并与 staging 部署 | Board、Task、Agents、Inbox | M3 |
| Contributor | 贡献者：创建 Task、使用可见 Agent 启动 Run、查看本 Team Workspace 的 Run 与证据 | Board、Task、Agents、Runs | M3 |
| Reviewer | 评审者：查看被指派的 Run 与证据，提交评审结论、审批合并 | Board、Task、Runs、Inbox | M3 |
| Viewer | 只读成员：只读被授权的 Task、Run 摘要与 Agent 描述 | Board、Task、Runs | M3 |
| Reviewer | 评审者：查看 Task/Run/证据、评论、审批合并；不能修改 Agent 权限 | Inbox、Task 详情、Run 详情 | M3 |
| Viewer | 只读成员：只读被授权的 Task、Run 摘要与 Agent 描述 | Board、Task、Runs | M3 |
| 角色化 Agent（非人类用户） | UI Design、Frontend、Backend、DevOps 等工作配置，作为内容主体出现在界面中 | Agent 卡片、Run 行、Task 分配 | M2 |

说明：

- M0 至 M2 是单用户本地模式，security-and-permissions.md §4.1 明确这一阶段没有登录、没有角色。本章 M1 的「评审者」只表示执行评审动作的本地用户，不是权限角色；不得用角色矩阵描述 M1-M2 的能力。
- M3 的角色模型与 security-and-permissions.md §4.2 完全一致：组织级 Owner、Admin、Member、Viewer；Team Workspace 级 Admin（workspace_admin）、Contributor、Reviewer、Viewer。workspace_admin/Contributor 是旧称，不再作为角色名。Operator 不是角色，只是本地单用户阶段的称呼。
- 团队共享任务、Agent、机器始于 M3，不是 M2。M2 通过本机单用户的多 Agent 协作完成角色流水线，不引入多账号；M2 的审批人是「本地用户」，不是 Admin 或 Reviewer。
- Machines 与 Audit 是 M3 的独立一级页面，不是 Settings 子页；单机模式下这两个入口不出现。

界面必须区分「人」与「Agent」的身份呈现。Agent 不作为登录用户展示，但在 Task 分配、Run 触发者、评论作者与审批记录中必须有清晰标识，避免用户误以为某个 Agent 是同事。

### 3.2 典型场景

| 场景 | 用户目标 | 界面路径 | 关键约束 |
|---|---|---|---|
| 早晨巡检 | 快速判断哪些任务卡住、哪些需要评审 | 打开 Board，查看 In Review 列与 Inbox 未读数 | 首屏不加载大日志；看板卡片数量可控 |
| 并行启动 | 为三个就绪任务分别选择合适的 Agent 并启动 | Board 打开 Task，选择 Agent，点击 Run，返回 Board | 启动不超过两次点击；Run 状态即时可见 |
| 观察执行 | 判断 Agent 是否偏离任务 | Task 详情查看 Run 时间线与日志 | 日志实时但不淹没关键事件；可暂停跟随 |
| 评审交付 | 阅读 diff、测试与截图，决定批准或退回 | Task 详情 Review 面板（M1）；M2 起可从 Inbox 跳转 | 证据与决定同屏；批准前必须看到证据摘要 |
| 处理阻塞 | 发现路径权限不足或 Runtime 不可用 | Inbox 阻塞项，跳转 Run 详情 | 错误信息可行动；提供修复入口 |
| 配置角色 | 新建 Frontend Agent，限定路径与命令 | Agents 页面，Agent 编辑器 | 权限默认拒绝；风险项有解释 |
| 合并成果 | 将已评审 Run 的分支合并 | Task 详情 Merge 对话框 | 展示分支、diff 统计、Review 结论；M2 增加门禁状态；默认按钮为取消 |
| 窄屏查看 | 在 13 英寸笔记本分屏时查看状态 | Board 横向滚动或状态切换；Task 单列 | 核心按钮不溢出；表格降级为卡片 |
| 断网或服务重启 | 理解界面为何不再更新 | 全局连接横幅 | 不伪造实时；重连后补齐事件 |

## 4. 信息架构与导航

### 4.1 一级导航

| 导航项 | 路由 | 目的 | 当前阶段 |
|---|---|---|---|
| Board | `/` | 以状态列纵览全部 Task，创建任务，拖拽流转 | M0 已实现 |
| Task | `/tasks/:id` | 单个任务的上下文、运行、日志、评审与合并 | M0 基础版，M1 扩展 |
| Agents | `/agents` | 浏览可复用工作配置，进入创建或编辑 | M0 列表与创建，M1 编辑 |
| Agent 编辑 | `/agents/:id` 或抽屉 | 编辑指令、技能、权限与限制 | M1 路由化，M0 仅创建弹窗 |
| Runs | `/runs` | 跨任务查看全部执行记录与异常 | M0 表格 |
| Run 详情 | `/runs/:id` | 单次执行的时间线、日志、Artifact 与错误 | M1 |
| Inbox（收件箱） | `/inbox` | 汇总待审批、门禁过期、阻塞、失败与升级 | M2 |
| Skills | `/skills` | 浏览、创建、编辑与归档技能 | M2 |
| Templates | `/templates` | 浏览角色模板与任务模板，并从模板创建 | M2 |
| Crew 视图 | `/crews/:id` | 只读查看队长计划的成员、依赖与状态 | M2 |
| Access | `/settings/access` | 成员、角色与审批策略 | M3 |
| Machines | `/machines` | Runner 注册、心跳、能力与状态 | M3 |
| Audit | `/audit` | 审计查询与导出 | M3 |
| Automations | `/automations` | 定时与 Webhook 自动化 | M4 |
| Notifications | `/notifications` | 通知中心与偏好 | M4 |
| Plugins / Telemetry | `/settings/plugins`、`/settings/telemetry` | 插件管理与遥测开关 | M4 |
| Settings | `/settings` | Runtime、Workspace、通知、访问与关于 | M0 基础版，M1 分页 |

M0 的侧边栏只包含 Board、Agents、Runs、Settings 四项，路由表中也只有五条路由（含 Task 详情），不存在 Inbox、Skills、Templates、Crew、Machines、Audit，也不存在独立的 Agent 详情与 Run 详情路由。Agents 的创建通过模态框完成，Runs 的表格行点击后跳转到所属 Task，而不是 Run 详情。这一现状是本章后续阶段规划的事实基线。

M2 起在 Agents 下增加 Skills 与 Templates 两个子入口（也可作为 Agents 页的二级标签），Crew 视图挂在 Task 详情中并提供独立只读路由。M3 团队模式在侧边栏增加 Machines 与 Audit 两项，并在 Settings 下增加 Access；单机模式下这些入口不渲染，避免制造「已有团队能力」的错觉。M4 的 Automations 与 Notifications 是独立一级页，Plugins 与 Telemetry 收在 Settings 下。

### 4.3 导航规则

- **常驻侧边栏**：宽屏下侧边栏固定 240px，不随内容滚动；一级导航始终可见。M0 已实现固定宽度，但没有折叠能力。
- **选中态**：当前路由与导航项匹配时高亮。Board 使用精确匹配，其余使用前缀匹配。M0 已实现该逻辑，但 Task 详情不归属 Board，M1 修正。
- **层级返回**：详情页返回上一级时保留列表的滚动位置、筛选条件与选中项；M1 起通过 URL 查询参数与页面缓存实现，不能直接回到默认看板顶部。
- **URL 可分享**：Task、Run、Inbox 项、筛选视图都必须有稳定 URL。M0 只有 Task 详情具备地址直达能力；筛选与选中 Run 尚未写入 URL，M1 补齐。
- **未保存保护**：Agent 编辑器、Task 描述内联编辑在离开前检测脏状态，弹出确认；M1 实现。
- **窗口标题**：桌面窗口标题应反映当前页面或对象，例如「ATeam · Board」「ATeam · Fix login redirect · Run #a1b2」；M1 实现。
- **徽标**：Inbox 显示未读与待处理数量；Runs 在一级导航上不显示计数，避免与 Inbox 语义重叠。M2 实现。
- **键盘可达**：侧边栏项目可通过 Tab 顺序访问，支持方向键在导航组内移动；M1 实现。
- **导航不劫持**：拖拽中、模态框打开、日志全屏时不响应全局导航快捷键，防止误跳转。

### 5.2 Board 页面

**目标**：用状态列呈现任务流水，让用户在不打开任何详情的情况下判断「哪里堵住了、哪里需要我」。

**M0 关键元素**

- 页头：标题 Board、副标题「Tasks and their current execution state」、主按钮「+ New task」。
- 状态列：按共享常量渲染 Backlog、Todo、In Progress、In Review、Done 五列。每列显示名称、任务数量与提示文案（例如 Todo 列为「Ready for an agent」）。
- 任务卡片：标题自然换行（M0 未做行数截断，最多两行是 M1 目标）、描述最多两行（line-clamp-2）、状态徽标、优先级文字、四位短 ID。卡片整体可点击、可拖拽。
- 列内空状态：显示「No tasks」与「Drag a card here or create a new one.」。
- 新建 Task 模态框：Title、Description、Status 三个字段，Enter 直接创建，Cancel 与 Create 按钮。
- 容器：列宽 256px，横向滚动，列内纵向滚动。

**M0 的行为与已知缺口**

- 拖拽放下时直接调用更新接口修改状态；拖到同列不做任何请求。
- 没有乐观更新：请求返回前卡片仍在原列；请求失败时没有回滚提示，错误会以未处理的 Promise 拒绝形式丢失。
- 只有五列，`blocked` 与 `cancelled` 虽然在类型与徽标中定义，但看板上没有独立列，用户无法通过看板看到这两类任务。
- 卡片不显示 Agent、运行状态、证据数量或阻塞原因；多 Agent 场景下的辨识度不足。
- 没有筛选、搜索、排序、批量选择与 WIP 限制。

**M1 至 M2 计划**

- 卡片增加 Agent 角色标识、活动 Run 指示、证据计数、阻塞原因摘要。
- 增加搜索框与筛选器：按 Agent、标签、优先级、状态、是否有待评审过滤；筛选条件写入 URL。
- 增加「待我处理」快捷视图与保存视图（M2）。
- 拖拽改为乐观更新，失败时回滚并提示；进入 Done 前校验评审与证据规则。
- 提供拖拽的键盘与菜单替代：卡片菜单中的「Move to…」。
- 列虚拟化或分页：单列超过 200 张卡片时启用窗口化，避免渲染卡顿。

### 5.3 Task 详情页面

**目标**：一个任务的全部上下文与执行证据都在这里闭环。用户不需要在多个工具之间复制粘贴任务背景，也不需要去文件系统里寻找 diff。

**M0 关键元素**

- 页头：完整 Task ID、状态徽标、标题、状态下拉框、返回按钮。
- 描述区：只读展示，保留换行；无描述时显示占位文案。
- Runs 区：Agent 下拉选择、Run 按钮、不可运行提示、运行列表。运行项显示 Run 状态、触发方式、创建时间、摘要或错误。
- 日志区：选中 Run 后显示 `[事件类型] 消息` 的纯文本日志，最大高度 320px，内部滚动；运行中每 1.5 秒轮询刷新；提供 Cancel 按钮。
- 加载与不存在状态：加载时显示文本；任务不存在时显示「Task not found.」与返回看板按钮。

**M1 页面结构（三区）**

| 区域 | 宽度建议 | 内容 | 目的 |
|---|---|---|---|
| 左栏：上下文 | 280 至 320px | 描述、验收标准、标签、优先级、依赖、Agent 分配、Workspace 信息 | 回答「这个任务要求什么」 |
| 中栏：执行 | 自适应，最小 480px | Run 启动器、Run 列表、Run 时间线或日志、Diff 入口 | 回答「Agent 做了什么」 |
| 右栏：评审 | 360 至 420px | 证据摘要、Review 决定、门禁状态（M2）、Merge 入口 | 回答「能不能收」 |

窄于 1280px 时，右栏折叠为标签页；窄于 1024px 时，三区改为纵向堆叠，评审区置顶于执行区之后。

**Task 详情必须覆盖的子模块**

1. **Run 启动器**：选择 Agent、显示该 Agent 的 Runtime 与权限摘要、显示预计超时、启动按钮。任务状态不属于 Todo、In Progress、In Review 时禁用启动，并在按钮旁说明原因，而不是只禁用不解释。M0 已有「Move the task to Todo or In Progress before starting a run.」提示。
2. **Run 列表**：按创建时间倒序；每项显示状态、Agent 名称与角色、触发方式、开始时间、耗时、摘要、错误、证据计数。选中项有明确边框或背景差异。M0 只有状态、触发、时间、摘要与错误。
3. **运行日志与时间线**：M0 是纯文本；M1 改为结构化时间线，详见第 5.4 节。
4. **Diff 查看器**：M1 提供文件树、变更统计、统一与分栏两种视图、按文件折叠、语法高亮、行内评论、已读标记。二进制文件显示「无法预览」而不是乱码。
5. **证据面板（M1 展示 Artifact；Evidence 实体从 M2 起）**：M1 展示 Artifact 列表，包括测试输出、截图、构建产物、日志附件与自定义证据；每项显示类型、来源、生成时间、摘要与预览入口。证据是评审依据，不是普通附件。
6. **评审面板**：M1 提供 Approve、Request changes 两个主决定；附评论；显示评审人、时间与意见。退回时必须填写原因。
7. **评审与合并**：M1 的 Merge 入口必须打开合并确认对话框，展示目标分支、源分支、head commit、diff 统计、证据清单、Review 结论与风险提示，默认焦点在取消按钮，并要求显式勾选「我理解该操作会修改目标分支」。M1 的确认是 Review + confirm，不产生 Approval 实体；M2 才引入 Approval 与策略，未满足策略时 Merge 按钮禁用并说明缺少哪个门。合并对话框必须提供策略选择（M1 为 squash 与 merge；M2 增加 rebase；不提供 force merge），展示冲突检测结果；存在冲突时禁止合并并列出冲突文件与双方分支，允许中止。目标分支在评审后前进或目标工作区不干净时，合并入口禁用并说明需重新评审或先清理。合并失败不得留下半完成状态，界面显示失败原因、可重试与回滚说明。
8. **活动与评论**：M2 提供人类与 Agent 的操作时间线，包括状态变更、Run 启停、评审、审批、合并与评论。评论不进入 Agent 对话上下文，除非显式附加到下一次 Run 的任务说明中。
9. **依赖与交付物**：M2 展示任务依赖 DAG 的局部视图与交付物契约，明确本任务需要消费哪些上游产物、必须产出哪些交付物；未就绪时必须显示结构化原因（例如 `dependency_unfinished`、`contract_not_frozen`、`gate_pending`），而不是点击后才失败。

**Task 详情的关键规则**

- 状态修改与运行启动是两个独立动作：修改状态不自动启动 Run。但启动 Run 在 M0 已有明确副作用：`createRun` 把任务的处理人写为所选 Agent（`assigneeType=agent`、`assigneeId`），并在任务为 `todo` 时自动转为 `in_progress`（task-management.md TASK-023，internal/api/handlers.go）。这是当前实现，不是可选行为；界面必须在启动后刷新页头状态与处理人，并同步看板。若产品希望改为「显式选择是否移动」，属于 M1+ 行为变更，必须先修订 TASK-023 与 API 合约，本章不提前承诺。
- 可运行状态为 `todo`、`in_progress`；`in_review`（M1）、`backlog`、`done`、`blocked`、`cancelled` 均禁用 Run 按钮并说明原因（TASK-022、UI-033）。M2 的 in_review 返工例外必须先创建新 Review 或记录取代原因，界面按任务模块 §5.2 提示。
- 当任务存在运行中的 Run 时，状态选择器允许改到 In Review，但改到 Done 需要满足证据与评审规则；M0 无此约束，属于 M1 计划。M1 的 Done 条件是「至少一个 approve 评审且必需 Evidence 齐全」，合并成功后默认进入 done；M2 起由门禁与契约共同决定。
- **证据化完成定义（DoD）**：M1 的 DoD 基于 Artifact（diff、测试结果、日志、报告；`screenshot` 可选、不作为 M1 必需项）与 Review 决定，界面逐项显示满足状态，缺失项必须显式列出；M1 不引入 Evidence 实体。M2 起引入 Evidence 与契约冻结状态，`screenshot` 才作为 UI 类 DoD 必需项，未冻结契约的下游任务不可运行。界面不得只凭 Run 状态为 Completed 就显示任务已完成。
- 一个任务可以有多条 Run；必须明确标出「当前活动 Run」，避免用户把旧 Run 的日志当成最新状态。M0 选中项用边框高亮，但没有跨页面的活动 Run 标识，M1 补齐。
- 删除 Task 是既有能力（`DELETE /api/tasks/{id}`，M0 API 已存在，M1 补界面入口与二次确认）；删除 Run 记录当前没有任何 API 合约，本章不安排在 M1；Workspace 清理与 Run 记录删除后移至 M2，见第 8.3 节与 UI-127。M0 三者均无界面入口，不得声称已有。
- M2 起 Task 详情采用标签页：Overview、DAG、Contracts、Gates、Evidence、Timeline（M2 里程碑第 2.1 节）。标签页只在对应数据存在时显示，不提前渲染空壳。

### 5.4 Run 详情与时间线

**目标**：解释一次执行的全过程，回答「开始了吗、做了什么、卡在哪、产出了什么、为什么失败」。

**页面结构**

- 页头：Run 短 ID、状态、所属 Task 链接、Agent 名称与角色、触发方式、开始与结束时间、耗时、取消与重试按钮。
- 摘要条：状态、分支、Workspace 路径、Runtime 名称、模型（若配置）、超时设置。
- 标签页：Timeline、Logs、Diff、Artifacts、Review（M1）与 Approval（M2）。M1 至少提供 Timeline、Logs、Diff、Artifacts 与 Review 入口；Approval 在 M2 完整。
- 时间线：按时间顺序展示生命周期事件、关键日志、工具调用、文件变更、测试结果、Artifact 生成、评审与审批。每类事件有固定图标与颜色，普通日志不进入主时间线，避免噪声。
- 日志：等宽字体，支持跟随尾部、暂停跟随、搜索、级别过滤、自动换行开关、下载。超过阈值启用虚拟滚动。
- 错误态：显示错误摘要、可展开的原始错误、可能原因与下一步动作。例如 Runtime 未安装时提供「打开 Settings 检查 Runtime」入口。

**事件分类与展示**

| 事件类别 | 示例 | 时间线可见 | 默认展开 |
|---|---|---|---|
| 生命周期 | queued、preparing、running、completed、failed、cancelled | 是 | 是 |
| Workspace | provisioning、ready、failed | 是 | 是 |
| 关键日志 | Agent 开始、阶段总结、阻塞声明 | 是 | 是 |
| 工具调用 | 读取文件、执行命令、写入文件 | 是 | 否 |
| 文件变更 | 修改、新增、删除文件 | 是 | 是 |
| 测试结果 | 通过、失败、跳过，含命令与耗时 | 是 | 是 |
| Artifact | 截图、报告、构建产物 | 是 | 是 |
| 评审与审批 | 评审提交、门禁请求、批准、拒绝、过期 | 是 | 是 |
| 普通日志 | 详细输出、调试信息 | 否，仅在 Logs 标签 | 不适用 |

**M0 现状与差距**

M0 没有独立 Run 详情页，日志嵌在 Task 详情中，以纯文本拼接显示，事件只有 `log`、`summary` 等少量类型；没有时间线、文件变更、测试、Artifact 与审批事件。M1 才引入独立路由与结构化事件渲染。界面不得在 M0 阶段宣称具备 diff 或证据能力。

### 5.5 Agents 页面

**目标**：让用户快速找到可复用的工作配置，理解每个 Agent 的职责边界与运行约束。

**M0 关键元素**

- 页头：标题、副标题「Reusable work profiles for tasks」、主按钮「+ New agent」。
- 空状态：提示可创建 UI Design、Frontend、Backend、DevOps 角色 Agent。
- 卡片网格：宽屏三列、中屏两列；卡片显示名称、描述、Runtime 标签、指令前三行、并发数、超时、Workspace 模式。
- 创建模态框：Name、Description、Instructions、Runtime、Model、Max concurrency、Timeout、Allowed paths。

**M1 至 M2 计划**

- 卡片增加角色标识、最近使用时间、关联运行数、成功率、权限风险徽标。
- 支持编辑、复制、归档与删除。删除前展示受影响的未完成任务与历史 Run 数量。
- 提供角色模板：UI Design、Frontend、Backend、DevOps，每个模板预置指令骨架、默认权限与交付物说明。
- 提供搜索、按 Runtime 与角色筛选、按最近使用排序。
- 显示 Runtime 可用性：已安装、未安装、版本不兼容。不可用时卡片置灰并给出修复链接。

### 5.6 Agent 编辑器

**目标**：用一致、可验证的表单表达一个 Agent 的身份、能力、边界与限制。编辑器不是自由文本堆砌，而是把会影响执行行为的配置显式化。

**表单分区**

| 分区 | 字段 | 规则 | 阶段 |
|---|---|---|---|
| 基本信息 | 名称、描述、角色 | 名称必填；M0-M2 为本地唯一（冲突返回 409），M3 起为团队内唯一；角色来自固定枚举或自定义标签 | M0 部分，M2 角色 |
| Runtime | Runtime、模型、版本约束 | 只允许选择本机已安装的 Runtime；模型留空表示使用 Runtime 默认；M1 提供 mock 与 Claude Code，Codex 为 M2 | M0 基础，M1 可用性检查 |
| 指令 | 职责、边界、检查项、汇报格式 | Markdown 源文编辑；提供预览；长度上限与敏感信息提示 | M0 纯文本，M2 预览与模板 |
| 技能 | 附加技能列表 | 每个技能显示来源、版本、启用状态；仅 M2 技能模型可用后开放 | M2 |
| 权限 | 允许路径、允许命令、禁止命令 | 默认拒绝；路径必须为仓库相对路径；命令使用前缀或精确匹配规则 | M0 仅允许路径，M2 完整 |
| 限制 | 最大并发、超时、Workspace 模式 | 校验上限为并发 1 至 16、超时 1 至 1440 分钟；UI 建议值可更窄（并发 1–10、超时 1–480），但不得作为服务端校验上限 | M0 并发与超时，M1 校验 |
| 高级 | 环境变量、运行前置命令 | M2 开放；M3 起仅 Owner/Admin 可见；密钥只显示已配置或未配置 | M2 高级，M3 管理员 |

**指令编辑器规则**

- 使用纯文本 Markdown 编辑，提供只读预览切换；不使用所见即所得，避免隐藏字符与粘贴样式污染。
- 明确展示「此指令会与 Task 上下文一起构成 Runtime prompt」的说明，避免用户误以为指令可以替代任务描述。
- 提供占位变量说明，例如任务标题、描述、验收标准、依赖交付物；变量语法由 Runtime 模块定义，编辑器只做插入与高亮，不做执行。
- 未保存离开时弹出确认；保存成功后显示 toast，并保留当前滚动位置。
- M2 起提供模板片段插入，但不得自动覆盖用户已有内容。

**权限编辑器规则**

- 「允许路径」是白名单：为空表示不允许写入任何路径，而不是允许全部。界面必须明确这一语义，避免危险的默认值误解。
- 「允许命令」按可执行文件或命令前缀配置，展示示例与风险等级。`git push`、`deploy`、`rm -rf` 等高风险命令在 M2 不允许由 DevOps Agent 自主执行，只能生成计划并等待人工审批。
- 权限变更保存前显示「影响预览」：列出该 Agent 当前可写的路径与可执行的命令类别。
- 任何放宽权限的修改都需要二次确认，并在确认框中说明风险。

### 5.7 Runs 页面

**目标**：跨任务观察执行健康度，发现失败、超时与异常模式。

**M0 关键元素**

- 页头：标题、副标题「Every agent execution」、Refresh 按钮。
- 空状态：提示从Task 详情启动 Run。
- 表格列：Status、Task、Trigger、Created、Summary。行点击跳转到所属 Task。
- 没有分页、筛选、排序、耗时列、Agent 列与 Run 详情入口。

**M1 至 M2 计划**

- 增加 Agent、耗时、分支、证据数、错误摘要列。
- 行点击进入 Run 详情；Task 名称作为独立链接，避免整行跳转语义混淆。
- 提供状态、Agent、时间范围筛选；支持按创建时间与耗时排序。
- 增加「仅看失败」「仅看进行中」快捷筛选。
- 运行中的行显示轻量进度指示，但不播放持续动画，避免视觉噪声。
- 超过 100 行时分页；默认每页 50 行，可切换 100。

### 5.8 Inbox 页面（M2）

**目标**：把所有「需要人」的事项集中到一个可清空的工作队列，而不是让用户在 Board、Runs、日志之间寻找待办。

**收件项类型（以 collaboration-and-review.md §10.1 的十类为准）**

| 类型 | 触发条件 | 默认优先级 | 截止与提醒 | 主操作 | 跳转目标 |
|---|---|---|---|---|---|
| approval_request | 门禁创建：design_review、api_contract_review、crew_plan、merge、staging、contract_break、high_risk_command、scope_change；push 若启用独立推送门则同样生成条目；prod 为人工执行并记录，不生成待审批条目 | 高 | 按门禁 TTL；到期前提醒 | 打开对象并批准或拒绝 | 门禁对象（Task 详情 Gates 标签或审批面板） |
| gate_expired | 门禁超时 | 高 | 有明确截止时间 | 重新请求或取消 | 门禁对象 |
| blocker | Agent 上报阻塞 | 高 | 无固定 TTL，按任务优先级排序 | 回复、改范围、取消任务 | Run 详情或 Task 时间线 |
| escalation | 连续失败或超时升级 | 紧急 | 立即提醒，不受限频 | 接管、改派、取消 | Task 详情或 Crew 视图 |
| mention | 评论中提及 | 中 | 无 | 打开任务时间线 | Task 时间线 |
| contract_change | 契约新版本或破坏性变更 | 中 | 按契约门 TTL | 查看影响并确认 | Task 详情 Contracts 标签 |
| dependency_ready | 依赖条件满足 | 低 | 无 | 启动下游任务 | Task 详情 |
| run_failed | Run 失败 | 中 | 无 | 查看日志、重试 | Run 详情 |
| crew_plan_ready | 队长计划提交 | 高 | 按 crew_plan 门 TTL | 审核计划 | Crew 视图 |
| evidence_unverified | 证据校验不一致 | 中 | 无 | 抽查并决定 | Evidence 面板 |

**条目呈现与排序**

- 每条显示类型图标、对象标题、状态徽标、优先级、来源（Agent 或系统）、创建时间与截止时间；紧急与已过期条目同时使用图标、文字与底色，不只靠颜色。
- 排序：紧急 > 高 > 中 > 低；同级按截止时间升序，再按创建时间升序。已读未处理条目保留在「待处理」，已处理条目移入「已处理」。
- 聚合与去重：同一对象同一类型的未处理条目只保留一条，更新其最新时间与摘要；同一任务 10 分钟内最多生成一条同类普通通知；审批与 escalation 不受限频（collaboration-and-review.md §10.3）。
- 图标与颜色的映射见 §7.9 的事件映射表；M2 只要求类型可辨，不要求插画。

**交互规则**

- 未读项有明确圆点与加粗标题；已读但未处理项仍保留在「待处理」筛选。
- 批量选择后可以「全部标记已读」，但不能批量批准、批量合并或批量拒绝；高风险决定必须逐条打开并确认（collaboration-and-review.md §8.2）。
- 支持 J 与 K 在列表中上下移动，Enter 或 E 打开，M 标记已读，Esc 返回列表。
- 空状态区分「全部处理完」与「还没有任何事项」，避免把无数据误读为完成。
- Inbox 不承载自由聊天，也不允许 Agent 主动写入营销式摘要；每个条目必须关联明确的 Task、Run、门禁或契约对象。
- 「已读」与「已处理」是两个不同状态：分别调用 `POST /api/inbox/{id}/read` 与 `POST /api/inbox/{id}/action`（collaboration-and-review.md §14.2），界面不得用已读代替处理。

**与 Run 评审的关系**

Run 完成后的 diff 评审在 Task 详情的 Review 面板进行。Inbox 不设独立的「待评审」类型：合并门创建时生成 `approval_request`，评审入口由 Board 的待评审筛选与任务页提示承担。若产品确实需要在 Inbox 中出现「待评审」条目，必须先扩展 collaboration-and-review.md §10.1 的类型表，本章不擅自增加第十一类。M2 里程碑文档仍写「六类事项」，与协作模块不一致，应按十类修订；本表以十类为准。

**审批门界面**

审批界面必须覆盖全部十一类门禁：design_review、api_contract_review、crew_plan、merge、push、staging、contract_break、high_risk_command、scope_change、destructive_operation 提供批准与拒绝页面；prod 提供计划、人工执行记录与回滚说明页面，不提供产品内「一键批准」。每个审批页至少展示：门禁类型与对象、请求人与时间、证据快照清单及校验状态、影响范围（分支、路径、命令或契约版本）、过期时间、历史决定记录。批准前必须逐项打开证据，不提供「一键批准全部」；拒绝必须填写原因；过期后对象回到待处理状态，界面不得允许对过期快照继续批准。

### 5.9 Settings 页面

**目标**：让用户确认本机连接、Runtime 与 Workspace 状态，并管理影响全局行为的偏好。

**M0 关键元素**

- API CONNECTION：Check health 按钮，成功后显示 OK 与版本号，失败显示错误文本。
- WORKSPACE：说明每个 Run 位于 `~/.ateam/workspaces/runs/{run-id}`，并注明 git worktree 隔离属于下一里程碑。
- ABOUT：声明 ATeam 为原创、本地优先实现。

**M1 至 M4 计划**

- 分页：Runtime、Workspace、Appearance、Notifications（M4 迁移为独立页）、Access、Plugins、Telemetry、About。
- Runtime 页：M1 列出 mock 与 Claude Code，显示可执行文件路径、版本、最后检测时间，并提供重新检测。M0 的注册表已包含 mock 与基础 claude adapter；该 adapter 只是把 `claude -p` 的输出逐行转成日志，没有结构化流式事件与权限参数，界面不得把它描述为「完整 Claude Code 集成」。Codex 属于 M2，不得列入 M1 可用列表。
- Workspace 页：M1 只读展示根目录、Run 的 worktree 路径、分支、base/head commit 与生命周期状态（`GET /api/runs/{id}/workspace`）；磁盘占用与手动清理入口属于 M2，见 UI-127 与 api-and-data.md §9.5。
- Appearance 页：字号密度、日志换行默认值、语言切换（M2，按 NFR-I18N-002）；不提供浅色主题。
- Notifications 页：M2 提供 Inbox 开关；M4 随通知中心提供桌面通知、声音与 Webhook 渠道开关。
- Access 页（M3）：成员、角色、审批策略；仅 Owner/Admin 可见。
- Plugins 页（M4）：插件来源、签名、权限差异、启停与卸载。
- Telemetry 页（M4）：遥测开关、数据预览与本地导出。
- About 页：版本、许可证、第三方依赖声明入口。

### 5.10 全局搜索与命令面板（M2）

**目标**：让熟练用户不离开键盘完成定位与动作。

- 快捷键 Cmd/Ctrl+K 打开命令面板。
- 搜索范围：Task 标题与描述、Agent 名称与描述、Run ID、标签。
- 动作范围：新建任务、新建 Agent、打开 Inbox、切换页面、启动选中任务的 Run。
- 结果分组并显示类型图标；最近访问项置顶。
- 不提供自然语言执行动作；命令必须对应明确的产品动作。
- 无结果时给出搜索建议与「新建任务」入口，而不是空白。

### 5.11 技能库与模板库（M2）

**目标**：让技能与模板成为可浏览、可版本化、可复用的产品对象，而不是只能藏在 Agent 编辑器里的多选列表。

**Skills 页面**

- 列表：名称、描述、标签、最新版本、被哪些 Agent 绑定、更新时间；支持搜索与标签筛选；默认按最近更新排序。
- 创建与编辑：名称、描述、instructions、文件清单、标签；保存草稿不发布版本。
- 版本：发布新版本后版本号单调递增且不可修改；版本历史可查看，提供两版差异视图；删除为软删除，被 Agent 绑定时返回冲突并提示先解绑。
- 详情：显示来源、版本、启用状态与绑定 Agent 列表；从 Agent 编辑器可跳转到技能详情。
- 权限：M2 本地用户可管理全部技能；M3 起按 Agent 可见性（private/team/shared）与角色矩阵控制，界面不得提前展示团队共享控件。

**Templates 页面**

- 角色模板：至少 UI Design、Frontend、Backend、DevOps 四类；预览包含职责说明、默认 instructions、默认 Runtime、默认 allowedPaths、默认 allowedCommands、必交契约/证据与默认审批门。
- 任务模板：至少 UI Design、Frontend、Backend、DevOps Staging、Bugfix、Feature；预览包含预填 DAG、角色、契约与证据要求。
- 从模板创建：复制模板内容生成独立 Agent 或 Task，并把模板版本与内容快照写入对象；后续模板升级不回溯修改已实例化对象，用户可手动升级并查看差异。
- 模板只能归档；仍被 Agent 或 Task 引用时不得删除，界面说明引用数量并提供跳转。
- 创建前显示影响预览：将生成的 Agent 数量、默认权限与证据要求，避免用户在不了解权限边界时一键创建。

### 5.12 Crew 与队长只读视图（M2）

**目标**：让用户理解队长如何拆分任务、谁在执行、卡在哪里，而不是让 Crew 成为黑箱。

- 入口：Task 详情在存在 Crew 时显示 Crew 标签页；同时支持 `/crews/:id` 只读路由直达。
- 页头：Crew 状态（planning、running、paused、blocked、completed、failed）、父任务链接、队长 Agent、预算使用（Run 数、总时长、重试次数）。
- 计划区：只读展示队长提交的子任务拆分、角色分配、依赖、契约清单、验收标准与人工确认点；已批准计划不得在界面内修改，范围变化必须走 `scope_change` 门。
- 成员区：每个成员的 Task、Agent、Run 状态、最近事件摘要与证据计数；失败的成员显示失败分类与重试入口。
- 人工控制：允许人工暂停、恢复、取消 Crew，均需确认并说明影响；不允许人工在只读视图中直接编辑计划或代替队长提交交付物。
- 阻塞与升级：死锁、预算超限、队长失败时显示明确原因与建议动作，并生成 escalation 或 crew_plan_ready 收件项。
- 空状态：没有 Crew 时不显示空标签页；Crew 未启动时说明可由队长计划创建，不提供「一键让多个 Agent 自由协作」入口。

## 6. 用户故事与验收标准

### US-UI-01 看板纵览

**作为**独立开发者，**我希望**打开应用就看到所有任务的状态分布，**以便**决定先处理哪一项。

- Given 本机已有 12 个任务，分布在 Backlog、Todo、In Progress、In Review
- When 我进入 Board
- Then 五列按固定顺序显示，每列显示任务数量；卡片显示标题、状态与优先级；页面在 1 秒内完成首屏渲染，不等待所有 Run 日志加载

### US-UI-02 拖拽更新状态

**作为**独立开发者，**我希望**把卡片拖到目标列即可更新状态，**以便**快速整理任务。

- Given 一个 Todo 任务
- When 我把它拖到 In Progress 并放下
- Then 状态更新请求发出；成功后卡片出现在目标列；失败时卡片回到原列并显示错误 toast；网络请求期间卡片有进行中样式且不可重复拖拽

M0 仅覆盖成功路径与前半段交互，失败回滚属于 M1 验收。

### US-UI-03 创建任务（M1 完整）

**作为**本地用户，**我希望**在看板直接创建任务并填写足够上下文，**以便**后续 Agent 可以直接运行。

- Given 我在 Board
- When 我点击 New task，填写标题与描述，选择 Todo，点击 Create
- Then 标题为空时 Create 不可提交并显示「Title is required」；成功创建后模态框关闭，新卡片出现在对应列顶部；失败时保留已填内容并显示可重试错误

M0 可以创建任务，但空标题只做静默返回，不显示错误文案；行内校验与失败重试属于 M1 验收。

### US-UI-04 启动并观察 Run

**作为**独立开发者，**我希望**从Task 详情启动 Agent 并实时看到执行进展，**以便**判断是否需要介入。

- Given 一个 Todo 任务与一个可用 Agent
- When 我选择 Agent 并点击 Run
- Then 立即出现新的 Run 项，状态从 Queued 进入 Preparing 再进入 Running；任务状态在同一响应后从 Todo 变为 In Progress，处理人显示为所选 Agent（M0 行为，TASK-023）；日志区域显示该 Run 的事件（M0 轮询刷新，M1 流式跟随）；Task 详情顶部显示活动 Run 标识；切换页面再返回时仍能看到同一 Run

M0 已具备运行列表即时插入、自动选中、日志轮询与启动 Run 时的状态/处理人副作用；顶部活动 Run 标识与真正的流式跟随属于 M1。

### US-UI-05 取消 Run

**作为**独立开发者，**我希望**在发现 Agent 跑偏时取消执行，**以便**停止浪费资源。

- Given 一个 Running 状态的 Run
- When 我点击 Cancel 并在确认框中确认
- Then 发送取消请求；状态在 3 秒内变为 Cancelled 或显示「正在取消」；日志保留；重复点击不会发出第二次请求

M0 的 Cancel 直接执行，没有确认框；确认交互与防重复提交属于 M1 验收。

### US-UI-06 评审 diff 与证据后合并（M1）

**作为**执行评审的本地用户，**我希望**在批准前看到 diff、测试与截图，**以便**做出有依据的决定。

- Given 一个 Completed 且带证据的 Run
- When 我打开 Review 面板
- Then 同屏可见 diff 统计、测试结果摘要与截图缩略图；Approve 按钮只有在证据加载完成后可用；点击 Merge 打开合并确认对话框，默认焦点在取消，提供 squash 与 merge 两种策略并展示冲突检测结果；有冲突时禁止合并并列出冲突文件；确认后显示合并结果与目标分支

### US-UI-07 审批门阻止未满足条件的合并（M2）

**作为**本地用户，**我希望**未满足评审与证据条件的合并在界面上被明确阻止，**以便**治理规则不依赖人的记忆。

- Given 一个已完成但缺少 approve 评审，或缺少测试证据的 Run
- When 我查看 Merge 入口
- Then 按钮禁用并显示缺少的评审结论或证据项；点击禁用的按钮不会发出请求；补齐后按钮恢复，合并确认对话框列出 Review 记录与证据快照
- 说明：M2 是单用户本地模式，审批人为本地用户，不显示角色或审批人数；按角色的审批缺口与双人评审属于 M3，见 US-UI-16

### US-UI-08 编辑 Agent

**作为**独立开发者，**我希望**修改 Agent 的指令与允许路径，**以便**让角色行为更符合项目规范。

- M1：Given 一个已有 Agent，When 我修改指令并把允许路径从 `web/` 改为 `web/, packages/ui/` 并保存，Then 保存成功后 toast 提示，离开页面不再提示未保存
- M2：When 我放宽允许路径，Then 保存前显示影响预览，列出新增可写路径；放宽权限触发二次确认，确认框说明风险；取消不保存

### US-UI-09 Inbox 处理待审批（M2）

**作为**本地用户，**我希望**在一个列表里处理所有待审批项，**以便**不遗漏任何门禁或失败。

- Given Inbox 有 3 条 approval_request（合并门）与 1 条 run_failed
- When 我用 J 移动到第二条并按 Enter
- Then 打开对应门禁对象或 Run 详情；返回后该条标记为已读但仍在待处理列表；完成审批或处理后移入已处理，列表显示剩余数量

### US-UI-10 断线重连

**作为**独立开发者，**我希望**在服务重启或网络中断时知道界面数据已过期，**以便**不基于旧状态做决定。

- Given 界面已连接 WebSocket
- When 服务停止
- Then 2 秒内出现「连接已断开，正在重试」横幅；日志停止追加并显示暂停原因；恢复后自动重连并按事件序号补齐缺失事件，横幅消失

### US-UI-11 键盘完成核心路径（M1）

**作为**熟练用户，**我希望**不离开键盘就能新建任务并启动运行，**以便**保持操作节奏。

- Given 我在 Board 且焦点不在输入框
- When 我按 N，输入标题，按 Cmd/Ctrl+Enter
- Then 任务创建成功；焦点回到新卡片；按 R 可启动该任务的 Run，且不会与浏览器刷新快捷键冲突

### US-UI-12 窄屏查看（M1）

**作为**在分屏环境工作的开发者，**我希望**在窄于 768px 的窗口下仍能查看任务与运行状态，**以便**不必频繁切换窗口。

- Given 视口宽度小于 768px
- When 我打开 Board 与 Task 详情
- Then 侧边栏变为抽屉；看板可横向滚动或切换状态；Task 详情纵向堆叠；主操作按钮始终可见且不溢出

### US-UI-13 权限不足（M3）

**作为**低权限成员，**我希望**在点击超出权限的操作前就知道原因，**以便**不反复尝试。

- Given 我的角色是 Viewer，或 Contributor 试图合并自己发起的 Run
- When 我打开 Task 详情或直接访问 Access、Machines、Audit
- Then Merge 按钮可见但禁用，并显示所需角色（Reviewer/workspace_admin/Admin）；无权限的团队页面显示权限不足状态或入口不渲染；错误信息不泄露受限数据
- 说明：M0-M2 是单用户模式，没有角色，不得用本故事验收 M2

### US-UI-14 空状态引导（M1 完整）

**作为**首次使用者，**我希望**在没有任何数据时知道下一步做什么，**以便**快速完成第一次 Run。

- Given 本机没有任何 Task 与 Agent
- When 我首次打开 Board
- Then 看板显示空状态与「Create your first task」入口；Agents 页面提示先创建角色 Agent；创建完成后空状态消失且不残留骨架屏

### US-UI-15 合并冲突与目标分支变化（M1）

**作为**执行评审的本地用户，**我希望**在合并前看到冲突与基准变化，**以便**不把不可合并的分支误合并。

- Given 一个已 approve 的 Run，但目标分支已前进，或合并预检发现冲突，或目标工作区有未提交修改
- When 我打开合并对话框
- Then 目标分支前进时提示需要重新评审并禁用合并；冲突时列出冲突文件与双方分支，禁止合并并提供中止；工作区不干净时提示先提交或 stash；合并失败显示错误原因与重试入口，不产生半完成状态

### US-UI-16 双人评审与角色审批（M3）

**作为**团队维护者，**我希望**合并审批遵循职责分离与角色矩阵，**以便**治理规则在多人环境下仍然成立。

- Given Contributor 发起的 Run 需要一名 Reviewer 批准，且发起人不能自批
- When Contributor 查看 Merge 入口
- Then 按钮禁用并显示「发起人不能批准自己的合并」；Reviewer 账号批准后按钮恢复；对话框列出审批角色、时间与证据快照 ID；Admin 覆盖审批需要填写理由并写审计

## 8. 交互与规则

### 8.1 拖拽规则

- 拖拽开始后 150 毫秒内显示可放置区域；合法列边框高亮，非法列显示禁止光标与原因。
- 放下时先执行本地校验，再发出请求；本地校验失败不发请求。
- M0 允许五列之间任意流转；M1 引入状态机规则后，拖拽必须遵守 Task 模块定义的状态流转表。
- 进入 Done 的条件在 M1 为「存在 approve 评审且必需 Evidence 齐全」；合并成功后 Task 默认进入 done。M2 起由审批门与交付物契约共同决定。界面不得仅凭 Run 完成就允许 Done。
- 拖拽失败必须回滚并弹出错误 toast；回滚动画不超过 200 毫秒，避免用户误以为操作成功。
- 多选拖拽在 M2 提供；拖拽多个任务时显示数量徽标，并在确认框中列出将受影响的任务标题。

| 类型 | 出现方式 | 持续时间 | 动作 | 可访问性 |

### 8.5 数据刷新与实时性

- M0 使用 WebSocket 事件触发列表重新拉取，Task 详情额外每 1.5 秒轮询活动 Run；这会造成重复请求，M1 统一为事件驱动加增量更新。
- WebSocket 断开后客户端每 2 秒重试；M1 起在界面上显示连接状态，并在重连后按事件序号补齐缺失事件。
- 日志增量追加，不整段重绘；用户暂停跟随后不得自动滚动到底部。
- 页面不可见时降低刷新频率；恢复可见时立即拉取一次快照。
- 所有时间显示为本地时区，悬停显示 UTC 与完整时间戳；相对时间超过 7 天改为绝对日期。

## 9. 数据与 API 影响

### 9.2 WebSocket 事件契约

M0 实际广播的事件（api-and-data.md §6.1）：`task.created`、`task.updated`、`task.deleted`、`agent.created`、`agent.updated`、`agent.deleted`、`run.queued`、`run.preparing`、`run.running`、`run.updated`、`run.event`。客户端当前对任意 `run.*` 事件重新拉取全部 runs 与 tasks，对 `task.*`、`agent.*` 分别全量刷新；这是 M0 实现，M1 改为按事件增量更新。

M1 起界面订阅的事件与消费方式：

| 事件 | 阶段 | 界面消费 |
|---|---|---|
| `run.completed` / `run.failed` / `run.cancelled` / `run.timeout` | M1 | 终态更新、完成或失败提示；`run.finished` 是旧名，只在一个里程碑内并行发送 |
| `merge.started` / `merge.completed` / `merge.failed` | M1 | 合并结果、Task 状态与目标分支；`run.merged` 是旧名 |
| `artifact.created` / `artifact.deleted` | M1 / M2 | 证据面板增量 |
| `review.requested` / `review.approved` / `review.changes_requested` / `review.superseded` | M1 | Review 状态与合并门；`review.created` 是旧名 |
| `run.workspace.provisioning` / `run.workspace.ready` / `run.workspace.failed` / `run.workspace.cleaned` | M1 | Workspace 状态条 |
| `events.replay_reset` | M1 | 丢弃增量并重新拉取快照 |
| `task.dependency.added` / `task.dependency.removed` | M2 | DAG 与就绪状态 |
| `deliverable.updated` | M2 | Contracts 与 Evidence 标签 |
| `approval.requested` / `approval.decided` / `approval.expired` / `approval.cancelled` / `approval.consumed` | M2 | Inbox 与审批页；`gate.*` 与 `approval.revoked` 是旧名 |
| `crew.updated` / `crew.plan_submitted` | M2 | Crew 视图 |
| `skill.created` / `skill.updated` / `skill.deleted` | M2 | Skills 页面与 Agent 绑定 |
| `inbox.updated` | M2 | 侧边栏未读徽标 |
| `evidence.added` / `comment.created` / `task.readiness_changed` | M2（collaboration §14.3） | 证据、时间线、Run 按钮 |
| `machine.online` / `machine.offline` / `machine.updated` | M3 | Machines 页面 |
| `run.unschedulable` | M3 | Run 详情排队原因 |
| `task.restored` | M2 | 恢复的 Task 重新出现在列表 |

事件规则：

- 事件名以 api-and-data.md §6.3 与 collaboration-and-review.md §14.3 为准，本章不定义新事件。M1 里程碑的 `run.status` 与 API 模块的 `run.updated` 语义重叠，统一前客户端按 `run.updated` 处理，并在第 16 节登记。
- M1 起每个事件携带全局 `id` 与单调递增 `seq`；客户端按 `id` 去重，不得依赖到达顺序做唯一真相判断。
- 重连握手携带 `afterSeq`；收到 `events.replay_reset` 时必须丢弃增量并重新拉取快照，不得静默忽略。
- 事件只携带摘要与对象 ID 时，客户端按需拉取详情；不得在事件载荷中期待完整证据内容。

### 9.3 客户端状态规则

- 服务端状态放在 Pinia store，按实体分域；store 不持有仅用于展示的临时状态。
- URL 保存视图状态：筛选、排序、搜索词、选中 Run、Task 标签页。刷新与分享必须可还原。
- localStorage 保存用户偏好：侧边栏折叠、列表密度、日志换行、最近使用的 Agent；键名带产品前缀与版本。
- 日志缓冲设置上限，超出后丢弃最旧的行并显示「较早日志已截断」；不得无限增长。
- 任何写操作在 UI 上必须有明确的三态：进行中、成功、失败。禁止「点击后无反馈」。
- 缓存失效以事件驱动为主，轮询仅作为降级；断线期间显示数据可能过期。

### 9.4 数据模型影响

为支撑界面，需要新增或明确的字段包括：Task 的验收标准与依赖关系；Run 的分支、Workspace、耗时、失败码与证据计数；Artifact 的类型、校验和、预览地址、大小与来源；Review 的评审人、决定、意见与时间；Approval 的门禁类型、证据快照、状态与决定记录（M3 增加角色与作用域）；InboxItem 的类型、优先级、关联对象、截止时间、未读与处理状态。字段定义以 02-domain-model.md 与 api-and-data.md 为准，界面只消费稳定字段，不直接依赖数据库列名。

## 10. 异常与边界

| 场景 | 界面行为 | 阶段 |
|---|---|---|
| 任务或 Run 不存在 | 显示专用不存在状态，提供返回列表与搜索入口；不显示空白页 | M1 |
| 服务未启动 | 顶部横幅提示无法连接 API；已缓存内容可读；提供重试 | M1 |
| WebSocket 断开 | 连接指示变为断开；日志暂停并标注；自动重连 | M1 |
| 拖拽请求失败 | 卡片回滚原列；错误 toast 含重试；不重复提交 | M1 |
| 并发修改冲突 | 显示服务器最新值并说明覆盖内容；提供刷新 | M2 |
| 表单校验失败 | 行内错误与错误摘要；焦点移到第一个错误字段 | M1 |
| Run 超时 | 状态为 Failed，错误分类为超时；提供调整超时或重试入口 | M1 |
| 取消与完成竞态 | 以服务端最终状态为准；界面显示「已完成，取消未生效」 | M1 |
| 日志量过大 | 虚拟滚动、截断提示、下载入口；页面不卡死 | M1 |
| diff 文件过大 | 显示统计并提供按文件加载或下载；不一次性渲染数万行 | M1 |
| 二进制文件 | 显示类型与大小，不渲染内容 | M1 |
| 证据缺失 | 评审面板显示「缺少测试证据」；Merge 按钮按策略禁用 | M1 |
| Workspace 被外部删除 | Run 详情显示路径失效；禁止打开；提供重新检测与重新启动 Run 的入口 | M1 |
| 合并冲突 | 阻止合并并列出冲突文件与双方分支；提供中止与人工处理说明，不自动解决 | M1 |
| 目标分支已前进 | 合并禁用并提示需要重新评审；不静默覆盖 | M1 |
| 目标工作区不干净 | 禁止合并，提示先提交或 stash | M1 |
| 合并失败 | 显示失败原因、重试与回滚说明；不产生半完成状态 | M1 |
| 本地令牌失效 | 显示会话失效并允许重新连接；不进入无限重试，不显示令牌 | M2.1 |

| 超长标题 | 页头最多两行并省略；悬停显示完整标题；列表内单行省略 | M0 部分，M1 完整 |
| 时区差异 | 默认本地时间，悬停显示 UTC；跨时区团队不产生歧义 | M2 |
| 窄屏旋转或缩放 | 布局重排不丢失选中对象；输入内容不丢失 | M1 |
| 剪贴板不可用 | 显示可手动选择的文本；提示复制失败原因 | M1 |

## 11. 权限与安全

### 11.1 M0 的信任模型

M0 是单用户、本地优先工具，没有登录、角色与团队权限。界面必须如实反映这一点：Settings 中不出现虚假的「团队安全」表述；API 默认仅监听本机回环地址；界面不展示或缓存模型密钥；任何外部链接在系统浏览器打开，不在桌面 WebView 内导航。

桌面壳会话令牌按 security-and-permissions.md SEC-003 定义，实际交付里程碑统一为 M2.1：桌面壳每次启动生成随机令牌并注入 WebView，除 `/api/v1/health`、`/api/v1/auth/bootstrap` 与 M3 登录端点外的 API 都要求令牌。界面不得显示、缓存或记录该令牌；令牌失效时的处理见 §11.5。M0-M2 仍然没有用户角色，任何「按角色审批」的界面都属于 M3，不得提前出现。

### 11.2 M3 角色能力矩阵

本节直接复用 security-and-permissions.md §4.2 的两层角色模型：Owner/Admin 为组织级，workspace_admin/Contributor/Reviewer/Viewer 为 Team Workspace 级；不另立角色，也不把本地单用户阶段包装成角色。组织 Member 未加入 Team Workspace 时没有该 Workspace 的任何界面能力。

|---|---|---|---|---|---|---|
| 查看 Task | 全部 | 全部 | 本 Team Workspace | 本 Team Workspace | 本 Team Workspace | 被授权范围 |
| 创建 / 编辑 Task | 是 | 是 | 是 | 是 | 否 | 否 |
| 删除 Task | 是 | 是 | 是（软删除） | 仅自己创建 | 否 | 否 |
| 创建 Agent | 是 | 是 | 是 | 是（private） | 否 | 否 |
| 编辑 Agent 权限 | 是 | 是 | 是（team） | 仅自己 private | 否 | 否 |
| 启动 Run | 是 | 是 | 是 | 是 | 否 | 否 |
| 取消 Run | 是 | 是 | 是 | 自己启动的 | 否 | 否 |
| 审批合并 | 是 | 是 | 是 | 否 | 是 | 否 |
| 审批 staging 部署 | 是 | 是 | 是 | 否 | 否 | 否 |
| 审批 prod 部署 | 是 | 是 | 否 | 否 | 否 | 否 |
| 管理成员与角色 | 是 | 是 | 否 | 否 | 否 | 否 |

矩阵是默认策略；自定义角色不在 M3 范围。界面实现采用「敏感页面隐藏、可发现动作禁用」的混合策略：Access、Machines、Audit 对无权限角色不显示入口；Task 上的 Merge 按钮保持可见但禁用并解释原因，避免用户误以为产品没有该能力。任何隐藏都不能替代服务端鉴权。

M2 的审批界面不出现角色列，只显示「本地用户」；若某页面在 M2 需要「所需角色」文案，说明该能力被错误提前，应移回 M3。

### 11.3 高风险动作

- **合并**：M1 必须经过「Review + confirm」对话框，展示源分支、目标分支、head commit、diff 统计、证据完整度与评审记录；请求携带 reviewId 与 expectedHeadCommit，commit 变化后旧评审失效。M2 引入 Approval 后，对话框展示门禁状态、证据快照与过期时间；未满足策略时按钮禁用。Agent 不持有合并入口。
- **推送**：界面不提供独立推送按钮；推送作为合并流程的一部分，或由用户在 Runtime 中显式执行。M2 的 DevOps Agent 只能生成推送计划，不得自主推送。
- **部署**：M2 只允许 staging 部署与部署计划生成，且需 staging 门批准；prod 部署必须人工在 ATeam 之外执行，界面最多展示计划与人工执行检查清单，不提供「一键上线」。
- **门禁批准**：十一类门禁必须逐项查看证据后决定；过期快照不可批准；拒绝必须填写原因；合并、prod 与 contract_break 不允许批量审批。
- **删除**：删除 Task、Agent、Workspace 与清理日志都需确认；Workspace 清理属于 M2，需输入名称或 Run 分支确认；删除操作不提供「不再提示」。
- **权限放宽**：需要二次确认并展示影响预览；管理员操作写入审计（M3）。

### 11.4 内容与渲染安全

- Task 描述、Agent 指令、评论与日志按纯文本或经过清洗的 Markdown 渲染，禁止直接插入原始 HTML。
- 外部链接统一使用安全属性打开，桌面端交给系统浏览器；不在 WebView 内加载远端页面。
- 密钥、令牌、环境变量值在界面上只显示「已配置」或「未配置」，不提供查看明文入口。
- 日志渲染前进行敏感信息遮蔽，至少覆盖常见令牌格式；遮蔽规则由安全模块维护。
- 证据预览使用隔离的渲染容器；图片与文本可预览，可执行文件不可预览、不可自动下载执行。
- 复制操作不复制隐藏的敏感字段；复制路径时只复制路径，不附带环境变量。

### 11.5 本地令牌在客户端的处理

security-and-permissions.md SEC-003 要求本地会话令牌，交付里程碑统一为 M2.1；api-and-data.md 的认证端点同样标注 M2.1。客户端按以下规则实现：

- 桌面壳：每次启动生成 256 位随机会话令牌，通过 Wails 绑定或一次性 URL 片段注入 WebView；令牌只保存在内存，刷新后通过绑定重新获取。界面不提供查看、复制或编辑令牌的入口。
- 浏览器模式：服务启动时打印一次性 bootstrap URL；页面通过同源 `POST /api/v1/auth/bootstrap` 换取会话令牌，并用 `history.replaceState` 清除 URL 片段；会话令牌存放在 sessionStorage 或内存中，关闭标签页即失效。界面不得把令牌写入 localStorage、日志或错误上报。
- 请求携带 `X-ATeam-Token` 或 `Authorization: Bearer`，由统一 API client 注入，页面代码不直接读取令牌。
- WebSocket 不能设置自定义头，必须使用短期一次性 ticket：客户端用会话令牌调用 `POST /api/v1/auth/ws-ticket`，再以 ticket 建立连接；不得把长期令牌放在查询参数中。
- 收到 401 时显示「本地会话已失效」横幅，提供重新连接动作；不得无限自动重试，也不得回退到无认证请求。
- 令牌缺失或注入失败时，页面显示可诊断的错误（例如「桌面壳未提供会话令牌」），而不是空白页或静默失败。

## 12. 指标

指标用于验证界面是否真的降低认知负担，而不是衡量点击量。所有指标默认本地计算，跨设备上报必须选择性加入。目标值在 M1 建立基线后校准，当前为产品假设。

| 指标 | 定义 | 目标 | 测量方式 | 阶段 |
|---|---|---|---|---|
| 首次价值时间 | 从首次启动到完成第一次成功 Run 的时间 | 3 分钟内 | 本地事件时间戳 | M1 |
| 任务创建完成率 | 打开新建任务表单后成功创建的比例 | 不低于 90% | 本地埋点 | M1 |
| 启动 Run 步骤数 | 从 Task 详情到 Run 创建所需的点击次数 | 不超过 2 次 | 交互路径评审 | M1 |
| 评审证据打开率 | 批准前打开过 Diff 或 Evidence 的评审占比 | 100% | 本地埋点 | M1 |
| 评审时长 | 从打开 Review 到作出决定的中位时间 | 5 分钟内 | 本地事件 | M2 |
| 合并绕过次数 | 未展示证据即完成合并的次数 | 0 | 服务端校验 | M1 |
| 看板拖拽失败率 | 拖拽请求失败占总拖拽的比例 | 低于 2% | API 结果 | M1 |
| 列表首屏时间 | 看板 200 张卡片下的可交互时间 | 1 秒内 | 性能采样 | M1 |

## 13. 依赖与风险

### 13.1 依赖

- **共享类型与 API 客户端**：界面依赖 `@ateam/shared` 的状态枚举、标签与实体类型，以及 `@ateam/api-client` 的请求方法。字段变更必须同步更新前端，避免界面显示未定义状态。
- **Task、Agent、Run、Workspace、Evidence 模块**：页面语义依赖这些模块的对象定义与状态机。界面不自行发明状态。
- **Runtime 适配器**：Run 时间线的工具、文件、测试事件来自 Runtime 适配器的流式解析；适配器不产出的事件，界面无法展示。
- **Wails 桌面壳**：打开文件夹、系统通知、窗口尺寸与外部链接行为依赖桌面壳能力；Web 开发模式下需提供降级。
- **设计资产与图标集**：统一使用本地打包的线性图标，不能依赖运行时从 CDN 拉取，避免离线失效。

### 13.2 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 信息过载 | 看板与Task 详情塞入过多状态，用户反而看不清 | 渐进披露；默认只显示决策必需信息；高级信息收进折叠区 |
| 状态语义漂移 | Task 与 Run 状态在界面与 API 中不一致 | 状态枚举单一来源；徽标与筛选共用映射；契约测试 |
| 文档间事件与端点命名漂移 | 界面调用不存在的路径或事件，联调返工 | 以 api-and-data.md 与 collaboration-and-review.md 为单一来源；契约测试；第 16 节登记的差异在 M1/M2 开工前清零 |
| 合并冲突与策略差异 | 用户误合并或无法完成闭环 | 合并前预检；冲突时阻止并列出文件；策略与默认值在 M1 开工前统一；不提供 force merge |
| 日志与时间线重复 | 用户不知道看哪个 | 时间线只放关键事件；日志作为独立标签；默认定位到摘要 |
| 证据查看器复杂 | 评审成本上升，用户跳过证据 | 首屏给摘要与缩略图；详情按需展开；Merge 前强制显示证据清单 |
| 审批疲劳 | 频繁确认导致用户盲目点击 | 只对高风险动作强确认；常规动作不弹窗；确认按钮文案具体 |
| 并行运行性能 | 多日志流导致界面卡顿 | 虚拟滚动、增量追加、页面不可见降频、日志上限 |
| 拖拽可访问性差 | 键盘用户无法流转任务 | 提供菜单替代；快捷键；焦点管理；不把拖拽作为唯一入口 |
| 窄屏降级不完整 | 小屏用户无法完成关键操作 | 明确支持边界；核心路径优先；表格降卡片；按钮固定可见 |
| 深色主题对比度不足 | 小字号辅助信息难读 | 提高小字号文字亮度；实测对比度；不以浅灰承载关键信息 |
| 桌面 WebView 差异 | macOS 与 Windows 行为不一致 | 以标准 Web API 为主；关键能力做能力检测；在两类窗口实测 |
| 文案语言不一致 | 界面英文、文档中文导致理解偏差 | M0/M1 保持英文界面并设置 lang=en；M2 按 NFR §6.6 引入资源文件与语言切换；不混用半句翻译 |
| 未保存丢失 | 编辑 Agent 指令时误导航 | 脏状态拦截；自动草稿；保存成功提示 |

## 14. 里程碑映射

### M0：骨架（当前已完成部分）

已实现的界面能力：固定侧边栏与四个一级入口；Board 五列、卡片、拖拽、创建任务；Task 详情描述、Run 启动、运行列表、轮询日志、取消；Agents 列表与创建；Runs 表格；Settings 健康检查与说明；深色主题基础 token；WebSocket 触发列表刷新。Runtime 注册表包含 mock 与基础 claude adapter（行式输出，非结构化流式，无权限参数）。

M0 明确未实现：Inbox、独立 Run 详情、Agent 编辑、diff、证据、评审、审批、连接状态、toast、确认对话框、快捷键、焦点陷阱、响应式折叠、可访问性系统化验证、i18n。

M0 的界面退出标准是「可以演示完整骨架」，不是「可以日常使用」。当前状态符合这一标准。

### M1：本地闭环的界面

交付内容：

- Task 详情三栏结构：上下文、执行、评审；启动 Run 后按 M0 规则同步任务状态与处理人。
- Run 详情独立页面与结构化时间线，Workspace 状态与生命周期可见。
- Diff 查看器、Evidence 面板、Review 决定与合并确认对话框；合并策略、冲突检测、目标分支变化与失败处理可见。
- Agent 编辑、删除、影响预检与 Prompt 预览；mock Run 显著标识。
- 全局连接状态、本地令牌失效处理（M2.1 起）、toast、确认对话框、错误边界、骨架屏。
- 侧边栏折叠、基础快捷键、模态框焦点管理、WCAG AA 基线。
- 响应式断点 640、768、1024、1280 的基础降级。
- Workspace 只读元数据展示；Workspace 清理与 Run 记录删除不在 M1。

退出标准：独立开发者可以在不打开终端查看日志的情况下完成「创建任务、启动 Run、查看 diff 与测试、批准、合并」；合并冲突与目标分支变化被明确阻止；所有高风险动作有确认；键盘可完成核心路径；无严重可访问性问题。

### M2：角色协作的界面

交付内容：

- Inbox 一级入口与协作模块定义的十类事项，覆盖 gate_expired、escalation、contract_change、crew_plan_ready、evidence_unverified。
- Task 详情标签页：Overview、DAG、Contracts、Gates、Evidence、Timeline；DAG 局部视图与依赖编辑；交付物契约面板。
- 十一类门禁的审批界面与证据快照查看；审批人为本地用户，不显示角色列。
- Agent 角色模板、技能编辑器、路径与命令权限编辑器、风险分级；Skills 与 Templates 页面。
- Crew 与队长模式的只读编排视图，不提供多 Agent 自由聊天。
- 保存视图、看板筛选、批量操作、命令面板、快捷键帮助。
- Inbox 十类的排序、聚合、截止时间与去重；Evidence 校验状态展示。
- i18n 基础设施与中英切换（按 non-functional-requirements.md §6.6；若 M2 决策推迟则从本里程碑移出）。
- 更完整的响应式与 200% 缩放支持。

退出标准：UI Design、Frontend、Backend、DevOps 四类 Agent 可以通过任务依赖与交付物契约协作；十类 Inbox 条目均可生成、找到入口并处理；所有合并与部署计划都经过显式审批；审批与 escalation 不积压，P0 待办在 24 小时内处理。

### M3：团队模式的界面

交付内容：

- 登录与邀请接受、会话失效与只读模式。
- Access（成员与角色）、Machines（注册与状态）、Audit（审计查看器）。
- 两层角色矩阵对应的导航可见性与禁用态；发起人不能自批。
- GitHub PR 状态面板与合并联动。
- 共享 Agent 的可见性、版本快照与权限差异展示。

退出标准：2 至 10 人团队可以共享任务与 Agent，权限边界在界面上可理解，所有高风险动作可追溯。页面内部规格以 `../milestones/M3-team-mode.md` 为准，本章只约束入口、可见性与状态呈现。

### M4：自动化与分发的界面

交付内容：

- 定时与 Webhook 自动化编辑器（列表、详情、运行历史、dry-run 预览）。
- 通知中心与桌面通知设置；通知内容最小化与深链。
- Wails 打包后的更新提示、版本信息与回滚状态。
- 插件设置页与受限的界面扩展点。
- 可选遥测开关与本地数据导出。
- 安装器、许可与关于页本地化；主界面的语言切换已在 M2 按 NFR 交付。

退出标准：自动化任务可配置、可暂停、可审计；安装包在各平台可启动并完成首次 Run；用户能理解并控制数据上报。页面内部规格以 `../milestones/M4-automation-and-packaging.md` 第 6 节为准。

## 16. 待确认与未文档化

以下问题需要在对应里程碑进入开发前确认。每项都给出建议默认值与决策责任角色，未确认前按建议默认值执行，但不得在对外文档中写成最终结论。

1. **界面文案语言**：当前代码中的界面文案为英文，产品文档为简体中文。non-functional-requirements.md §6.6 已把 i18n 基础设施与中英切换放在 M2，并要求 M1 至少把 HTML lang 设为 en。建议按此执行：M1 英文界面且 lang=en，M2 提供资源文件与语言切换，M4 补安装器与关于页本地化；若产品决定推迟，必须先修订 NFR-I18N-001 至 003，不能只在 UI 章节改口径。此事影响所有页面的文案验收与截图基线。
2. **是否支持浅色主题**：本章将浅色列为非目标。若团队需要在强光环境使用，需单独评估 token、对比度与截图回归成本，不能以简单反色实现。
3. **Board 拖入 Done 的语义**：是仅改变任务状态，还是隐含「验收通过」？建议 M1 为状态变更，验收与合并分别记录；M2 由门禁与契约决定。需要与 Task 与 Collaboration 模块共同确认。
4. **Inbox 的归属阶段**：产品简报将 Inbox 放在 M2。若 M1 的评审通知没有落点，是否需要在 M1 提供最小「待评审」筛选作为过渡？建议 M1 在 Board 增加待评审筛选，M2 再引入完整 Inbox；但「待评审」不新增 Inbox 类型，理由见 §5.8。
5. **Run 详情与 Task 详情的日志分工**：完整日志放在 Run 详情，Task 详情只显示当前活动 Run 的摘要与最近事件。需要确认用户是否习惯从 Task 详情直接取消，而不进入 Run 详情。
6. **diff 渲染方案与阈值**：采用自研轻量渲染还是引入成熟组件，需要评估许可证、包体积、虚拟滚动与大文件表现。本章只约束行为，不指定库。阈值建议单文件 5000 行、单 Run 200 个文件时降级为按需加载。
7. **证据保留与展示期限**：截图与测试输出占用磁盘，界面需要知道何时显示「已清理」。保留策略与磁盘配额属于 Workspace 与 Evidence 模块，需共同定义。
8. **审批身份在 M2 的含义**：M2 没有登录，审批记录只能记录本机操作者与确认时间（security-and-permissions.md §4.1 明确本地用户不是安全认证）。是否需要在 M2 引入轻量本地身份，还是等 M3 账号体系？建议 M2 记录本机用户名与机器标识，M3 绑定真实账号。
9. **DevOps 的 staging 能力边界**：M2 允许生成部署计划与执行 staging，但 staging 的凭据来自本机环境变量还是 ATeam 配置尚未定义。界面在凭据缺失时必须禁用执行并说明，不得提供明文输入密钥的字段。
10. **快捷键与操作系统冲突**：Cmd/Ctrl+B 在部分编辑器内是加粗，G 序列可能与输入法冲突。需要在 macOS、Windows、Linux 的 Wails 窗口内实测，并提供全量禁用开关。自定义键位不在 M1-M2 承诺；若需要，先补 FR 与冲突检测设计。
11. **桌面最小窗口与移动浏览器支持边界**：本章建议桌面最小 1024×640（与 NFR-PORT-006 一致），窄屏只保证 360px 可读，统一断点为 360/640/768/1024/1280/1440。是否将移动浏览器列为正式支持范围，需要产品与测试共同确认。
12. **通知渠道与默认值**：Inbox 默认开启；桌面系统通知默认开启还是关闭？建议默认开启但可一键关闭，且审批类通知不可被静默丢弃，至少保留在 Inbox。
13. **命令面板的权限边界**：命令面板是否允许执行合并、删除等高风险动作？建议只允许导航与低风险创建动作，高风险动作必须在对应页面确认。
14. **可访问性验收工具与责任人**：需要确定使用哪些自动扫描工具、是否进行读屏人工测试、以及每个里程碑的验收责任人。未确定前，M1 以「核心路径键盘可达、无严重对比度问题、模态框焦点正确」为最低门槛。
15. **UI 组件的长期归属**：基础组件（Modal、EmptyState、StatusBadge、TaskCard）已集中在 `apps/web/src/components/`，但没有形成独立组件层、组件预览页与稳定的 props 契约。M1 是否整理为可复用组件库，需要前端负责人决策；本章只要求行为一致，不强制目录结构。
16. **事件命名与目录差异（已裁决）**：以 api-and-data.md §6.3/§6.4 为唯一事件目录；M1 使用 `run.completed`/`run.failed`/`run.cancelled`/`run.timeout`、`run.workspace.*`、`merge.*`、`review.requested` 等规范名；`run.finished`、`run.merged`、`workspace.*`、`gate.*`、`contract.*` 为旧名，客户端按 §9.2 的映射处理。
17. **合并默认策略（已裁决）**：策略枚举统一为 `squash`、`merge`、`rebase`，M1 默认 `squash`、可选 `merge`，M2 增加 `rebase`；api-and-data §5.7 与 M1 里程碑已按此回写。
18. **Inbox 类型数量**：collaboration-and-review.md §10.1 定义十类，`../milestones/M2-role-agents.md` 第 4.3 与 AC-M2-F-13 仍写「六类」。建议以十类为准并修订里程碑文档；否则 M2 验收会漏掉 gate_expired、escalation、contract_change、crew_plan_ready、evidence_unverified。
19. **本地令牌的阶段（已裁决）**：security-and-permissions.md SEC-003、api-and-data.md 认证端点与 04 AC-SEC-01 统一为 M2.1；本章 UI-140 与 §11.5 按 M2.1 交付，M1 只做 Origin/Host/CORS 收紧。
20. **搜索与偏好端点**：命令面板需要跨实体搜索，Settings 需要持久化偏好，但 api-and-data.md 未定义 `search` 与 `preferences` 端点。M1 建议偏好存 localStorage、M2 搜索先做本地过滤；若要服务端能力，必须先补 API 合约。
21. **M3/M4 页面规格归属**：本章只定义入口与可见性，Access、Machines、Audit、Automations、Notifications、Plugins、Telemetry 的字段与交互由里程碑文档承接。需确认里程碑文档在对应阶段进入开发前已经包含可验收的页面规格，避免出现「有交付项、无页面规格」的空洞。
22. **API 版本前缀与协作模块端点路径**：本章与 api-and-data.md 约定 M1+ 使用 `/api/v1`，但 collaboration-and-review.md §14.2 的契约、门禁、Crew、Inbox 端点写成未版本化的 `/api/...`。M2 开工前必须统一为同一前缀；本章 §9.1 暂按协作模块原样列出并加注，不自行改写其合约。
