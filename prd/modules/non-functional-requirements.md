# 模块：非功能需求

## 本章导读

本章定义 ATeam 在性能、可靠性、可移植性、可观测性、可访问性、国际化、打包与升级、资源占用、离线与弱网、成本、安全与隐私等方面的非功能需求。它回答的不是「功能做什么」，而是「在什么条件下、以什么质量水平、在多长的时间内、以多少资源把功能做可靠」。

阅读建议：

- 产品与决策者：先读第 5 节（现状与目标总览）、第 11 节（指标）、第 12 节（验收标准）、第 14 节（里程碑映射）。
- 工程师：重点读第 6 至第 10 节，其中每个需求都带编号、验收方法、优先级和里程碑。
- 测试与发布负责人：重点读第 9 节（异常与边界）、第 12 节（验收方法）以及第 13 节（依赖与风险）。

状态口径：

- 「已实现（M0，需回归）」表示当前仓库代码已经具备该能力，后续里程碑仍须保留回归测试。
- 「计划（M1）」至「计划（M4）」表示目标需求，不得在对应里程碑完成前对外宣称已具备。
- 本章的 M0 事实以当前仓库代码为准；功能与契约（API、数据、安全、协作）以对应模块文档为准，本章不重复定义，只规定它们必须满足的质量边界与里程碑归属。
- 若本章与其他文档冲突，先修改对应模块文档与里程碑，再更新本章；不允许同时存在两套口径。

编号规则：本章统一使用 `NFR-<DOMAIN>-###` 命名空间：NFR-PERF（性能）、NFR-REL（可靠性）、NFR-PORT（可移植性）、NFR-OBS（可观测性）、NFR-A11Y（可访问性）、NFR-I18N（国际化）、NFR-PKG（打包与升级）、NFR-RES（资源占用）、NFR-NET（离线与弱网）、NFR-COST（成本）、NFR-SEC（安全与隐私）。该命名空间是 PRD 内非功能需求的唯一编号来源；`01-scope-and-roadmap.md` 与里程碑文档中的旧 `NFR-001` 至 `NFR-010` 编号按第 1.5 节映射为历史别名，不得用于新增需求或缺陷跟踪。

## 1. 目的与范围

### 1.1 目的

ATeam 的核心承诺是「本地优先、多 Agent、证据化完成」。这三点都不是纯功能问题：本地优先意味着数据、日志、工作区和模型调用边界必须可控；多 Agent 意味着并发、资源占用、调度公平性和故障隔离必须可度量；证据化意味着 Run 时间线、日志、指标和诊断信息必须可信、可追溯、可导出。本章把这些承诺转化为可测试的工程约束，作为架构设计、实现评审、测试验收和发布门禁的统一依据。

具体目标包括：

1. 给出每一类非功能需求的量化目标，避免「感觉很快」「应该没问题」式的验收。
2. 明确 M0 已实现能力与 M1-M4 计划能力的边界，防止把规划写成现状。
3. 为多 Agent 并行、日志洪峰、崩溃恢复、升级失败等高风险路径规定降级与兜底行为。
4. 为安全、隐私、成本与合规提供最低约束，尤其是 BYOK、代码不出本机、高风险动作人工审批这三条底线。
5. 为后续团队模式（Postgres、远程 Runner、登录权限）预留可扩展的非功能口径，避免 M3 推倒重来。
6. 建立跨文档唯一的指标表与编号映射，使测试计划、发布检查单和缺陷跟踪可以引用同一个键。

### 1.2 范围

本章覆盖以下产品表面：

- 桌面端：Wails v3 原生窗口加内嵌 WebView，M0 已存在，M4 正式打包分发。
- 浏览器开发模式：Go 服务加 Vite 开发服务器，M0 已存在，主要用于开发与调试。
- 本地服务：HTTP API、WebSocket 事件流、SQLite 持久化、进程内调度器。
- Runtime 边界：本机 Claude Code、Codex 或 mock Runtime 的进程调用、输出采集、超时与取消。
- 数据边界：Task、Agent、Run、RunEvent、Workspace、Artifact/Evidence、审批与审计记录。
- 团队与远程形态：M3 的 Postgres、登录权限、远程 Runner、机器注册；本章只规定非功能约束，不展开业务模型。
- 分发形态：M4 的 DMG、NSIS、AppImage、自动更新、签名与公证、遥测与崩溃上报。

本章不覆盖：具体页面布局、字段级校验规则、任务状态机细节、Agent 模板内容、协作流程的逐步交互、数据库表结构与 API 端点清单。这些由对应功能模块与 API 模块定义；本章只规定它们必须共同满足的质量边界。

### 1.3 基线环境与测量口径

所有性能与资源目标默认在基准 A 上测量，并记录实际机器配置。Windows 与 Linux 的验收基线按 `01-scope-and-roadmap.md` §6.3 在 M4 补充；M1-M3 的 Windows/Linux 数据只用于内部开发验证，不构成对外支持承诺。

| 基准 | 硬件与系统 | 用途 |
|---|---|---|
| 基准 A（验收基线） | 8 核 ARM64（Apple Silicon），16 GB 内存，SSD，macOS 14 或更高；Go 1.27，Node 24 | 所有性能与资源门禁的验收基准 |
| 基准 A-min（最低支持机） | Apple MacBook Air M1，8 GB 内存，macOS 14 或更高 | 只做可用性冒烟与降级验证，不作为指标门禁 |
| 基准 B（计划） | Windows 11 x64，4 核 CPU，16 GB 内存，SSD | M4 补充并用于 Windows 发布验收 |
| 基准 C（计划） | Ubuntu 24.04 x64，4 核 CPU，16 GB 内存，SSD | M4 补充并用于 Linux 发布验收 |

测量规则：

1. 性能数据必须来自 release 构建，不得使用 `go run` 或 Vite 开发服务器数据作为发布依据。
2. 冷启动指进程启动到看板首次可交互（任务数据已渲染且可点击）；热启动指系统缓存已存在时的同等过程。每项至少测量 10 次，报告 p50 与 p95，取 3 轮中的中位数。
3. API 延迟在服务端中间件计时，包含 JSON 序列化，不包含浏览器渲染；UI 延迟用浏览器 Performance API 或桌面端打点测量。
4. 内存以常驻内存集 RSS 计，桌面端合计包含 Go 服务进程与 WebView 进程；Runtime 子进程单独记录，不计入 ATeam 自身内存，但按第 6.8 节单独纳入并发总预算。
5. 日志吞吐以持久化成功并可通过事件接口读回为准，不以仅广播到 WebSocket 为准；主动截断必须与丢失分开统计。
6. 网络基线为本地回环；模型调用延迟不计入产品性能指标，但必须单独记录并展示。
7. 数据集基线：1,000 个 Task 与 100 个 Agent（列表默认单页 limit=50）、10,000 条 RunEvent、50 个 Workspace 目录（只测目录准备与清理）。压力数据集为 5,000 个 Task、全局事件日志 100,000 条、单 Run 20,000 条事件。
8. 任何要作为发布门禁的指标，必须登记在第 1.5 节的映射表中，注明指标、定义、目标、基准机、数据集、里程碑与 owner；未登记的数字只能作为参考，不得用于验收。

### 1.4 状态标记约定

需求表中的「状态」列使用以下值：

- 已实现（M0，需回归）：当前代码已具备，后续变更不得破坏。
- 计划（M1）：本地闭环里程碑必须交付。
- 计划（M2）：角色 Agent 协作里程碑必须交付。
- 计划（M3）：团队模式里程碑必须交付。
- 计划（M4）：自动化与分发里程碑必须交付。
- 持续：跨里程碑长期有效的策略性约束。

当一条需求跨多个里程碑时，状态列必须写明分段，例如「计划（M1 本地；M3 团队）」，不得把已实现部分与计划部分混在同一状态里。

## 2. 非目标

以下内容明确不在本章或近期产品范围内，避免范围蔓延：

1. 不把 ATeam 做成模型托管、模型转售或统一计费平台。ATeam 不代管用户额度，不代理模型请求，不赚取模型差价。
2. 不以移动端、平板端或纯 Web SaaS 为初期目标；M1-M3 的主形态是桌面端加本地服务。
3. 不追求 WCAG AAA 全量认证；核心流程以 WCAG 2.1 AA 为目标，非核心装饰性内容允许记录豁免。24×24 像素目标尺寸是产品自定的人机工程目标（与 WCAG 2.2 SC 2.5.8 对齐），不作为 WCAG 2.1 AA 合规声明。
4. 不承诺跨机器强一致或分布式事务；M1-M2 是单机单库，M3 的团队模式采用中心库加远程 Runner 的最终一致性模型。
5. 不保证任意 Linux 发行版和任意 WebKitGTK 版本可用；M4 起只保证第 6.3 节列出的 Tier 1 环境，M1-M3 的 Linux/Windows 构建仅用于内部验证。
6. 不对第三方 Runtime CLI 的内部行为、模型质量、供应商可用性做保证；ATeam 只保证调用边界、超时、取消、证据采集和错误呈现。
7. 不在 M1-M2 提供多租户隔离、组织级配额、云端审计导出；这些属于 M3 及以后。
8. 不在本章定义具体 UI 组件尺寸、配色 token 和页面信息架构；这些由 `ui-ux.md` 定义，但必须满足本章的可访问性与性能约束。
9. 不承诺自动修复损坏的数据库；ATeam 提供备份、诊断和恢复指引，不擅自删除用户数据。
10. 不在默认配置下上传任何遥测、崩溃报告、提示词、代码或使用记录。
11. 不在本章重复定义数据库表、API 端点或错误码目录；这些由 `api-and-data.md` 维护，本章只引用。

## 3. 角色与场景

### 3.1 角色

| 角色 | 关注点 | 非功能诉求 |
|---|---|---|
| 独立开发者 | 同时运行 3-5 个 Agent，频繁切换任务与评审 | 启动快、Run 启动快、日志不卡顿、磁盘可控、成本可见 |
| 小团队成员 | 2-10 人共享任务、Agent、机器 | 数据可靠、审计可查、并发不互相拖垮、升级不丢数据 |
| 评审者 | 查看 diff、测试证据、截图和 Run 时间线 | 证据完整、时间线准确、可访问性良好、可导出 |
| 角色 Agent（UI Design、Frontend、Backend、DevOps） | 按任务 DAG 与交付物契约工作 | 工作区隔离、路径与命令权限、超时与取消、失败可诊断 |
| 团队管理员（M3） | 管理成员、机器、预算、审计 | 登录权限、远程 Runner 健康、预算与配额、审计留存 |
| 支持与诊断人员 | 根据用户反馈定位问题 | 结构化日志、诊断包、指标、可复现的环境信息 |

### 3.2 关键场景

| 场景 | 触发 | 期望结果 |
|---|---|---|
| 首次启动 | 用户安装后首次打开 | 3 秒内看到空看板与引导（M4 打包应用 5 秒内）；无需联网；数据目录自动创建且权限正确 |
| 大看板 | 看板有 1,000 个 Task | 首屏只加载第一页（默认 50 条）与统计，1.5 秒内可交互；滚动与筛选按游标继续加载，不一次性载入全量 |
| 并行 Run | 同时启动 5 个 Run | 调度公平；UI 不冻结；日志按 Run 隔离；ATeam 自身内存 ≤700MB，三路并发含 Runtime 总 RSS ≤2GB |
| 日志洪峰 | 某个 Run 每秒输出数百行 | 事件不丢、顺序不乱、UI 合并渲染、磁盘写入可控；达到单 Run 上限时明确标记截断而不是假装完整 |
| 运行中崩溃 | 应用被强杀或系统断电 | 重启后 queued Run 重新入队，preparing/running Run 标记 failed 且 errorCode=interrupted/app_restart，保留事件，可重试，不出现「永久运行中」 |
| 升级 | 用户安装新版本 | 数据自动备份与迁移；失败可回滚；签名校验通过；不丢任务与证据 |
| 离线 | 网络断开或模型供应商不可用 | 本地 CRUD 与评审照常；Run 给出明确错误分类与重试入口；不阻塞启动 |
| 预算告警（M3） | 某 Agent 月度用量达到阈值 | 80% 提醒；100% 阻止新 Run 并要求显式覆盖；记录审计；单用户模式不承诺费用硬限制 |
| 键盘操作 | 用户不使用鼠标 | 建任务、改状态、启动/取消 Run、评审、合并均可完成；焦点可见且顺序合理 |
| 中英切换（M2） | 用户在设置中切换语言 | 无需重启；日期、数字、时区、文案同步切换；布局不溢出 |
| 空状态 | 无 Task、无 Agent、无 Run，或搜索无结果 | 区分「尚无数据」与「筛选无结果」，给出解释与一个主入口；读屏可播报，不残留骨架屏 |
| 依赖阻塞（M2） | 下游任务依赖未满足 | 任务显示 blocked 与阻塞原因，禁止启动 Run；依赖满足后自动解除，无需手工刷新 |
| 等待审批（M2） | 高风险动作提交审批 | 显示等待审批状态、审批人与到期时间；审批前不执行；超时默认拒绝 |

## 4. 用户故事（Given/When/Then）

### 4.1 性能

**US-NFR-01 冷启动**

Given 用户已安装 ATeam 且本地已有 1,000 个 Task  
When 用户双击图标启动应用  
Then 开发桌面壳在基准 A 上 p95 不超过 3 秒进入可交互看板（M4 打包应用不超过 5 秒），期间显示明确的加载状态，不出现白屏或假死。

**US-NFR-02 Run 启动**

Given 调度器有空闲 worker，Task 状态为 todo  
When 用户点击 Run 并选择 Agent  
Then 300 毫秒内看到 Run 进入 queued，1.5 秒内进入 running，日志区域开始出现事件，且 Task 自动变为 in_progress。

**US-NFR-03 日志洪峰**

Given 一个 Run 正在持续输出日志  
When 输出速率达到每秒 200 条并持续 60 秒（未触及单 Run 20,000 条上限）  
Then 事件全部持久化、序号连续、UI 不冻结，用户仍可切换页面和取消 Run；若持续速率使单 Run 达到 20,000 条或 50 MB，系统追加 `EVENTS_TRUNCATED` 告警，Run 继续执行且验收只统计未截断窗口。

**US-NFR-04 大列表加载**

Given 数据库中有 5,000 个 Task  
When 用户打开看板并滚动列表  
Then 前端只按服务端游标逐页加载（默认每页 50 条，最大 200 条），已加载窗口不超过 500 行；超过窗口的搜索走服务端 `q` 查询，不把全量数据载入前端。

### 4.2 可靠性

**US-NFR-05 崩溃恢复**

Given 一个 Run 处于 running，另有一个 Run 处于 queued  
When 应用进程被强制终止后重新启动  
Then queued Run 重新入队；running Run 在 2 秒内被标记为 failed，errorCode=interrupted/app_restart，已写入的事件完整保留，用户可一键重试。

**US-NFR-06 迁移失败**

Given 本地数据库版本为上一发布版本  
When 新版本首次启动并执行迁移  
Then 系统先创建可恢复备份；若迁移失败，应用拒绝启动并展示备份路径与错误原因，原数据库保持可打开状态。

**US-NFR-07 取消竞态**

Given 一个 Run 处于 queued 或 running  
When 用户点击取消  
Then 取消幂等；queued Run 从队列移除且永不执行；running Run 先优雅终止、宽限期后强制终止进程树；终态不被后续回写覆盖。

### 4.3 可访问性

**US-NFR-08 纯键盘操作**

Given 用户只能使用键盘和屏幕阅读器  
When 用户创建任务、移动到 in_progress、启动 Run、取消 Run 并打开评审面板  
Then 所有操作均可完成，焦点始终可见，模态框打开后焦点被限制在框内，关闭后回到触发按钮。

### 4.4 国际化（M2）

**US-NFR-09 语言切换**

Given 当前界面语言为中文  
When 用户在设置中切换为 English  
Then 所有产品文案、状态标签、日期与数字格式在 1 秒内切换，页面语言属性同步更新，已打开的表单内容不丢失。

### 4.5 分发与升级

**US-NFR-10 安全更新**

Given 用户已安装签名版本并开启自动更新检查  
When 发布新版本  
Then 客户端从 HTTPS 获取签名清单，校验签名与校验和后原子替换，失败时保留旧版本并可回滚；升级前自动备份数据库。

### 4.6 离线与成本

**US-NFR-11 模型不可用**

Given 本机网络断开或模型供应商返回错误  
When 用户启动一个使用真实 Runtime 的 Run  
Then Run 在合理时间内失败并显示错误分类（网络不可达、认证失败、限流、供应商错误），本地任务数据不受影响，用户可显式重试（创建新 Run，不自动重放原 Run）。

**US-NFR-12 预算控制（M3）**

Given 团队为某 Agent 设置了月度预算或并发配额  
When 用量达到 80% 和 100%  
Then 分别产生提醒和阻止新 Run 的行为；覆盖操作需要填写理由并写入审计。

### 4.7 阻塞、空状态与审批

**US-NFR-13 依赖阻塞（M2）**

Given 下游任务依赖的上游交付物尚未冻结  
When 用户尝试启动下游 Run  
Then 系统拒绝启动并展示缺失的依赖与上游状态；上游契约冻结后自动解除阻塞，用户无需手工修改任务。

**US-NFR-14 空状态**

Given 用户首次启动，没有任何 Task、Agent 或 Run  
When 用户打开 Board、Agents 或 Runs 页面  
Then 每个页面显示各自的空状态标题、解释与一个主入口；若因筛选导致无结果，文案必须区别于「尚无数据」；读屏可识别。

**US-NFR-15 审批超时（M2）**

Given 一个高风险动作已提交审批  
When 审批在配置时限内未处理  
Then 审批自动过期并默认拒绝，通知请求者；不得默认通过，不得自动执行动作。

## 6. 功能需求

说明：以下需求表描述目标状态。标记为「已实现（M0，需回归）」的行是当前已具备的能力，后续里程碑不得回退；其余均为计划需求，不得提前宣称已实现。优先级 P0 为发布阻断，P1 为发布应满足，P2 为优化项。

### 6.1 性能

性能目标围绕四条用户可感知路径：启动、看板浏览、Run 启动、日志消费。ATeam 的性能问题通常不是单次计算慢，而是「事件扇出加全量刷新」造成的放大效应，因此本节的验收同时约束服务端与前端。多 Agent 场景下还必须约束调度开销和 WebSocket 扇出，避免一个话多的 Run 拖垮整个驾驶舱。

#### 6.1.1 大列表数据加载策略

1. 服务端游标分页是唯一默认通道：默认 `limit=50`、最大 200，排序稳定，游标不可跳项或重复。
2. 看板按列或按筛选条件分页加载，并配合虚拟化；不得以「先把 5,000 条拉下来再前端筛选」实现搜索。
3. 客户端搜索与筛选只作用于已加载窗口（≤500 行）；输入超过 500 行的数据集时必须切换到服务端 `q` 查询。
4. NFR-PERF-004、NFR-PERF-016、NFR-RES-011 的测试口径统一为「数据库有 N 条，单页 limit=50 或 200」，不得用单页全量响应构造测试。
5. 全量导出（迁移、诊断、证据归档）走独立的后台任务与流式响应，不占用看板交互预算。

### 6.2 可靠性

可靠性是本地优先产品的生命线。ATeam 必须假设进程会被强杀、系统会断电、Runtime 会挂起、数据库会被另一个进程占用。可靠性需求的核心是：已提交的数据不丢、未完成的 Run 不装死、失败后的处理可解释、重复操作不产生重复副作用。M0 已有 WAL、迁移记录、超时与取消，但取消存在已知竞态，且缺少启动恢复、幂等和迁移备份，这些是 M1 的阻断项。

| 编号 | 需求 | 验收方法 | 优先级 | 状态 |
|---|---|---|---|---|
| NFR-REL-001 | 已提交的 API 写入在进程崩溃后不丢失；系统断电最多丢失最近 1 秒内的日志事件，数据库不得损坏。M1 必须明确 SQLite 耐久策略：WAL + `synchronous=FULL`，或经 kill -9/断电测试证明等价的 `NORMAL` + checkpoint 策略 | kill -9 循环测试、断电模拟、启动后完整性检查 | P0 | 计划（M1） |
| NFR-REL-002 | 启动时扫描非终态 Run：queued 重新入队（队列已持久化时）或明确标记失败；preparing、running 标记为 failed，错误码 `interrupted/app_restart`，保留事件并写入结束时间；1,000 个遗留 Run 的恢复不超过 2 秒。不新增 `interrupted` 状态，统一由 errorCode 表达 | 构造遗留数据后启动，核对状态、错误码与事件 | P0 | 计划（M1） |
| NFR-REL-003 | 排队中的 Run 必须持久化；重启后要么恢复执行，要么明确标记失败，不得静默消失 | 入队后杀进程，重启核对 | P0 | 计划（M1） |
| NFR-REL-004 | 仅对 `POST /runs`、`POST /runs/{id}/retry`、`POST /approvals/{id}/decision` 支持 Idempotency-Key；同一键在 24 小时内返回同一响应并带 `Idempotency-Replayed: true`；键相同但请求哈希不同返回 409 `IDEMPOTENCY_CONFLICT`。Task 与 Agent 创建不使用幂等键，依靠唯一约束与前端防重复提交 | 重复请求与并发请求测试（以 `api-and-data.md` §6.6 为准） | P1 | 计划（M1） |

### 6.3 可移植性

### 6.6 国际化

国际化不仅是翻译，还包括文案组织、日期时间、数字与复数、布局伸缩、错误码与本地化边界。ATeam 面向中文与英文用户。M1 只做与国际化相关的最小正确性（稳定错误码、UTC 存储、用户内容不翻译、字体回退），语言切换与资源文件基础设施放在 M2，与 M2 里程碑保持一致；全量覆盖在 M2 完成，M3 团队页面继承，M4 补安装器与关于页。产品内容（用户输入、代码、日志、模型输出）不做自动翻译；只翻译产品自身文案。`01-scope-and-roadmap.md` 的待确认第 12 条指出国际化策略未定，因此 M1 不设 i18n 发布门禁；默认语言、回退语言与文案归属必须在 M2 启动前决策。

### 6.10 成本与用量

## 7. 交互与规则

### 7.1 加载、反馈与错误呈现

1. 操作在 100 毫秒内完成的，不显示 loading 指示，避免闪烁。
2. 超过 300 毫秒的加载显示骨架屏或局部进度；超过 5 秒显示阶段说明与取消入口。
3. 所有错误必须包含：用户能理解的原因、稳定错误码、下一步动作；不得只显示原始异常文本。
4. 破坏性操作使用确认对话框；确认按钮文案说明后果，不使用含糊的「确定」。
5. 表单提交期间禁用重复提交；`POST /runs`、`POST /runs/{id}/retry` 与审批决策接口使用 Idempotency-Key，前端在重试时复用同一个键；Task 与 Agent 创建依靠唯一约束和前端防重复，不使用幂等键。
6. 长任务必须可取消；取消后 UI 立即进入取消中状态，最终以服务端确认的终态为准，不得由前端先行宣告 cancelled。
7. 网络或服务不可用时显示全局横幅，并保留离线可用的本地能力；横幅不得遮挡主要操作。
8. 审批等待中的动作显示明确状态与到期时间，不显示为「处理中」或「已完成」。

### 7.2 性能降级策略

1. 日志洪峰时，前端按时间窗口合并渲染，DOM 中只保留最新 N 条，历史通过分页或虚拟化查看；不得让 DOM 节点无限增长。
2. WebSocket 事件密集时，前端对列表刷新做 250 毫秒去抖合并；优先增量更新，必要时才全量重拉。
3. 数据库写入繁忙时，事件先进入内存队列并按批落盘；队列达到上限时对 Run 施加背压，暂停读取 Runtime 输出而不是丢弃事件。
4. WebSocket 不可用时降级为 3 秒轮询，并在界面标明「实时连接已断开」。
5. 前端内存超过阈值时释放非当前页面的缓存数据，但不得丢失未提交表单。
6. 大列表默认使用服务端游标分页（默认 50、最大 200）并按需加载；超过 500 行必须启用虚拟化；超过 5,000 行必须要求筛选或分页，不得全量载入前端。
7. 单 Run 事件达到 20,000 条或 50 MB 时，停止写入正文并追加 `EVENTS_TRUNCATED` 告警；UI 必须显示「事件已截断」，不得表现为「仍在实时输出」。

### 7.3 错误分类与用户文案规则

Run 失败原因以 `api-and-data.md` 的 errorCode 目录为唯一来源；HTTP 错误以同一文档的错误信封与状态码目录为唯一来源。本表只描述用户可见分类与重试边界，不引入新码。

| 用户可见类别 | errorCode | 用户可见文案要点 | ATeam 是否自动重试 |
|---|---|---|---|
| Runtime 缺失 | runtime_error/runtime_missing | 说明未找到 CLI 并给出配置路径入口 | 否 |
| Runtime 非零退出 | runtime_error/nonzero_exit | 显示退出码与日志位置 | 否 |
| 超时 | timeout/timeout | 说明超时阈值与调整入口 | 否 |
| 取消 | cancelled_by_user/user_cancel | 说明由谁取消 | 否 |
| 服务重启中断 | interrupted/app_restart | 说明应用异常退出，可显式重试 | 否 |
| 队列拒绝 | internal_error/queue_rejected（HTTP 503 QUEUE_FULL） | 说明并发上限与排队情况 | 是（Retry-After） |
| 工作区准备失败 | workspace_error/workspace_provision_failed | 指向 git/worktree 诊断信息 | 否 |
| 权限越界 | permission_denied/path_denied 或 command_denied | 指出被拒绝的路径或命令，引用 Run 时间线证据 | 否 |
| 证据写入失败 | internal_error/artifact_write_failed | 说明证据缺失原因与磁盘状态 | 否 |
| 内部错误 | internal_error/scheduler_internal | 显示 requestId 与诊断包入口 | 否 |

网络不可达、认证失败、限流与供应商错误不作为独立持久化码，而是 Runtime 输出与事件载荷上的 UI 分类；其重试由 Runtime CLI 内部负责，ATeam 不重放整个 Run。HTTP 层的 `TASK_NOT_EXECUTABLE`、`REVIEW_REQUIRED`、`APPROVAL_REQUIRED`、`IDEMPOTENCY_CONFLICT`、`INVALID_LIMIT`、`QUEUE_FULL` 等语义参见 `api-and-data.md` §7.3；其中 `QUEUE_FULL` 仅作为 HTTP 503 语义，Run 自身的入队失败使用 `internal_error/queue_rejected`。

### 7.4 时间、日期与本地化规则

1. 数据库统一存储 UTC 毫秒时间戳；API 返回 ISO 8601 字符串并带时区信息。
2. 界面按用户系统时区显示；设置页展示当前时区，允许手动覆盖，覆盖值持久化（M2 起）。
3. 相对时间用于 7 天内的记录，超过 7 天显示绝对日期；悬停显示完整时间与秒。
4. 时间线、日志与导出必须保留毫秒精度；展示层可按场景省略。
5. 日期格式不由前端手工拼接，统一使用 Intl.DateTimeFormat；英文使用 12 小时或 24 小时遵循用户区域设置。
6. 所有定时与调度以本地时区解释用户输入，以 UTC 存储执行时间；夏令时切换需有测试样例。

### 7.5 数据保留与清理

1. Task、Agent、评审与审批记录默认保留到用户显式删除；归档（软删除）从 M1 起为确认 + 归档，M2.1 起默认保留 30 天恢复窗口。
2. RunEvent 采用两段式上限：单 Run 最多保留 20,000 条或 50 MB（先到者为准），达到上限后停止写入正文并追加 `EVENTS_TRUNCATED` 告警；Run 结束后保留 90 天（可配置 30–365 天）。全局 WebSocket 重放缓冲保留 7 天或 100,000 条，后台定期清理最旧记录，清理后旧 afterSeq 触发重放重置；`domain_events` 领域事件日志保留 90 天。该口径与 `api-and-data.md` §9.5 和 `security-and-permissions.md` §5.5 的同一张表一致。
3. 审计记录：本地审计默认保留 90 天；M3 团队 `audit_events` 按团队策略保留，默认 180 天并可配置（90 天–3 年），只归档不物理删除。
4. 日志保留按 NFR-OBS-002 执行：单文件 10 MB、最多 10 份、总上限 100 MB、最多 7 天；崩溃日志单独保留 30 天。
5. Workspace 本身保留到用户删除；Run Workspace（worktree）在已合并或放弃后默认保留 30 天，Artifact 与 Evidence 保留 90 天；删除前必须提示未合并变更与证据；未合并且有改动的 worktree 不得自动删除。
6. 诊断包由用户手动生成与导出，默认保留在临时目录并在应用退出时清理。
7. 删除操作可恢复的实现优先放入回收站；不可恢复的删除必须二次确认并记录审计。

### 7.6 更新与升级交互

1. 默认仅检查更新，不自动下载；用户开启自动更新后才自动下载与安装。
2. 存在活跃 Run 时不得自动重启应用；提示用户等待或手动安排。
3. 更新安装前自动备份数据库；更新失败时展示旧版本继续使用与查看日志两个选项。
4. 跨大版本升级展示变更摘要与不兼容说明；数据库降级直接拒绝并给出恢复建议。
5. 更新检查失败不打断使用，只在设置页显示最近一次检查结果。

### 7.7 审批与高风险动作交互

1. M1 起，合并必须由人在评审界面显式确认；确认框展示目标分支、源分支、base/head commit、diff 统计、证据清单、评审结论与风险提示；服务端校验 reviewId、证据完整性、expectedHeadCommit 与目标工作区状态。合并是 M1 的发布门禁，不得推迟到 M2。
2. M2 起，推送、staging 部署、删除 Workspace、批量删除 Task 与越权命令进入通用审批面板；面板展示对象、证据、影响范围与回滚方案。目标分支、SHA 或环境变化后审批失效。
3. 审批人必须是人类；Agent、Runtime 与 Crew 不能自我审批。M1 的合并确认与 M2 的通用审批门都要求显式确认；M3 支持角色化审批与双人审批。
4. DevOps Agent 在 M2 经人工审批后可执行 staging 部署与冒烟测试；prod 只允许生成部署计划与回滚方案，必须由人在 ATeam 之外执行，ATeam 记录结果与证据。产品不得提供 Agent 直接执行 prod 的开关。
5. 审批拒绝需要原因；拒绝记录与批准记录同等审计。
6. 审批超时可配置，超时后默认拒绝并通知请求者，不得默认通过；过期审批不可复用。

### 7.8 空状态与阻塞交互

1. Board、Agents、Runs、Inbox 与日志区域各自定义空状态：标题、解释与一个主入口；不得共用一段泛化文案。
2. 必须区分「尚无数据」与「筛选/搜索无结果」；后者提供清除筛选入口。
3. 空状态不得残留骨架屏、加载动画或旧数据。
4. 任务依赖未满足时（M2），任务显示 blocked 与阻塞原因、上游任务与缺失交付物；禁止启动 Run，提供跳转到上游的入口。
5. 阻塞解除后任务自动恢复可执行状态，不需要用户手工改状态；状态变化写入时间线。

### 8.2 API 非功能契约

以下只列非功能约束；端点、字段与错误码目录以 `api-and-data.md` 为准。本章的端点一律使用版本化路径思路，具体路径由 API 模块确定。

3. 旧 `/api` 与 `/api/v1` 的兼容窗口按 `api-and-data.md` 执行，本章不另行定义。
4. 任何新增端点（包括诊断与时间线相关端点）必须先进入 `api-and-data.md` 的端点表，再进入实现；本章不维护第二套端点清单。

## 9. 异常与边界

| 场景 | 触发条件 | 期望行为 | 里程碑 |
|---|---|---|---|
| 端口被占用 | 8787 已被其他进程监听 | 服务模式启动失败并提示更换端口；桌面端使用随机端口不受影响 | M0 已具备（服务模式报错） |
| 非回环监听 | 用户用 `--addr 0.0.0.0` 启动 | 未提供 `--allow-remote` 时启动失败并说明原因；提供后必须启用认证并显示常驻红色横幅 | M1 |
| 数据库被占用 | 另一个进程持有锁 | busy_timeout 5 秒内重试；超时后返回可读错误，不损坏数据 | M0 已具备（需验证） |
| 磁盘写满 | 事件或日志写入失败 | 暂停新 Run 启动，保留内存事件并提示清理；不得静默丢数据 | M1 |
| 数据库损坏 | 文件截断或磁盘错误 | quick_check 失败后拒绝写入，展示备份与诊断入口 | M2 |
| 迁移失败 | SQL 执行错误或磁盘不足 | 事务回滚，保留迁移前备份，拒绝启动并给出回滚指引 | M1 |
| 迁移降级 | 数据库版本高于应用 | 拒绝启动，提示安装更新版本或恢复备份 | M4 |
| Runtime 缺失 | PATH 中找不到 CLI | Run 失败，错误码 runtime_error/runtime_missing，给出配置入口 | M1 |
| Runtime 卡死 | 进程无输出且不退出 | 超时后先优雅终止、10 秒宽限后终止进程树，错误码 timeout/timeout | M1 |
| Runtime 输出超长行 | 单行超过 1 MB | 截断并标记，保留前后片段；不得阻塞扫描 | M1 |
| 非法 UTF-8 | Runtime 输出非 UTF-8 | 以替换字符展示并记录告警；不得导致解析崩溃 | M1 |
| 事件洪峰 | 每秒超过 500 条 | 背压 Runtime，批量写入，UI 合并渲染；单 Run 超上限时标记 EVENTS_TRUNCATED | M2 |
| 队列溢出 | 排队 Run 超过容量 | 返回 503 QUEUE_FULL，不静默丢弃 | M1 |
| 重复提交 | 用户双击或网络重试 | 幂等键返回同一响应；Task/Agent 创建由唯一约束拒绝重复 | M1 |
| 应用被强杀 | 进程收到 SIGKILL | 重启后 queued 重新入队，preparing/running 标记 interrupted/app_restart，保留事件 | M1 |
| 排队取消竞态 | 取消 queued Run 后 worker 又取到 | 调度器领取时检查终态并跳过，Run 永不执行 | M1 |
| 运行中取消竞态 | API 先写 cancelled，adapter 后写 failed | 调度器确认停止后再写终态；终态不被覆盖 | M1 |
| 系统睡眠唤醒 | 长时间挂起后恢复 | 重新校验在途 Run 与 Runtime 进程，无法确认则标记中断 | M2 |
| WebSocket 断开 | 网络切换或服务重启 | 指数退避重连，恢复后按 afterSeq 补拉事件 | M1 |
| 时钟漂移 | 系统时间被调整 | 使用单调计时计算超时；显示层提示时间异常 | M2 |
| 时区变更 | 用户跨时区 | 展示随系统时区更新；存储仍为 UTC | M2（展示）；M0（存储） |
| 依赖阻塞 | 下游任务依赖未满足（M2） | 任务 blocked，禁止启动 Run，显示上游与缺失交付物；依赖满足后自动解除 | M2 |
| 等待审批 | 高风险动作已提交、尚未决策（M2） | 动作保持待执行，显示审批人与到期时间；不得自动执行 | M2 |
| 审批超时 | 审批超过配置时限（M2） | 默认拒绝并通知请求者，记录审计；不得默认通过 | M2 |
| 空状态 | 无 Task、Agent、Run 或搜索无结果 | 区分「尚无数据」与「筛选无结果」，提供主入口与读屏文案；不残留骨架屏 | M1（Inbox M2） |
| 屏幕阅读器 | 使用辅助技术 | 核心流程可完成，动态状态播报节流 | M2 |
| 更新签名无效 | 清单或包被篡改 | 拒绝安装，保留旧版本，记录安全事件 | M4 |
| 更新中断 | 下载或替换过程中断电 | 下次启动回滚到上一可用版本 | M4 |
| 低对比显示器 | 用户使用低质量显示器 | 核心文本仍满足 4.5:1；主题选择不在本章承诺，见「待确认/未文档化」 | M2 |

## 10. 权限与安全

### 10.1 本地 API 暴露面

ATeam 的本地服务是本机应用的一部分，不是公开 Web 服务。M0 默认监听回环地址是正确的，但 CORS 反射任意 Origin、WebSocket 接受任意 Origin、且没有认证，这意味着用户浏览器中任意网页都可能尝试调用本地 API；同时 `--addr` 可以无守卫地绑定到 0.0.0.0。M1 必须完成：CORS 允许列表、Host 头校验、WebSocket Origin 校验、本地会话令牌、非回环启动守卫与红色风险横幅。M3 支持远程 Runner 或团队服务时，必须使用独立机器凭据与 TLS。

### 10.2 凭据与数据保护

1. ATeam 自身不保存模型密钥；Runtime 使用本机 CLI 的认证。
2. 未来若支持直接 API Key，必须存入系统密钥链（M2 起），不得进入 SQLite、配置文件、日志或诊断包。
3. 数据目录权限 0700，数据库、日志与备份 0600；启动时检测并修正过宽权限。
4. 诊断包生成前执行脱敏：移除密钥、令牌、Cookie、绝对用户路径中的用户名与提示词内容。
5. 导出功能可能包含代码与 diff，必须由用户显式发起并提示敏感性；不得自动上传。

### 10.3 高风险动作与审批

合并、推送、部署、删除 Workspace、批量删除 Task 属于高风险动作，必须满足：

1. 有人工审批门，Agent、Runtime 与 Crew 不能自我批准。
2. 审批界面展示目标、变更摘要、证据、影响范围与回滚方案；审批绑定目标分支、SHA 或环境，目标变化后审批失效。
3. 审批结果写入审计日志，包含操作者、时间、理由与结果。
4. 合并的门禁在 M1 生效：人类评审记录 + 显式确认 + expectedHeadCommit 绑定。M2 起通用 Approval Gate 覆盖推送、staging 部署、删除与越权命令。
5. DevOps Agent 在 M2 经审批后只能执行 staging 部署与冒烟测试；prod 只生成部署计划与回滚方案，由人在 ATeam 之外执行，ATeam 记录结果与证据。
6. 自动化任务（M4）不得绕过审批；定时或 Webhook 触发的 Run 仍按同一审批策略执行。

### 10.4 供应链与分发安全

1. 依赖锁定版本，CI 执行漏洞与许可扫描；新增依赖需要说明用途与维护状态。
2. 发布产物签名，更新清单签名；签名密钥存放于受控 CI 密钥库，并有轮换与撤销流程。
3. 构建环境尽量可复现；发布记录包含提交号、构建时间、依赖清单与 SBOM。
4. 产品为原创实现，不引入第三方产品的代码、文档、UI 资产、图标或品牌；NOTICE 与 LICENSE 保持完整。

### 10.5 隐私

1. 默认不收集遥测、崩溃报告、提示词、代码、diff 或使用明细。
2. 遥测必须显式开启，内容最小化、端点公开、可随时关闭，并在隐私说明中列出字段。
3. 本地日志可能包含任务标题与路径，用户导出日志或诊断包时应看到内容预览与脱敏说明。
4. 团队模式（M3）的审计与用量数据归团队所有；跨组织不得共享。
5. 卸载与删除数据时明确告知不可恢复范围；备份文件同样纳入删除选项。

## 12. 验收标准

### 12.1 通用验收方法

1. 使用第 1.3 节的基准环境与数据集；release 构建；每项至少 3 轮，报告 p50 与 p95。
2. 性能与资源类需求必须提供可重复脚本或基准命令，结果归档到发布记录。
3. 可靠性类需求必须提供故障注入脚本：kill -9、磁盘满、数据库损坏、迁移失败、Runtime 卡死、队列溢出、取消竞态。
4. 可访问性类需求必须提供键盘走查清单与屏幕阅读器测试记录。
5. 国际化类需求必须提供中英截图与伪本地化截图，检查布局溢出。
6. 安全类需求必须提供跨源请求、Host 伪造、非回环拒绝、路径越权、命令越权的测试用例。
7. 打包类需求必须在干净虚拟机或全新用户账户下安装、升级、回滚、卸载。
8. 任何未达标项不得以「后续优化」关闭；必须降级为已知问题并记录影响与豁免期限。
9. 每个门禁项必须来自 01-scope 退出标准、对应里程碑文档或本章 NFR 条目之一；不得在门禁中临时新增未登记的要求。

## 与其他文档的关系

本章是整个 PRD 的横切约束层，与以下内容存在直接依赖：

1. 与 `task-management.md`、`agent-system.md` 的关系：功能模块定义对象、状态机与交互；本章约束它们的性能、可靠性、资源与异常行为。功能文档中的验收标准应引用本章 NFR 编号，避免重复定义两套口径。
2. 与 `runtime-and-workspace.md` 的关系：worktree 准备时间、取消宽限期（10 秒）、事件大小（单条 64 KiB）、证据体积（50 MiB）由该模块定义；本章引用这些口径，不重复数值。
3. 与 `collaboration-and-review.md` 的关系：合并门（M1）与 staging/prod 部署门（M2）、交付物契约与证据化 DoD 由该模块定义；本章约束其审计、可访问性与审批超时行为。
4. 与 `security-and-permissions.md` 的关系：认证、令牌、密钥链、权限信封、审计与远程信任的里程碑以该模块为准（M2.1 本地令牌与本地审计；M2 钥匙链与通用审批门；M3 团队审计）；本章只引用 SEC-* 条目并补充非功能验收。
5. 与 `api-and-data.md` 的关系：数据库 schema、端点、分页默认值（50/200）、错误码目录、health 字段、事件类型与保留策略以该模块为准；本章只保留索引、保留期、延迟、体积等非功能约束并显式引用。
6. 与 `ui-ux.md` 的关系：页面结构、空状态（UI-080）、可访问性基线（UI-108/UI-112）与交互细节由该模块定义；本章规定质量门槛，二者不得冲突。
7. 与里程碑文档的关系：`milestones/M0-scaffold.md`、`milestones/M1-local-loop.md`、`milestones/M2-role-agents.md`、`milestones/M3-team-mode.md`、`milestones/M4-automation-and-packaging.md` 定义目标、范围、交付物与退出标准；本章第 12 节只对齐这些退出标准中的非功能项。里程碑中的旧 NFR 编号按第 1.5 节映射。
8. 与 `04-acceptance-and-test-plan.md`、发布检查单与运维手册的关系：本章第 12 节是测试与发布门禁的来源；第 8 至 10 节是诊断、备份恢复与安全审查的输入；测试计划必须登记第 1.5 节的编号映射。
