# 里程碑 M2.4：Agent 状态看板与工作台

## 本章导读

本章定义 ATeam M2.4 里程碑「Agent 状态看板与工作台」的目标、范围、用户故事、交付物、验收标准、演示脚本与退出标准。M2.4 的核心命题不是「再加一个列表页」，而是让用户在看板上直接判断每个 Agent **现在是否在工作、刚完成了什么**，并从工作中或已完成的 Agent 一步进入其**工作上下文与完成任务的过程**。

模块细节以 `prd/modules/agent-system.md` §4.6、§10.8、`prd/modules/ui-ux.md` §5.5.1、`prd/modules/api-and-data.md` §5.16 为准。本章只定义里程碑级范围、验收与交付节奏。

**状态声明。** 当前仓库已完成 M1（Workspace、worktree、真实 Claude Code adapter、Artifact、评审、合并、DoD），但 Agent 只有生命周期状态 `active/archived`，没有工作状态、没有 Agent 工作页、没有 Run 快照查询端点。M2.4 是计划，不是现状。

**与 M2.3 的关系。** M2.4 与 M2.3（Agent Team 与会话）相互独立：M2.3 是讨论层，M2.4 是执行状态的观察层。M2.4 可在 M1 完成后立即交付，不依赖 M2.1 的 DAG、M2.2 的 Crew 或 M2.3 的会话。

## 1. 里程碑目标

### 1.1 为什么需要 M2.4

M1 的 Run 详情页是「一次执行」的视角，用户要判断「Frontend Agent 现在忙不忙、上一个任务做到哪一步」，必须逐个打开 Run 列表或 Task 详情。Agent 越多，这种观察成本越高：

- 看板上的 Agent 卡片只显示配置，不显示是否正在工作；
- 用户无法从 Agent 进入其最近工作，必须在 Run 列表按 Agent 过滤；
- Run 详情展示事件，但缺少「Agent 视角」的上下文汇总（Task、配置快照、Workspace、权限）；
- 已完成与失败的工作没有明确的结束态，用户容易误以为 Agent 仍在运行。

M2.4 用「派生工作状态 + Agent 工作页」解决上述问题，不引入新的执行实体或权限模型。

### 1.2 一句话目标

**让 Agent 看板显示空闲、工作中、已完成、失败待处理四种工作状态，并让用户从工作中或已完成的 Agent 进入工作页，查看其工作上下文与完成任务的过程。**

### 1.3 可验证结果

1. **状态可判定**：Agent 看板显示 `workStatus`，判定与 Run 列表一致；有活跃 Run 必为 `working`，无活跃 Run 不得为 `working`。
2. **状态可解释**：工作中显示当前任务与阶段；已完成显示完成时间与任务；失败显示失败分类；空闲显示明确空态。
3. **入口可直达**：点击工作中或已完成的 Agent 进入 `/agents/{id}/work`；编辑配置使用独立入口。
4. **上下文可查看**：工作页展示所选 Run 的 Task 上下文、Run 配置快照摘要、Workspace/base/head commit、权限模式与提示词哈希。
5. **过程可回放**：工作页展示结构化时间线（生命周期、工具、文件变更、测试、Artifact、评审/合并），可过滤并跳转 Run 详情。
6. **历史可追溯**：工作页列出该 Agent 最近 20 条 Run 及结果；归档 Agent 历史只读。
7. **脱敏可验证**：工作摘要与快照不返回明文密钥、凭据值或完整拼装 prompt。

### 1.4 成功口径

M2.4 的成功以第 12 章退出标准为准：一条「看板识别工作状态 → 点击进入工作页 → 查看上下文与过程 → 跳转 Run 详情」的演示可在本地完成，且状态与 Run 列表一致、脱敏负向用例通过。

## 2. 范围与非目标

### 2.1 范围内

| 能力 | 核心内容 | 详情文档 |
|---|---|---|
| 工作状态派生 | `idle`/`working`/`completed`/`failed`；24 小时窗口；归档覆盖 | `agent-system.md` §4.6、`02-domain-model.md` §4.10 |
| 看板状态展示 | 卡片状态、当前任务与阶段、完成时间、状态分组/筛选 | `ui-ux.md` §5.5、UI-153 |
| 工作页入口 | 点击卡片进入 `/agents/{id}/work`；编辑独立入口 | `ui-ux.md` §5.5.1、UI-154 |
| 当前工作 | 活跃 Run 阶段、任务、时长、工作区/分支、最近事件 | UI-155、UI-156 |
| 工作上下文 | Task 上下文、RunConfigSnapshot 摘要、Workspace/commit、权限与提示词哈希 | UI-157、`api-and-data.md` §5.16 |
| 完成过程 | 结构化时间线、过滤、跳转 Run 详情 | UI-158 |
| 历史工作 | 最近 20 条 Run、结果、用量、评审/合并 | UI-159 |
| 实时更新 | 使用既有 `run.*` 事件刷新状态与当前工作；`runId` 深链 | UI-160 |
| API | `GET /agents/{id}/work`、`GET /runs/{id}/snapshot` | `api-and-data.md` §5.16、API-1416～1425 |

### 2.2 不在 M2.4 的范围

- 新增 Agent 生命周期状态或改变 `active/archived` 语义；
- 在工作页内编辑 Agent、启动/取消 Run、审批或合并；
- 新增派生 WebSocket 事件（`agent.work_status_changed` 不进入 M2.4）；
- Agent 之间的比较、排行或自动调度；
- 跨 Workspace 的 Agent 工作聚合；
- M2.3 会话回合的工作状态（会话不是 Run，不进入 Agent 工作状态）；
- 长期工作分析、成本报表与团队视图（M3/M4）。

### 2.3 裁剪顺序

1. 看板状态分组与筛选（保留单卡片状态）；
2. 历史工作的用量与评审摘要（保留状态与任务）；
3. 时间线按类型过滤（保留完整时间线）；
4. 多活跃 Run 的标签页切换（保留列表）；
5. **不可裁剪**：状态派生与一致性、工作页入口、上下文脱敏、完成过程时间线、归档只读、空态。

## 3. 关键决策

| 编号 | 决策 | 理由 |
|---|---|---|
| DEC-M24-01 | 工作状态是服务端派生的只读状态，不写入 Agent 配置 | 避免客户端伪造与多端不一致 |
| DEC-M24-02 | 有活跃 Run 必为 `working`；无活跃 Run 不得为 `working` | 看板必须与 Run 列表一致 |
| DEC-M24-03 | 24 小时作为「已完成/失败」的展示窗口，超时回到 `idle` | 避免已完成状态永久停留在看板上；首版不提供配置 |
| DEC-M24-04 | 工作页是 Agent 视角的只读汇总，不是新的执行入口 | 保持 Run 详情为唯一执行操作入口 |
| DEC-M24-05 | 不新增派生 WebSocket 事件，复用既有 `run.*` 事件 | 避免派生事件与真实事件不一致 |
| DEC-M24-06 | 工作页展示配置快照（含脱敏后的 instructions）与提示词哈希，不展示完整拼装 prompt 与明文凭据 | 保留可追溯性与工作上下文，同时避免工作页成为泄漏面 |

## 4. 当前实现基线与差距

### 4.1 已具备

- Agent CRUD、卡片网格与基础编辑入口；
- Run 列表支持 `agentId` 过滤，Run 详情包含事件、Artifact、评审与 Workspace 摘要；
- `run_config_snapshots` 表在 M1 创建，Run 创建时写入，不可补写；
- 事件 Hub 广播 `run.*` 生命周期事件；
- Task 详情与 Run 详情已有结构化时间线基础。

### 4.2 M2.4 需要新建

- 服务端 `workStatus` 派生与 `GET /agents/{id}/work`；
- `GET /runs/{id}/snapshot` 与脱敏；
- Agent 看板状态展示、分组/筛选与点击入口；
- `/agents/{id}/work` 工作页与上下文/时间线/历史组件；
- 索引 `runs(agent_id, status, ended_at)`、`runs(agent_id, created_at)`；
- 负向测试：PATCH `workStatus`、状态与 Run 列表不一致、快照泄漏、归档工作页写操作。

## 5. 用户故事与验收标准

### US-M2.4-01 看板识别工作状态

作为用户，我打开 Agents 看板就能看到每个 Agent 是否在工作。

**验收**：存在 running Run 的 Agent 显示「工作中」与当前任务；刚完成的显示「已完成」与完成时间；无近期工作的显示「空闲」；归档显示「已归档」。

### US-M2.4-02 从工作中 Agent 进入工作页

作为用户，我点击正在工作的 Agent，看到它当前在做什么。

**验收**：点击卡片进入 `/agents/{id}/work`；页头显示工作状态与活跃 Run 数量；当前工作区显示阶段、任务、开始时间、工作区与分支、最近事件；可跳转 Run 详情。

### US-M2.4-03 从已完成 Agent 复盘过程

作为用户，我点击已完成的 Agent，查看它如何完成任务。

**验收**：默认选中最近完成的 Run；工作上下文显示 Task、配置快照、Workspace 与 commit；完成过程显示工具、文件变更、测试、Artifact、评审/合并时间线。

### US-M2.4-04 空闲与归档

作为用户，空闲 Agent 的工作页不伪造内容，归档 Agent 的历史只读。

**验收**：空闲 Agent 显示「尚无工作记录」；归档 Agent 显示只读标识，历史 Run 可查看，工作页无编辑/启动/取消失败入口。

### US-M2.4-05 状态与 Run 列表一致

作为用户，我不希望看板说 Agent 在工作中，但 Run 列表没有活跃 Run。

**验收**：并发创建/结束 Run 时，`GET /agents?include=workStatus`、`GET /agents/{id}/work` 与 `GET /agents/{id}/runs` 结果一致；自动化测试覆盖竞态。

## 7. 交互规则

1. 看板默认排序「工作中 → 已完成 → 失败 → 空闲」；归档默认不显示，可通过筛选查看。
2. 点击卡片正文进入工作页；卡片上的「编辑」按钮进入编辑器，两者不冲突。
3. 工作页默认选中：活跃 Run（多个时按 `startedAt` 最早）→ 最近 Run → 空态。
4. 切换 Run 使用 `?runId=`；刷新、复制链接与前进/后退保持选中。
5. 时间线默认正序；可切换倒序；过滤条件写入 URL。
6. 普通日志不进入工作页时间线；需要日志时跳转 Run 详情 Logs。
7. 工作页不提供写操作；取消 Run、评审、合并均在 Run 详情执行。
8. 状态刷新由既有 `run.*` 事件触发；事件丢失时重连后重新拉取摘要。

## 8. 数据与 API 影响

### 8.1 数据

- 不新增表；`workStatus` 为派生字段。
- 新增索引：`runs(agent_id, status, ended_at)`、`runs(agent_id, created_at)`。
- `run_config_snapshots` 已在 M1 存在；M2.4 只新增读取端点与脱敏，不改变写入语义。

### 8.2 API

`GET /api/v1/agents/{id}/work`、`GET /api/v1/runs/{id}/snapshot`；同时挂在 `/api` 别名下。

### 8.3 事件

不新增事件；客户端消费 `run.queued/preparing/running/completed/failed/cancelled/timeout`。

## 9. 异常与边界

| 场景 | 行为 |
|---|---|
| Agent 不存在 | 404 `AGENT_NOT_FOUND` |
| Run 不存在 | 404 `RUN_NOT_FOUND` |
| 快照缺失 | 404 `RUN_SNAPSHOT_NOT_FOUND`；工作页显示「历史 Run 无完整快照」 |
| 归档 Agent | 工作状态显示「已归档」，历史只读 |
| 空闲 Agent | 空活跃 Run、空 lastRun、空 recentRuns；工作页空态 |
| 多活跃 Run | 显示数量与列表；状态保持 working |
| 状态竞态 | 以服务端查询为准；重连后重新拉取 |
| 快照含敏感字段 | 服务端脱敏；负向测试失败即阻断发布 |

## 10. 权限与安全

- 工作摘要与快照沿用 M1 的本地信任边界与 `SEC-071` 脱敏规则；
- 快照不返回完整拼装 prompt、明文密钥、凭据值与环境变量值；instructions 允许返回但须脱敏；`credentialRefs` 只返回引用 ID；
- 工作页只读，不提供编辑、启动、取消、审批或合并；
- 归档 Agent 的工作页保留历史，不提供新 Run 入口；
- 工作页的 Task 描述与事件内容按不可信文本渲染，禁止原始 HTML。

## 11. 指标

- 看板状态与 Run 列表一致率 100%（自动化检查）；
- `GET /agents/{id}/work` p95 ≤ 200 毫秒（10 万条 Run）；
- 工作页首屏可交互 ≤ 1.5 秒（最近 20 条 Run）；
- 状态事件到看板更新 p95 ≤ 2 秒；
- 快照脱敏负向用例通过率 100%。

## 13. 依赖、风险与假设

### 13.1 依赖

- M1 的 Run、事件、Artifact、评审与 `run_config_snapshots`；
- 既有 Agent CRUD 与卡片网格；
- 不依赖 M2.1 DAG、M2.2 Crew 或 M2.3 会话。

### 13.2 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 状态与 Run 列表不一致 | 用户不信任看板 | 服务端唯一派生、自动化一致性测试、并发竞态测试 |
| 24 小时窗口不符合预期 | 已完成状态过早消失 | 首版固定窗口并收集反馈；列入开放问题 |
| 工作页暴露敏感上下文 | 凭据或提示词泄漏 | 快照脱敏、字段白名单、负向测试 |
| 历史 Run 无快照 | 上下文缺失 | `legacy=true` 明确标注，不伪造 |
| 10 万条 Run 查询变慢 | 工作页卡顿 | 复合索引、20 条上限、p95 验收 |

### 13.3 假设

- 用户需要在看板层面区分 Agent 的工作状态；
- 24 小时足以覆盖「刚完成」的查看需求；
- Agent 工作页不需要承载写操作。

## 14. 演示脚本

1. 创建 Agent A（mock）与 Agent B（claude），启动 A 的一个 Run；
2. 打开 Agents 看板，确认 A 显示「工作中」、B 显示「空闲」；
3. 点击 A 进入工作页，确认当前任务、阶段、Workspace 与最近事件；
4. 等待 Run 完成，返回看板，确认 A 显示「已完成」与完成时间；
5. 点击 A 再次进入工作页，确认默认选中刚完成的 Run，展示 Task 上下文、配置快照摘要与完成过程时间线；
6. 点击时间线中的 Run 链接进入 Run 详情，再返回工作页确认 `runId` 保持；
7. 负向：PATCH Agent 携带 `workStatus` 返回 400；`GET /runs/{id}/snapshot` 响应不含明文密钥与完整拼装 prompt；空闲 Agent 工作页显示空态；归档 Agent 工作页只读。

**失败判定**：看板状态与 Run 列表不一致、工作页无法进入、上下文缺少关键字段、时间线混入普通日志、快照泄漏敏感信息、空态显示伪造数据，任一发生即 M2.4 不通过。
