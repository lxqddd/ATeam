# 里程碑 M2.3：Agent Team 与会话

## 本章导读

本章定义 ATeam M2.3 里程碑「Agent Team 与会话」的目标、范围、用户故事、交付物、验收标准、演示脚本、依赖、风险与退出标准。M2.3 的核心命题不是「给 Agent 增加一个聊天窗口」，而是在既有 Task → Run → 证据 → 评审 → 合并链路之前，增加一个**人类发起、可路由、可追溯、可一键转任务**的讨论层。

模块细节以 `prd/modules/agent-teams-and-conversations.md` 为权威事实源，本章只定义里程碑级范围、验收与交付节奏。API、事件、错误码与表的字段级契约以 `prd/modules/api-and-data.md` §5.15、§6.3、§7.3、§9.3 为准。

**状态声明。** M2.3 的 Slice 1–3 已实现：Agent Team 与成员管理、Conversation 与不可变消息、`@` 与规则路由、只读会话回复（流式事件与取消）、一键转任务与来源追溯，以及基础 Teams UI。LLM 路由（`router_llm`）、消息 32 KiB 截断的富文本展示与完整事件 replay 仍待后续切片。

**硬约束。** 会话中的 Agent 只能进行只读讨论：不得写仓库、不得创建 Run/Artifact、不得修改 Task 状态；Agent 与 Agent 不得互相自动对话；路由只处理用户消息；讨论结果必须通过「一键转任务」进入执行链路，不得从会话直接触发合并、推送或部署。

## 1. 里程碑目标

### 1.1 为什么需要 M2.3

M1 的闭环假设「用户已经知道要做什么，并把它写成了任务」。真实使用中，用户在创建任务之前需要先与不同角色的 Agent 澄清需求、比较方案、确认边界；在 M2 的角色 Agent 就绪后，这种讨论天然是**小组式**的：前端问题应该由 Frontend Agent 回答，部署问题应该由 DevOps Agent 回答，而不需要用户手工切换 Agent。缺少讨论层会导致：

- 用户把同一个问题分别发给多个 Agent，上下文重复、结论分散；
- Agent 对需求的理解无法沉淀，创建任务时又要重新描述；
- 多角色协作只能从 Task DAG 开始，而 DAG 之前的探索没有记录；
- 用户无法判断「这条建议来自哪个角色、依据是什么」。

M2.3 用「Agent 小组 + 可解释路由 + 一键转任务」解决上述问题，同时保持 M2 的显式协作边界不被破坏。

### 1.2 一句话目标

**让用户把多个角色 Agent 组成一个小组，在小组会话中通过自动路由或 `@` 定向与合适的 Agent 讨论需求，并将讨论结果一键转为可执行、可追溯的 Task。**

### 1.3 可验证结果

1. **小组可组建**：创建 Agent Team，增删成员；成员必须属于同一 Workspace 且非归档；一个 Agent 可属于多个小组。
2. **会话可讨论**：创建会话并发送消息；消息不可变、顺序稳定、可增量拉取；Agent 回复支持流式展示与停止。
3. **路由可解释**：每条用户消息产生唯一路由决策并持久化；Agent 回复旁展示「路由至 X · 依据」；歧义与无匹配返回稳定错误码与候选。
4. **@ 可覆盖**：用户可用 `@Agent` 跳过自动路由；非成员 `@` 被拒绝。
5. **执行有边界**：会话 Agent 以 `read_only` 权限运行，禁止写工具；不创建 Run/Artifact、不写仓库；Agent 消息不触发其他 Agent。
6. **转任务可追溯**：任意消息可一键转为 Task，幂等，回填 `origin_conversation_id`/`origin_message_id`，并在会话中回执；后续执行仍走 M1 链路。
7. **讨论可审计**：路由决策、成员变更、任务转换均可在会话中回看；归档会话只读。

### 1.4 成功口径

M2.3 的成功以第 14 章退出标准为准：一条「组建小组 → 发起会话 → 自动路由 → `@` 覆盖 → 一键转任务 → Run 执行」的演示可以在本地完成，且负向用例（非成员 `@`、路由歧义、Agent 尝试写文件、Agent 触发 Agent）全部被拒绝。

### 2.2 不在 M2.3 的范围

- Agent 与 Agent 的自动多轮对话或「Agent 开会」；
- 一条用户消息并行路由给多个 Agent 并汇总（列为开放问题）；
- 会话中直接创建 Run、修改仓库、提交补丁或触发合并/推送/部署；
- 会话内容参与执行上下文之外的长期记忆或跨会话检索（M3+）；
- 多人类成员的权限、共享与在线协作（M3 Team Workspace）；
- 移动端布局与远程 Runner；
- 会话内容自动回帖任务执行结果（默认仅手动链接，列为开放问题）。

### 2.3 裁剪顺序

若进度受限，按以下顺序裁剪，且不得裁剪 P0 安全项：

1. 成员在线/忙碌状态与 Fleet 式看板（降级为静态成员列表）；
2. 路由 rationale 的展开详情（保留一行标签）；
3. 会话重命名与成员 `roleOverride`；
4. 消息截断提示的富文本展示；
5. **不可裁剪**：只读执行边界、Agent 不触发 Agent、`@` 成员校验、路由决策持久化、转任务幂等与来源追溯、归档只读。

## 3. 关键决策

| 编号 | 决策 | 理由 |
|---|---|---|
| DEC-M23-01 | 会话是讨论层，不是执行入口；保留 Task → Run → 证据 → 评审 → 合并链路 | 避免绕过 M1 的证据、评审与合并门禁 |
| DEC-M23-02 | 自动路由 + `@` 覆盖；每条用户消息一个目标 Agent | 兼顾易用性与可控性；单目标便于审计与成本控制 |
| DEC-M23-03 | 路由决策持久化并在 UI 展示 | 讨论结论必须可解释，否则无法判断建议来源 |
| DEC-M23-04 | 会话 Agent 以 `read_only` 运行，禁止写工具与仓库写入 | 讨论层不得成为绕过权限信封的侧门 |
| DEC-M23-05 | Agent 消息不参与路由，Agent 不得触发 Agent | 防止自由聊天与无限连锁，维护 DEC-004 的执行层边界 |
| DEC-M23-06 | 转任务幂等并回填来源字段；不自动启动 Run | 追溯讨论到执行，同时保留人工启动权 |
| DEC-M23-07 | 实体命名用 Agent Team（Agent 小组），与 M3 的人类 Team Workspace 区分 | 避免产品与数据模型混淆 |

## 5. 用户故事与验收标准

### US-M2.3-01 组建 Agent 小组

作为用户，我可以创建小组并加入多个角色 Agent，以便在一个会话中获得不同角色的意见。

**验收**：创建小组 → 添加 Frontend、Backend、DevOps 三个成员 → 列表显示 `memberCount=3`；重复添加同一 Agent 返回 409；添加其他 Workspace 的 Agent 返回 409。

### US-M2.3-02 自动路由到合适角色

作为用户，我在小组会话中直接提问，系统把消息交给最合适的 Agent。

**验收**：发送「这个接口的分页参数应该怎么设计？」→ 路由到 Backend Agent；回复上方显示「路由至 Backend Agent · 依据：消息涉及 API 参数设计」；路由决策可通过 API 查询。

### US-M2.3-03 `@` 定向提问

作为用户，我可以用 `@Frontend` 指定某个 Agent 回答。

**验收**：输入 `@` 弹出成员选择器；发送 `@Frontend 这个布局在 1280px 下如何折行？` → 跳过自动路由，仅 Frontend Agent 回复；`@` 非成员返回 409 `AGENT_NOT_IN_TEAM`。

### US-M2.3-04 歧义时由用户选择

作为用户，当消息无法明确归属时，我得到候选而不是随机路由。

**验收**：发送「这个需求怎么拆？」→ 返回 409 `ROUTING_AMBIGUOUS` 与候选列表；UI 展示候选，用户选择或 `@` 后重发成功。

### US-M2.3-05 讨论不产生副作用

作为用户，我可以放心让 Agent 讨论，知道它们不会修改代码。

**验收**：会话 Agent 尝试写文件被拒绝；会话结束后仓库 `git status` 无变化；无 Run、无 Artifact 产生；Task 状态不变。

### US-M2.3-06 一键转任务

作为用户，我把一条讨论结论转成任务并继续执行。

**验收**：对 Agent 回复点击「转为任务」→ 创建 `backlog` Task，标题/描述预填，`originConversationId`/`originMessageId` 回填；再次点击返回同一 Task；会话中出现系统回执；启动 Run 后仍走 M1 证据与评审链路。

### US-M2.3-07 停止与归档

作为用户，我可以停止正在生成的回复，并归档不再需要的会话。

**验收**：生成中点击停止 → 5 秒内停止产生 delta，消息状态 `cancelled`；归档会话后发送消息返回 409 `CONVERSATION_ARCHIVED`。

## 7. 交互规则

1. **发送**：用户消息先落库（`completed`），再执行路由；路由失败时消息保留并记录失败原因，允许用户 `@` 后重发。
2. **单飞**：同一会话同一时间只允许一个 Agent 回复；回复进行中再次发送进入排队或提示等待（M2.3 采用提示等待，避免隐式排队）。
3. **上下文**：每次回复使用最近 20 条消息与 16 KiB 预算；`@` 消息在上下文中保留提及标记。
4. **停止**：停止仅取消当前回复，不回滚已生成的部分内容；消息标记 `cancelled` 并保留部分正文。
5. **失败**：Runtime 失败写 `failed` 并把错误摘要展示为系统消息；重试创建新消息，不修改原消息。
6. **归档**：小组或会话归档后只读；归档不影响已创建 Task。
7. **转任务**：转换前可在弹窗编辑标题/描述；同一消息仅一个 Task；转换不自动启动 Run。
8. **系统消息**：仅服务端追加，用户不可编辑；系统消息不参与路由。

## 9. 异常与边界

| 场景 | 行为 |
|---|---|
| 小组无成员 | 创建会话允许，发送消息返回 409 `TEAM_MEMBER_REQUIRED` 系统提示 |
| `@` 未知或非成员 | 409 `AGENT_NOT_IN_TEAM`，消息不落库 |
| 路由无匹配 | 409 `ROUTING_NO_MATCH`，消息保留 |
| 路由歧义 | 409 `ROUTING_AMBIGUOUS`，返回候选 |
| 会话归档后发送 | 409 `CONVERSATION_ARCHIVED` |
| 回复进行中再次发送 | 409 `CONVERSATION_BUSY` |
| 消息超长 | 服务端截断并标记 `truncated=true` |
| 会话超上限 | 409 `CONVERSATION_LIMIT_REACHED` |
| Runtime 不可用 | 回复 `failed`，系统消息展示可重试原因 |
| 转任务重复 | 返回已创建的 Task（200） |

## 10. 权限与安全

- **只读执行**：固定 `read_only`；禁止 Write/Edit/NotebookEdit/Bash；工作目录为临时草稿目录；
- **无凭据**：沿用 M1 环境白名单，剥离 `*_KEY`/`*_TOKEN`/`*_SECRET`/`*_PASSWORD`；
- **渲染安全**：消息按 Markdown 渲染并消毒，禁止原始 HTML；路由标签与成员名显示前转义；
- **提示注入**：会话内容视为不可信输入，不进入系统提示的指令区；路由器提示词与 Agent 指令隔离；
- **无自动对话**：Agent 消息不触发路由，防止注入内容驱动其他 Agent；
- **审计**：路由决策、成员变更、转换记录不可变；归档只读；
- **本地信任边界**：沿用 M1 的 loopback、Host/Origin 校验与版本头。

## 11. 指标

- 路由准确率（人工抽检）：目标 ≥ 85%（M2.3 演示集）；
- 首 token 延迟 p95 ≤ 4 秒；delta 到 UI p95 ≤ 1 秒；
- 会话回复失败率 ≤ 5%（不含用户停止）；
- 转任务转化可从会话追溯到 Task 的比例 100%；
- 每会话平均消息数与 token 成本纳入本地观测，不设硬性上限（受 5,000 条/20 MB 约束）。

## 13. 演示脚本

### 13.1 前置条件

- 已完成 M1：Claude Code CLI 可用并登录；默认 Workspace 已绑定；
- 存在至少三个 Agent：Frontend、Backend、DevOps（`read_only` 讨论不需要仓库写权限）。

### 13.2 演示步骤

1. 创建 Agent Team「支付重构小组」，加入 Frontend、Backend、DevOps；
2. 创建会话「支付页改造讨论」；
3. 发送「支付接口的分页参数怎么设计？」→ 观察路由到 Backend 与 rationale；
4. 发送 `@Frontend 支付页在移动端如何布局？` → 观察跳过自动路由；
5. 发送「这个需求怎么拆？」→ 观察歧义候选与选择；
6. 对 Backend 回复点击「转为任务」→ 打开 Task，确认来源字段与预填内容；
7. 启动 Run → 走 M1 证据、评审与合并链路；
8. 归档会话，确认只读；
9. 负向：`@` 非成员、生成中再次发送、Agent 写文件尝试，全部被拒绝。

### 13.3 预期结果与失败判定

所有正向步骤产生可查询的消息、路由决策与 Task 来源字段；所有负向步骤返回稳定错误码且无副作用。任一负向用例产生仓库变化、Run 或自动 Agent 连锁回复即判定失败。

## 15. 依赖、风险与假设

### 15.1 依赖

- M1 的 Runtime 适配器、`read_only` 权限模式、事件 Hub、Store 与 `/api/v1`；
- M2.1 的 Agent `role` 与 Workspace 归属；
- 不依赖登录、Postgres、远程 Runner 或 M3 的人类团队模型。

### 15.2 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 误路由 | 用户得到错误角色的建议 | rationale 可见、`@` 覆盖、歧义返回候选、可配置路由规则 |
| 上下文成本失控 | token 成本上升 | 20 条/16 KiB 预算、单目标、用量可见 |
| 讨论替代执行 | 用聊天代替任务，交付失去证据 | 产品文案强调「讨论层」、转任务入口、执行链路不变 |
| 提示注入驱动路由 | 恶意内容影响选人或回复 | 路由与内容隔离、Agent 不触发 Agent、只读执行 |
| 会话膨胀 | 页面与查询变慢 | 5,000 条/20 MB 上限、归档、增量拉取 |
| 路由实现依赖模型 | 不确定性 | 规则优先 + LLM 兜底；无模型时降级为规则并在 UI 提示 |

### 15.3 假设

- 用户希望在创建任务前进行跨角色讨论；
- 单目标路由足以覆盖 M2.3 场景；
- 本地 Claude Code 的 `read_only` 能有效阻止写工具（需负向测试验证）。
