## 本章导读

前面的章节回答「ATeam 要做什么、为谁做、怎么做」。本章回答另一个同样重要的问题：「什么会让 ATeam 做不成，或者做成了却没人用」。

本章不是一份泛泛的风险清单，而是一套可执行的风险治理机制，包含四类内容：

1. **关键假设**：ATeam 的产品逻辑建立在一组尚未完全验证的前提上。每条假设都给出验证方式、验证里程碑，以及假设不成立时的后果。
2. **风险登记表**：按产品、技术、安全与法律、采纳与竞争五类编号。每条风险都写明影响、概率、缓解措施和验证方式，并指定负责人与目标里程碑。
3. **治理需求**：把风险缓解转成可测试的治理约束，编号为 VAL（假设验证）与 GOV（风险治理）。安全、非功能、API、协作等工程需求不在本章另立编号，而是引用权威模块的既有编号（见下文「编号归属」）。
4. **决策日志与开放问题**：区分「已经决定、不再反复讨论」和「尚未决定、必须在上线前拍板」的事项。已决定项用 DEC 编号，开放问题用 OQ 编号。

阅读方式建议：产品与设计读者重点看第 2、3、6、12 章；工程读者重点看第 4、9、11 章；安全与法务读者重点看第 5、7.2、15 章；决策者重点看第 10、12、15 章。

### 评级口径

影响与概率使用统一口径，避免「感觉很重要」式的拍脑袋评级。概率只取单一等级，不使用「低到中」「中高」等区间值。

| 维度 | 等级 | 判定标准 |
|---|---|---|
| 影响 | 高 | 破坏核心闭环、造成数据丢失或凭据泄露、引发法律风险、导致产品命题不成立 |
| 影响 | 中高 | 里程碑延期超过 4 周，或显著损害用户信任与留存 |
| 影响 | 中 | 里程碑延期 1-4 周，或造成局部体验退化 |
| 影响 | 低 | 局部摩擦，可通过文档或配置绕过 |
| 概率 | 高 | 在当前计划下发生可能性超过 50% |
| 概率 | 中 | 发生可能性在 20%-50% 之间 |
| 概率 | 低 | 发生可能性低于 20% |

风险等级由完整的 4×3 影响-概率矩阵得出：

| 影响 \ 概率 | 高 | 中 | 低 |
|---|---|---|---|
| 高 | 红色 | 橙色 | 黄色 |
| 中高 | 橙色 | 橙色 | 黄色 |
| 中 | 黄色 | 黄色 | 蓝色 |
| 低 | 黄色 | 蓝色 | 蓝色 |

红色风险没有明确缓解方案时，不得进入对应里程碑的开发；橙色风险必须指定负责人并按周跟踪；黄色风险在里程碑评审时复审；蓝色风险只登记并观察。

**术语约定：**「公开预览」指 M4 的对外发布门禁（见 `prd/milestones/M4-automation-and-packaging.md` 的 M4.4）。本地 API 加固是 M1 退出条件，不得推迟到公开预览；M1 之前的任何对外分发都不属于公开预览。

## 1. 目的、范围与非目标

### 1.1 目的

本章的目的有四个：

1. **提前暴露失败模式**：在投入 M1-M4 之前，把可能导致返工、延期、数据事故或产品失败的因素写清楚。
2. **把假设变成实验**：所有关键假设都必须有验证方法和截止时间，禁止用「我们认为用户会需要」代替证据。
3. **把缓解变成可追溯的约束**：每条高等级风险至少关联一条可测试的权威工程需求（SEC、NFR、API、RUN、COLLAB、UI 等）或本章的 VAL/GOV 治理需求，避免风险文档与工程实现脱节。
4. **保留决策痕迹**：已决定事项和待决定事项分开记录，减少重复争论，也让后来者理解决策背景。

### 1.2 范围

本章覆盖：

- 目标用户与使用场景相关的前提假设；
- 产品范围、协作模型、指令质量、评审负担等产品风险；
- Runtime 适配、worktree、长任务、WebView、SQLite、命令执行等技术风险；
- 本地凭据、本地 API 暴露面、共享机器、第三方许可、清洁室合规、模型服务条款等安全与法律风险；
- 相对单 Agent CLI 的增量价值、迁移成本、信任与习惯等采纳风险；
- 大厂与云 Agent 平台带来的竞争风险；
- 风险治理需求、指标阈值、里程碑映射、决策日志与开放问题。

### 1.3 非目标

本章明确不承担以下职责：

- 不替代各模块的详细功能需求。任务看板、Agent 配置、Runtime 与 Workspace、协作与评审、安全与权限、API 与数据、非功能需求、UI 与交互的字段、状态机、接口细节，以 `prd/modules/task-management.md`、`agent-system.md`、`runtime-and-workspace.md`、`collaboration-and-review.md`、`security-and-permissions.md`、`api-and-data.md`、`non-functional-requirements.md`、`ui-ux.md` 为准。
- 不替代安全评审与法务意见。SEC 需求是工程约束，不构成法律结论。
- 不承诺消灭所有风险。本章承诺的是：风险被识别、被评级、有人负责、有验证方式、有退出标准。
- 不做完整的竞品功能拆解。竞争风险只讨论结构性威胁与差异化策略，不逐项对标第三方产品。
- 不记录日常 bug。缺陷进入缺陷跟踪系统；只有当缺陷模式上升为系统性风险时，才登记到本章。

### 1.5 当前实现基线（M0）

本章的所有「当前已实现」判断以仓库代码为准。截至本文档撰写时，M0 的真实状态如下。

**已实现：**

- 领域模型包含 Task、Agent、Run、RunEvent，见 `internal/domain/domain.go`；Task 状态包含 backlog、todo、in_progress、in_review、done、blocked、cancelled。
- SQLite 持久化与迁移机制，初始迁移见 `internal/store/migrations/0001_init.sql`；数据库开启 WAL、busy_timeout 与外键。
- HTTP API 覆盖 Task 与 Agent 的完整 CRUD；Run 只有创建（`POST /api/tasks/{id}/runs`）、列表、详情、事件查询与取消，没有 Run 的更新或删除端点；WebSocket 事件流见 `internal/api/api.go` 与 `internal/events/hub.go`。
- 调度器使用全局 worker 池执行 Run，支持超时上下文与运行中取消，见 `internal/scheduler/scheduler.go`。
- Runtime 注册表包含 mock 与 claude 两个适配器；mock 产生确定性日志，claude 适配器以 `claude -p` 方式执行本地 CLI 并按行扫描输出，见 `internal/runtime/mock.go` 与 `internal/runtime/claude.go`。
- Workspace 管理为每次 Run 创建一个目录，默认位于数据目录下的 `workspaces/runs/{run-id}`，见 `internal/workspace/workspace.go`。
- Vue 看板、Task 详情、Agent 管理、Run 列表与设置页；Wails v3 桌面壳可启动本地服务并加载 Web UI，见 `apps/desktop/main.go`。
- 仓库中不提交第三方研究资料，也不以第三方资料作为产品实现依据；研究结论必须以原创表述重新记录。

**与风险直接相关的 M0 缺口：**

| 缺口 | 代码事实 | 关联风险 | 目标里程碑 |
|---|---|---|---|
| Workspace 不是 git worktree | `Prepare` 只创建目录，忽略 `WorkspaceMode`；`Run.Branch` 从未赋值 | RISK-T-002 | M1 |
| Runtime 适配脆弱 | claude 适配器只调用 `claude -p`，无模型、权限、输出格式参数，无结构化流解析，单行上限 1 MiB | RISK-T-001 | M1 |
| 取消存在竞态 | 取消接口先改数据库状态；调度器执行前不检查 Run 是否已取消，排队中的 Run 仍可能被执行 | RISK-T-003 | M1 |
| 无崩溃恢复 | 应用重启后没有 Run 状态对账，运行中的 Run 可能永久停留在 running | RISK-T-003 | M1 |

| 无 diff、Artifact、Evidence | Run 只记录文本事件与摘要，没有变更集与验证证据；Artifact 从 M1 起交付，Evidence 从 M2 起交付 | RISK-P-005、RISK-P-007 | M1（Artifact）/M2（Evidence） |
| 无任务依赖与交付物契约 | Task 只有 `ParentID`，没有 DAG 边与契约校验 | RISK-P-002 | M2.1 |
| 未知 Runtime 静默回退 | `runtime.Registry.Get` 对未注册名称返回 mock；拼错 runtime 会以 mock 成功，制造假完成 | RISK-T-001、RISK-P-007、RUN-002/RUN-003 | M1 |
| RunEvent 唯一约束缺失 | `run_events` 只有 `(run_id, seq)` 普通索引，没有唯一约束，并发写入可能产生重复 seq | RISK-T-005、NFR-REL-010、API-1067/API-1186 | M1 |

| 无打包、登录、远程 Runner | `ateam runner` 仅为占位提示；无安装包、无用户体系、无远程执行 | RISK-T-004、RISK-S-003 | M3-M4 |

### 1.6 产品级非目标

本章的风险判断以 `prd/01-scope-and-roadmap.md` §2.4 的非目标为边界。以下事项在初期明确不做，任何「顺手实现」都视为范围蔓延（RISK-P-001）：

## 2. 关键假设与验证计划

### 2.1 假设清单

ATeam 的产品命题建立在以下假设上。每条假设都必须在本章指定的里程碑内获得证据，否则相关范围应收缩。

| 编号 | 假设 | 依据 | 若不成立的后果 | 验证方式 | 样本量与成功标准 | 截止时间 | 当前状态 |
|---|---|---|---|---|---|---|---|
| ASM-001 | 目标用户已经安装并登录 Claude Code 或 Codex 等本地 CLI | 目标用户是已经在用单 Agent 的开发者；ATeam 不转售模型，也不托管模型 | 用户必须先解决安装、登录、计费问题，首次价值时间显著拉长，采纳漏斗断裂 | 招募目标用户，记录从下载到第一个 Run 的耗时与失败点 | 10-15 名新用户；至少 70% 在无人工协助下完成首个 Run | M1 退出前 | 部分观察，未系统验证 |
| ASM-002 | 目标用户愿意让代码和 Agent 在本机执行 | 本地优先是核心定位；开发者对源码外传敏感 | 若用户更愿意用云端 Agent，本地执行成为劣势而非卖点 | 访谈与试点问卷，询问代码外传政策与真实执行位置 | 10 名访谈对象；至少 7 名接受本机执行并说明数据流向 | M1 退出前 | 未验证 |
| ASM-003 | 目标用户接受人工评审门，而不是追求全自动合并 | 高风险动作需要人工审批；证据化完成定义的价值前提是有人看证据 | 若用户要求全自动，ATeam 的评审门会被视为摩擦，可能被关闭或绕过 | 试点中统计审批通过率、审批耗时、是否有人要求自动合并 | 20 次真实审批；至少 60% 的评审者认为审批门有价值且未要求跳过 | M2.1 退出前 | 未验证 |
| ASM-004 | 大多数开发任务可以表达为「一个可审查的 diff」 | 核心闭环以 git 仓库为工作单元，以 diff 与测试为证据 | 若大量任务无法产出 diff（调研、运维、跨仓库改造），核心闭环覆盖面不足 | 对真实任务分类，统计可 diff 任务占比 | 30 个真实任务；至少 70% 能产出可审查 diff | M1 退出前 | 未验证 |
| ASM-005 | 同时运行 3-5 个 Agent 是真实痛点，而不是想象中的需求 | 目标用户画像为独立开发者与小团队；多 Agent 并行被列为核心场景 | 若用户实际只跑 1 个 Agent，ATeam 相对 CLI 的增量价值不足 | 日记研究：记录两周内的并行 Run 数、切换成本、上下文丢失次数 | 10 名用户；至少 50% 在两周内出现一周并行 3 个以上 Run | M1 退出前 | 未验证 |
| ASM-006 | 角色 Agent 可以通过任务 DAG 与交付物契约协作，而不需要自由聊天 | 自由聊天难以审计、难以复现、容易发散；契约式交付更符合工程流程 | 若契约无法覆盖真实协作，M2.1 的协作模型需要重做 | 在样例仓库上跑通 UI、Frontend、Backend、DevOps 四角色场景，统计返工与交接缺陷 | 连续 3 轮四角色场景；返工率不超过 20%，交接缺陷不超过 10% | M2.1 退出前 | 未验证 |
| ASM-007 | 用户能写出可执行的任务描述，或模板可以弥补差距 | Task 是上下文容器；指令质量决定 Run 质量 | 若用户只写一句话，Run 成功率低，用户会把失败归因于产品 | 统计任务描述完整率；做可用性测试 | 8-10 名用户；任务描述完整率达到 80% | M2.1 退出前 | 未验证 |
| ASM-008 | 证据化完成定义能提升信任并缩短评审时间 | 评审者需要 diff、测试、截图等证据，而不是 Agent 自述 | 若证据无人看，Artifact 与 Evidence 只是额外成本 | 对比有无证据面板时的评审耗时与拒绝率 | 20 次对照评审；有证据面板时评审耗时下降至少 30% | M1 退出前 | 未验证 |
| ASM-009 | 目标机器的资源足以并行运行 3-5 个 Agent | 本地执行意味着 CPU、内存、磁盘、网络都由用户承担 | 机器过载导致 Run 失败、风扇狂转、体验崩塌 | 在 16 GB 与 32 GB 内存机器上做 5 个并行 Run 的压力测试 | 两种机型各 3 轮；Run 失败率不超过 10%，系统保持可交互 | M2.1 退出前 | 未验证 |
| ASM-010 | 用户接受自带 Key 或自带订阅的成本模型，并理解自己的账单 | ATeam 不转售模型，不做模型托管 | 若用户期望统一计费，商业模型与产品架构都要调整 | 访谈中询问计费偏好；统计因计费放弃的比例 | 10-15 次访谈；至少 60% 接受 BYO Key 或自带订阅 | M3 范围冻结前 | 未验证 |

### 2.2 用户故事

以下故事把假设转化为可观察的行为。每条故事都标注里程碑，并应在对应里程碑的演示脚本中出现。

**故事一：首次价值（验证 ASM-001、ASM-007；里程碑 M1）**

- Given 一名已安装 Claude Code 且已登录的开发者，第一次打开 ATeam；
- When 他创建一个 Task、选择一个默认 Agent 并点击运行；
- Then 他应在 10 分钟内看到一个可审查的 diff 或明确的失败原因，而不是停留在配置界面。

**故事二：并行而不混乱（验证 ASM-005、ASM-009；里程碑 M1 起，M2.1 完整）**

- Given 一名开发者同时有 4 个互不依赖的任务；
- When 他启动 4 个 Run；
- Then 每个 Run 有独立 Workspace、独立事件流、独立证据，任一 Run 失败不影响其他 Run，机器资源占用可见且可控。

**故事三：角色交接（验证 ASM-006；里程碑 M2.1）**

- Given 一个包含 UI 设计、前端实现、后端接口、部署计划的任务 DAG；
- When Frontend Agent 开始工作；
- Then 它只能消费 UI Design 产出的交付物契约，契约缺失或不满足时任务阻塞并产生明确原因，而不是靠对话猜测。

**故事四：证据化评审（验证 ASM-003、ASM-008；分两段验收）**

- M1 段：Given 一个 Agent 声称任务完成；When 评审者打开 Run 详情；Then 他能在同一屏看到变更摘要、diff 与测试结果，且未批准前不得合并。
- M2.1 段：Given 评审者面对带审批门的高风险动作；When 他批准或拒绝；Then 审批绑定内容哈希与证据快照，内容变化即失效，操作进入审计。

**故事五：安全失败（验证 ASM-002，引用 SEC-071；里程碑 M1）**

- Given 一个包含密钥样本的仓库；
- When Agent 读取文件并产生日志；
- Then ATeam 的日志、事件与导出物中不出现明文密钥，且用户在界面上看到脱敏提示。

### 3.2 RISK-P-001 范围蔓延

**风险描述：** ATeam 的路线图从 M0 的骨架扩展到 M4 的分发与自动化，功能密度很高。仅 M2.1 就包含任务依赖 DAG、交付物契约、四类角色模板、路径与命令权限、审批门、收件箱、技能、模板、并行调度；M2.2 还包含 Crew 与队长。任何一项都可能独立成为一个中型项目。小团队在本地优先的约束下，很容易出现「每个功能都做了一点、没有一个能端到端演示」的局面。

**影响：** 高。里程碑延期、质量下降、演示失败、用户看到半成品、团队士气受损。更严重的是，核心闭环尚未稳定就叠加协作层，会让问题归因变得困难。

**概率：** 高。范围广、团队小、外部依赖多，这是结构性的。

**缓解：**

1. **范围分层**：每个里程碑区分「核心范围」与「可选范围」。M2.1 核心范围为任务 DAG、交付物契约、四类角色模板、路径与命令权限、审批门；收件箱、技能、模板属于 M2.1 应交付项，按 `prd/milestones/M2-role-agents.md` 的退出标准验收，更复杂的并行调度可在 M2.1 内后移；Crew、队长属于 M2.2，只有 M2.1 的并行调度与权限测试通过后才启动。
2. **设计冻结**：里程碑设计评审通过后冻结范围，新增需求进入下一个里程碑或开放问题清单，不得插队。
3. **一项进一项出**：任何进入当前里程碑的新增项，必须同时移除或推迟一项同等工作量的既有项，并在决策日志记录。
4. **功能开关**：所有 M2.1 协作能力默认关闭，按角色、按仓库逐步启用，避免半成品影响主流程。
5. **端到端演示优先**：每个迭代必须有一个可完整演示的场景，禁止只交付孤立接口。
6. **月度收缩评审**：每月检查一次范围与进度，必要时主动削减可选范围。

**验证方式：**

- 每周统计计划项与未计划项，未计划项连续两周超过 20% 即触发收缩评审。
- 每个里程碑用固定演示脚本验收，脚本未通过不得宣布完成。
- 记录每个功能从设计到可演示的周期，周期超过四周的功能必须拆分或降级。
- 里程碑结束后复盘：实际范围与计划范围的差异、延期原因、可复用的削减经验。

### 3.3 RISK-P-002 角色 Agent 协作复杂度过高

**风险描述：** 角色 Agent 协作不是让多个 Agent 在一个会话里自由聊天，而是通过任务 DAG、交付物契约、审批门和证据化完成定义来协作。这个模型在理论上清晰，但在实践中容易出现四类问题：依赖图出现环或过深导致阻塞；契约字段模糊导致下游 Agent 无法判断输入是否满足；交接只传递自然语言摘要导致上下文丢失；多个 Agent 重复修改同一路径导致冲突与返工。角色越多，组合状态越多，调试成本呈非线性上升。

**影响：** 高。若协作层无法稳定演示，M2.1 的核心卖点不成立，用户会退回到「并行跑几个独立任务」，ATeam 与普通多终端并无本质区别。

**概率：** 高。多 Agent 协作是行业共性难题，没有现成的低成本答案。

**缓解：**

1. **DAG 强校验**：创建与更新任务依赖时检测环、限制最大深度与最大宽度；超过阈值必须由人工确认。
2. **契约 Schema 化**：交付物契约包含输入、输出、验收标准、允许路径、允许命令、负责人、证据要求；缺字段不允许进入执行。
3. **交付物而非对话**：角色之间只通过 Artifact、Evidence、契约状态交接，不通过自由聊天传递关键信息。
4. **单一负责人**：每个 Task 在任一时刻只有一个负责人；角色切换必须经过状态迁移与审批。
5. **路径与命令边界**：UI Design、Frontend、Backend、DevOps 模板预设路径与命令白名单，越界即拒绝并产生策略事件。
6. **参考场景**：维护一个固定的四角色样例仓库与演示脚本，任何协作改动都必须先跑通该场景。
7. **分阶段评审**：设计交付物、实现交付物、部署计划分别设人工评审门，未通过不得进入下一阶段。
8. **Crew 后置**：同任务的 Crew 与队长模式属于 M2.2，不作为 M2.1 的必选项，避免在 DAG 与契约尚未稳定时引入第二套协作机制。

**验证方式：**

- 在样例仓库上执行四角色场景，统计交接缺陷率、返工率、DAG 阻塞时长、契约缺失率。
- 对协作场景做故障注入：故意缺失契约、故意制造路径冲突、故意制造循环依赖，系统必须给出可理解的错误而不是静默失败。
- 与「四个独立任务并行」的基线对比，若协作模式的总耗时超过基线 30%，说明协调开销过高，应简化为两角色或退回独立任务。
- 可用性测试中观察用户是否能解释「为什么这个任务在等待」，解释不了即视为协作模型可解释性不足。

### 3.4 RISK-P-003 用户不会写指令

**风险描述：** ATeam 的 Task 是上下文容器，Agent 的输出质量高度依赖任务描述、验收标准与约束。目标用户可能只写一句「做个登录页」，既不说明现有技术栈，也不给出验收标准与允许范围。结果是 Agent 自由发挥、Run 失败或产出不可评审的 diff，用户却认为是产品不好用。

**影响：** 中高。直接影响首次 Run 成功率与留存，也会放大模型成本与评审负担。

**概率：** 高。开发者习惯于口头或即时沟通，很少写结构化任务描述。

**缓解：**

1. **任务模板**：按角色提供模板，预置目标、背景、约束、验收标准、证据要求、允许路径。
2. **就绪检查**：创建 Run 前检查任务是否具备最低字段；缺失时给出提示，但不强制阻止，避免过度摩擦。
3. **澄清事件**：M2.1 引入可选的澄清阶段，Agent 最多提出三个关键问题，用户回答后继续；澄清过程本身作为事件记录。
4. **示例库**：内置高质量任务示例，用户可复制后修改。
5. **任务质量评分**：用规则而非模型给任务描述打分，提示缺失项；评分不参与权限判断。
6. **首次引导**：新用户第一次创建任务时，默认进入模板向导，而不是空白表单。
7. **失败归因**：Run 失败时区分「任务信息不足」「环境问题」「Runtime 问题」「代码冲突」，避免用户把一切归因于产品。

**验证方式：**

- 统计任务描述完整率：包含目标、约束、验收标准的任务占比，目标不低于 80%。
- 统计首次 Run 成功率：新用户第一次 Run 达到 completed 且产出可评审 diff 的比例，目标不低于 60%。
- 对 8-10 名目标用户做可用性测试，记录从空白任务到启动 Run 的耗时与卡点。
- 支持请求分类中，「不知道怎么写任务」的占比应逐月下降。

### 3.5 其他产品风险

**RISK-P-004 概念负担过重。** Task、Agent、Run、Workspace、Runtime、Artifact、Evidence 七个概念同时出现，新用户容易迷失。影响等级为中，概率为中。缓解：渐进披露，默认只展示 Task 与 Run；Agent 与 Runtime 放在设置层；Workspace 与 Artifact 在需要时展开；提供「从模板开始」路径。验证：首次配置完成率、概念理解测试、放弃率。

**RISK-P-005 评审成为瓶颈。** 多个 Agent 并行会产生大量 diff，人工评审可能跟不上。影响中高，概率为中。缓解：评审界面优先展示变更摘要、风险文件、测试结果与未通过项；按风险分级决定评审深度；支持批量批准低风险变更；限制每个评审者的并行 Run 数；提供评审排队指标。验证：评审排队时长、拒绝率、积压量、评审者主观负荷。

**RISK-P-006 本地优先边界被误解。** 用户可能期待关机后任务继续运行、跨设备访问、团队共享。影响等级为中，概率为中。缓解：产品文案明确本地执行边界；M3 提供远程 Runner；提供断点恢复与通知；不承诺云端能力。验证：支持请求分类、流失访谈、对「本地优先」一句话的理解测试。

**RISK-P-007 虚假完成。** Agent 可能声称完成但未运行测试、未覆盖边界、未产生实际 diff。影响高，概率为中。缓解：完成定义必须绑定证据；没有测试结果或 diff 的 Run 不得进入 in_review；人工批准前不得合并；记录回滚率。验证：虚假完成率、回滚率、评审拒绝原因分类。

### 3.6 RISK-P-008 模型成本与额度失控

**风险描述：** ATeam 支持同时运行 3-5 个 Agent，每个 Agent 的每次 Run 都会调用用户自带的模型服务。M0 不记录 token 用量，没有单 Run 成本上限，没有按 Agent 或按日的预算，也没有额度耗尽后的统一提示。用户可能在不知情的情况下把多个长任务并行放大，导致套餐额度耗尽、账单超预期，或 Runtime 频繁因限流失败却看不出原因。这不是单纯的费用问题，它会直接转化为「Run 为什么一直失败」的支持负担。

**影响：** 中高。额度耗尽会让核心闭环在同一时刻全面失败；账单惊吓会直接损害留存与信任。

**概率：** 高。并行是核心场景，而当前没有任何成本护栏。

**缓解：**

1. **用量记录**：按 NFR-COST-002 记录每次 Run 的 input/output/cache token；Runtime 无法提供时标记 `unknown`，不得估算冒充真实值。
2. **成本可见**：按 NFR-COST-003 使用带版本号的本地价格表估算费用，并在界面明确标注「估算」；最终以模型供应商账单为准（NFR-COST-009）。
3. **预算与上限**：M3 起按 NFR-COST-006 支持 Agent 月度预算与工作区日预算，80% 提醒、100% 阻止新 Run；M2.1 起按 NFR-COST-010 限制单 Run 最大时长与最大轮次。
4. **限流退避**：按 NFR-NET-004 对瞬时错误最多重试 3 次，429 遵循 `Retry-After`，认证与参数错误不重试。
5. **禁止后台自动调用**：按 NFR-COST-007，所有 Run 必须由用户触发或由用户显式配置的定时/Webhook 触发，不得在后台自动发起模型调用。
6. **失败归因**：额度耗尽与限流映射到 `RATE_LIMITED` 或 `PROVIDER_ERROR` 稳定分类（NFR-NET-003），在 Run 详情展示原因与建议，而不是只显示 stderr。

**验证方式：**

- 5 个并行 Run 的用量报告与各 Runtime 返回的 token 总数一致；缺失时显示 `unknown`。
- 预算达到 80% 时提醒、达到 100% 时阻止新 Run，覆盖操作有理由与审计。
- 模拟 429 与额度耗尽，Run 失败原因可读，不出现无限重试。
- 单 Run 达到最大轮次或最大时长时被终止并记录原因。

## 4. 技术风险

### 4.1 RISK-T-001 Runtime CLI 变化与适配脆弱

**当前事实：** `internal/runtime/claude.go` 只做了三件事：在 PATH 中查找 `claude`，以 `claude -p` 加提示词启动进程，按行扫描 stdout 与 stderr。它没有模型选择、权限模式、输出格式、会话恢复、结构化事件解析，也没有版本探测。单行扫描上限为 1 MiB，超长输出会被截断。mock 适配器是默认运行时，真实适配器在 M0 属于「可用但脆弱」状态。

**风险描述：** Runtime CLI 是外部依赖，其命令行参数、输出格式、认证流程、模型名称、限流策略都可能变化。CLI 可能在等待登录时挂起，可能因为订阅与 API 计费差异而失败，可能在不同操作系统上对参数的转义规则不同。适配器越薄，越容易在版本升级时无声失效。

**影响：** 高。Runtime 是核心闭环的发动机，适配失败意味着所有 Run 失败。

**概率：** 高。外部 CLI 的演进节奏不受 ATeam 控制。

**缓解：**

1. **能力探测**：启动 Run 前探测 CLI 是否存在、版本是否在支持范围、是否已完成认证；不满足时快速失败并给出可操作提示。
2. **契约测试**：为适配器建立覆盖启动、流式输出、退出码、超时、取消、认证失败、CLI 不存在七类场景的契约测试，使用录制的输出样本做回归。
3. **结构化优先**：优先使用 CLI 提供的结构化输出格式；只有在不支持时才退回按行扫描，并在事件中标注降级模式。
4. **错误分类**：Run 失败使用 `api-and-data.md` §7.4 的 `errorCode` + `failureDetail` 目录（`runtime_error`/`runtime_missing`、`runtime_error`/`runtime_auth`、`runtime_error`/`runtime_unavailable`、`runtime_error`/`invalid_agent_config`、`timeout`、`workspace_error`/`workspace_provision_failed`、`permission_denied`、`interrupted`、`cancelled_by_user`）。HTTP 层错误使用 §7.3 的大写错误码（如 `POLICY_DENIED`、`APPROVAL_REQUIRED`、`MERGE_CONFLICT`）。NFR-NET-003 的稳定分类可用于聚合与告警，但不得替代 Run 的 `errorCode` + `failureDetail`。
5. **版本矩阵**：维护「最低支持版本、推荐版本、最新验证版本」矩阵；每次发布前用矩阵跑回归。
6. **金丝雀任务**：每个版本在 CI 中运行一个真实但无副作用的金丝雀任务，验证端到端链路。
7. **原始输出留存**：保留原始 stdout 与 stderr 的脱敏副本，便于区分 CLI 变更与 ATeam 缺陷。
8. **禁止静默回退**：生产环境不得在真实 Runtime 失败时自动回退到 mock，避免用户误以为任务已完成。

**验证方式：**

- CI 矩阵覆盖最低支持版本与最新验证版本，七类契约场景全部通过。
- 每周金丝雀任务连续成功；失败时 7 天内定位到 CLI 变更或 ATeam 缺陷。
- 错误分类覆盖率不低于 95%，未分类错误进入缺陷跟踪。
- 在认证过期、CLI 被卸载、版本不兼容三种场景下，用户能在界面上看到明确原因与修复建议。

### 4.2 RISK-T-002 worktree 与合并冲突

**当前事实：** M0 的 `workspace.Prepare` 只创建目录，完全忽略 `WorkspaceMode`；Run 的 `Branch` 字段从未被赋值；没有 git 操作、没有 diff、没有合并。Agent 在普通目录中工作，无法保证与主工作区隔离。

**风险描述：** M1 引入 git worktree 后，会面对大量边界情况：仓库有未提交改动、仓库本身已是 worktree、存在子模块、使用 Git LFS、包含符号链接、路径过长、权限不足、磁盘空间不足、同一仓库并发创建多个 worktree、基础分支在运行期间前移、合并时产生冲突。任何一项处理不当都可能污染用户的主工作区或丢失改动。

**影响：** 高。工作区隔离是核心承诺；一旦破坏用户仓库，信任很难恢复。

**概率：** 高。真实仓库的形态远比演示仓库复杂。

**缓解：**

1. **预检**：创建 worktree 前检查是否 git 仓库、git 版本、基础分支、未提交改动策略、磁盘空间、路径长度、子模块与 LFS 状态。
2. **受控根目录**：所有 worktree 放在 ATeam 数据目录下的专用根目录，不写入用户仓库内部。
3. **一 Run 一 worktree 一分支**：分支命名可预测且带 Run ID；从固定基础 SHA 创建，记录基础 SHA。
4. **不触碰主工作区**：所有写操作限定在 worktree 内；禁止在用户主工作区执行 checkout、reset、clean。
5. **冲突预检**：合并前用只读方式检测冲突，冲突时阻止合并并生成证据，由人工解决。
6. **人工合并门**：合并必须经过人工批准；M1 只支持本地合并，M3 才引入 PR 流程。
7. **安全清理**：只清理 ATeam 创建的 worktree；清理前检查是否有未提交改动；默认保留策略可配置。
8. **仓库级锁**：同一仓库的 worktree 创建、合并、清理串行化，避免并发 git 操作互相破坏。
9. **可回滚**：合并失败或清理失败时保留现场，提供恢复指引，不自动删除。

**验证方式：**

- 使用固定样例仓库覆盖：干净仓库、脏仓库、嵌套 worktree、子模块、LFS、符号链接、长路径、只读目录。
- 合并冲突场景必须稳定复现并被阻止，不得产生半合并状态。
- 清理测试验证未提交改动不会被删除。
- 故障注入：运行中移动基础分支、删除 worktree 目录、磁盘写满，系统必须给出可恢复的错误。
- 用户主工作区的文件哈希在 Run 前后保持一致（只读校验）。

### 4.3 RISK-T-003 长任务稳定性

**当前事实：** 调度器使用进程内 worker 池，支持超时上下文与运行中取消，但没有心跳、没有断点、没有重试、没有启动对账。取消接口在调度器找不到取消函数时仍会把数据库状态改为 cancelled；排队中的 Run 被取消后，队列中的 ID 仍可能被 worker 取出执行。应用重启后，状态为 running 的 Run 不会自动收敛。

**风险描述：** 真实开发任务可能运行数十分钟到数小时。期间可能遇到笔记本休眠、网络中断、CLI 挂起、子进程成为孤儿、输出量暴涨、磁盘写满、应用崩溃。没有心跳与对账，用户会看到永久 running 的 Run；没有取消收敛，用户会看到「已取消但仍在跑」的状态。

**影响：** 高。长任务是 Agent 开发的常态，稳定性直接决定产品可信度。

**概率：** 高。M0 的实现已经存在可复现的取消竞态与崩溃恢复缺口。

**缓解：**

1. **心跳与租约**：Run 定期更新心跳时间；超过阈值无心跳时标记为 stalled 并触发告警或终止。M1 先以 Run 字段与 `run.updated` 承载心跳状态，不新增事件类型；若确需独立事件，必须先在 `api-and-data.md` §6.3 的事件目录登记并给出载荷 schema。
2. **进程组管理**：以进程组启动 Runtime，取消时终止整个进程组，避免孤儿进程（NFR-REL-015）。
3. **启动对账**：应用启动时扫描非终态 Run，按 NFR-REL-002 标记为 failed 且 `errorCode=interrupted`，保留事件并写入结束时间；不得静默保持 running。
4. **取消收敛**：取消接口必须同时处理排队中与运行中两种状态；worker 取出任务后先检查状态，已取消则跳过（API-1062）。
5. **重试策略**：区分可重试错误与不可重试错误；重试有次数上限与退避；重试复用同一 Task 但生成新 Run，避免覆盖历史证据。
6. **输出限额**：单条消息、单 Run 事件总量、单 Run 输出字节数均有上限；超限截断并记录（API-1072、RUN-008）。
7. **超时分层**：Agent 级超时、Run 级超时、进程级超时分别配置，默认值可被覆盖但有上限（NFR-REL-006）。
8. **状态机约束**：Run 状态迁移只允许白名单路径；终态不可回退；所有迁移写事件。

**验证方式：**

- 杀进程测试：运行中强制结束应用，重启后 10 秒内完成对账（与 `02-domain-model.md` DM-RUN-009、`03-user-flows.md` FLOW-X-021 一致），不出现永久 running。
- 取消测试：运行中取消与排队中取消均在 5 秒内收敛，且不会继续执行。
- 休眠测试：模拟机器休眠与唤醒，按 NFR-NET-009 重新校验在途 Run；无法确认时标记 failed（`errorCode=interrupted`），不得静默成功。
- 长跑测试：4 小时连续运行，事件与内存不出现无界增长。
- 输出洪泛测试：单 Run 产生 1 GB 输出，系统按限额截断且保持可用。

### 4.4 RISK-T-004 跨平台 WebView 与桌面壳

**当前事实：** 桌面壳使用 Wails v3，macOS 上以 WKWebView 加载本地 HTTP 服务；没有打包、没有签名、没有自动更新；开发模式依赖 Go 与 Wails CLI。README 明确打包是后续里程碑。

**风险描述：** 三个平台的 WebView 差异明显：macOS 的 WKWebView、Windows 的 WebView2、Linux 的 WebKitGTK 在字体、输入法、滚动、文件选择、下载、渲染性能上行为不同。Wails v3 仍在演进，API 可能变化。Windows 可能缺少 WebView2 运行时；Linux 发行版依赖复杂；大 diff 渲染可能卡顿。签名、公证、安装包格式与自动更新都会增加发布复杂度。

**影响：** 中高。桌面体验是「驾驶舱」定位的一部分，跨平台问题会带来大量支持成本。

**概率：** 中。核心 UI 是 Web 技术，风险主要集中在壳层与打包。

**缓解：**

1. **浏览器优先**：核心 UI 在浏览器中完整可用，桌面壳只做窗口与本地服务启动，降低对壳层 API 的依赖。
2. **能力检测**：启动时检测 WebView 版本与缺失运行时，给出安装指引或降级到浏览器。
3. **CI 矩阵**：M1 起至少保证三平台编译与冒烟；M4 打包前扩展到安装、启动、卸载、升级。
4. **最低系统版本**：明确支持范围，超出范围不承诺。
5. **性能预算**：大 diff 使用虚拟滚动与按需加载；单页渲染时间设预算并监控。
6. **打包后置**：M4 再做 DMG、NSIS、AppImage 与签名、公证、自动更新，避免过早陷入分发细节。
7. **回滚通道**：自动更新必须支持回滚到上一版本。

**验证方式：**

- 三平台冒烟清单：启动、创建 Task、运行 mock、打开 Web UI、查看 Run 事件。
- Windows 无 WebView2 场景必须给出可理解提示。
- 大 diff 性能测试：1 万行 diff 的首屏渲染时间与滚动帧率达标。
- 安装包在干净机器上完成安装、启动、卸载，无残留关键文件。

### 4.5 RISK-T-005 SQLite 与数据增长

**当前事实：** SQLite 使用 WAL、busy_timeout 5000 ms、最大打开连接数为 1；只有一份初始化迁移；RunEvent 无保留策略；Artifact 尚未实现。

**风险描述：** Agent 输出可能非常庞大，RunEvent 表会快速膨胀；单连接写入在高频事件下可能成为瓶颈；数据库文件过大导致备份、迁移、启动变慢；磁盘写满时写入失败可能影响状态一致性；未来团队模式需要多用户并发，SQLite 不再合适。

**影响：** 中。个人使用可通过清理缓解，团队模式会放大。

**概率：** 中。长任务与多 Agent 并行会加速数据增长。

**缓解：**

1. **事件限额与截断**：单条 `message` 上限 8 KiB（`api-and-data.md` §6.4、API-1072），单事件 payload 上限 64 KiB（RUN-008），每 Run 20,000 条或 50 MB（API-1072）；超过单条上限的内容截断后存储，达到每 Run 总量上限后停止写入正文，保留摘要与指针，并追加 `warning` 标记 `EVENTS_TRUNCATED`。
2. **保留策略**：统一保留表以 `api-and-data.md` §9.5、`security-and-permissions.md` §5.5 与 `non-functional-requirements.md` §7.5 的同一口径为准——WebSocket 重放缓冲保留 7 天或 100,000 条；RunEvent 每 Run 20,000 条或 50 MB 容量上限、Run 结束后保留 90 天；Artifact 与 Evidence 90 天；Run Workspace 已合并或放弃后 30 天；本地审计 90 天；团队审计 180 天（可配 90 天至 3 年）；本地遥测 30 天或直到用户删除。本章不另立默认值，只定义风险触发阈值（见第 10 章）。
3. **分页与索引**：事件查询分页；`(run_id, seq)` 必须是唯一约束（NFR-REL-010、API-1067、API-1186），避免并发写入产生重复序号；避免一次性加载全量事件。
4. **备份与恢复**：提供数据库备份与恢复命令；迁移前自动备份。
5. **容量监控**：设置数据库大小阈值，超过阈值提示清理。
6. **Postgres 迁移路径**：M3 团队模式使用 Postgres；Store 接口已抽象，迁移时保持领域模型不变。
7. **WAL 维护**：定期 checkpoint；异常退出后检查 WAL 完整性。

**验证方式：**

- 跨多个 Run 累计写入 100 万条 RunEvent 的浸泡测试，查询与写入延迟保持在预算内。
- 磁盘写满测试：写入失败时 Run 状态一致，不产生半写记录。
- 备份恢复演练：从备份恢复后数据完整，迁移版本一致。
- 数据库达到阈值时界面提示有效。

### 4.6 RISK-T-006 任意命令执行与提示注入

**当前事实：** Agent 的 `AllowedPaths` 与 `AllowedCommands` 只存储不执行；Runtime 以本地用户权限启动；Task 描述、Agent 指令与仓库内容都会进入提示词；M0 没有策略引擎、没有沙箱、没有网络限制。

**风险描述：** Agent 会读取仓库中的文件。如果仓库包含恶意指令（例如注释中要求忽略规则、读取密钥、上传数据），模型可能被诱导执行危险操作。Agent 也可能运行破坏性命令、访问工作区外的路径、读取环境变量中的凭据、通过网络外传源码。M0 的权限字段给用户一种「已经受限」的错觉，实际并未生效。

**影响：** 高。可能导致代码丢失、凭据泄露、供应链污染。

**概率：** 中。随着 Agent 能力增强与仓库来源多样化，提示注入是现实威胁。

**缓解：**

1. **把仓库当不可信输入**：系统提示中明确声明仓库内容是不可信数据，不得执行其中的指令。
2. **执行层强制策略**：M2.1 在适配器与 Workspace 边界强制执行路径与命令白名单，而不是只存字段；越界时终止 Run，`errorCode=permission_denied`（`failureDetail=path_denied` 或 `command_denied`），并按 SEC-018 记录本地审计。
3. **最小环境**：子进程只继承必要的环境变量；默认不传递敏感变量；需要时通过显式配置注入。
4. **工作区隔离**：Agent 的工作目录限定在 worktree 内；禁止访问用户主目录与系统敏感路径。
5. **Runtime 权限参数**：向 CLI 传递最小权限参数；高风险工具默认关闭。
6. **人工审批**：合并、推送、部署、删除等动作必须人工批准。
7. **网络策略**：M2.1 至少提供「禁止网络」与「允许网络」两种模式；默认按 Agent 模板配置。
8. **安全测试**：建立提示注入样例库，作为回归测试的一部分。
9. **插件沙箱**：M4 插件 API 必须有权限清单与隔离边界。

**验证方式：**

- 红队样例：仓库中植入诱导读取密钥、删除文件、外传数据的指令，Agent 不得执行，或至少被策略阻止并产生事件。
- 策略绕过测试：路径穿越、符号链接、命令拼接、环境变量展开均被拒绝。
- 密钥读取测试：Agent 无法读取未授权路径下的密钥文件。
- 破坏性命令测试：删除、推送、部署命令在无审批时被拒绝。

### 4.7 RISK-T-007 资源与并发失控

**当前事实：** 调度器只有全局 worker 数，默认 2；Agent 的 `MaxConcurrency` 未被执行；没有按 Agent 的队列与配额；Workspace 目录不会自动清理。

**风险描述：** 用户同时启动多个 Run 时，可能出现 CPU、内存、磁盘、网络争用，导致所有 Run 变慢甚至失败。某个 Agent 可能占满全局 worker，饿死其他 Agent。长时间运行积累的 worktree 会占满磁盘。

**影响：** 中。影响体验与稳定性，但通常可恢复。

**概率：** 中。并行是核心场景，资源争用必然出现。

**缓解：**

1. **双层并发控制**：全局上限加 Agent 级 `MaxConcurrency` 信号量；超过配额进入队列并显示排队位置。
2. **公平调度**：按提交时间或权重轮转，避免单一 Agent 饿死其他 Agent。
3. **资源提示**：界面显示当前运行数、队列长度、CPU 与内存占用估算。
4. **磁盘配额**：Workspace 根目录设置配额；超过阈值阻止新 Run 并提示清理。
5. **清理任务**：按保留策略清理已结束的 worktree 与临时文件。
6. **压力保护**：检测系统负载过高时降低并发或暂停新 Run。

**验证方式：**

- 5 个并行 Run 压力测试：全部完成或给出明确失败原因，机器不出现无响应。
- Agent 级并发测试：超过 `MaxConcurrency` 的 Run 必须排队。
- 磁盘配额测试：达到阈值后新 Run 被阻止，提示可操作。
- 清理测试：过期 Workspace 被回收，用户可恢复或导出。

### 4.8 RISK-T-008 依赖供应链

**当前事实：** Go 依赖包含 Wails v3、gorilla/websocket、modernc.org/sqlite 等；前端依赖通过 pnpm 管理并有锁文件；仓库尚无可视的依赖审计流水线。

**风险描述：** 依赖升级可能引入破坏性变更或漏洞；锁文件被意外修改可能引入不可信版本；Wails v3 的演进可能影响桌面壳；打包产物若未签名，可能被篡改。

**影响：** 中高。供应链问题往往在发布后才暴露。

**概率：** 低。依赖数量可控，但升级不可避免。

**缓解：**

1. **依赖审计**：CI 中运行 Go 漏洞扫描与前端依赖审计；高危漏洞阻断合并。
2. **锁文件审查**：依赖升级必须单独提交并说明原因；禁止无锁文件变更的依赖漂移。
3. **SBOM**：M4 分发前生成软件物料清单。
4. **最小依赖**：新增依赖必须说明用途、许可证与替代方案。
5. **签名发布**：安装包与自动更新包必须签名并校验。
6. **可复现构建**：记录构建环境与工具版本，尽量保证可复现。

**验证方式：**

- CI 审计任务连续通过；高危漏洞为零。
- 依赖升级 PR 均包含变更说明与回归结果。
- 发布包签名校验通过；篡改包被拒绝。
- SBOM 包含全部运行时依赖与许可证信息。

## 5. 安全与法律风险

### 5.1 RISK-S-001 本地凭据

**风险描述：** ATeam 本身不要求用户输入模型 Key，但 Runtime CLI 会在本机保存认证信息。ATeam 启动子进程时可能继承环境变量；RunEvent 可能记录包含 Token 的输出；Artifact 可能包含配置文件；远程 Runner 在 M3 会跨机器传递凭据引用。

**影响：** 高。凭据泄露可能导致用户账单损失、代码仓库被访问、模型账号被滥用。

**概率：** 中。只要日志与导出存在，泄露路径就存在。

**缓解：**

1. **默认不代管密钥**：M0-M1 依赖 Runtime CLI 自身的认证机制；M2.1 起如用户在 ATeam 内保存 Secret，数据库只保存钥匙串引用，不落明文（SEC-013）。
2. **环境白名单**：子进程只继承必要环境变量；敏感变量默认不传递。
3. **日志脱敏**：写入 RunEvent、Artifact、导出物前执行密钥模式扫描与脱敏。
4. **系统钥匙串**：M2.1 起模型的 Secret 引用写入操作系统钥匙串（SEC-013）；M3 远程 Runner 令牌使用安全存储与短期租约。
5. **最小权限**：远程 Runner 使用一次性注册令牌、机器密钥与短期租约，支持吊销与轮换（SEC-040～SEC-044）。
6. **安全提示**：共享机器与远程 Runner 场景明确提示用户风险。

**验证方式：**

- 注入常见密钥样本，日志、事件、导出物中不可检索到明文。
- 环境变量测试：未授权变量不出现在子进程环境中。
- 远程 Runner 令牌泄露演练：吊销后立即失效。
- 代码扫描中不存在硬编码密钥。

### 5.2 RISK-S-002 本地 API 暴露面

**当前事实：** `internal/api/api.go` 的 CORS 中间件会反射任意 Origin；`internal/events/hub.go` 的 WebSocket `CheckOrigin` 恒为 true；HTTP API 没有任何认证。`app.DefaultConfig` 只把 `127.0.0.1:8787` 作为默认值，`ateam serve --addr 0.0.0.0:8787` 可以直接绑定所有网卡，当前没有守卫、没有认证、也没有启动告警。桌面模式使用随机本地端口，但端口可被扫描。

**风险描述：** 恶意网页可以在用户浏览器中向本地 API 发起请求，读取任务、Agent、Run 与事件数据，甚至创建或取消 Run。DNS 重绑定与跨站 WebSocket 会放大风险。回环绑定不等于安全：浏览器中的任意页面都能访问回环地址；而 `--addr` 又能把服务直接暴露到局域网，形成「用户以为只在本机、实际全网可连」的反差。

**影响：** 高。可能造成数据泄露与未授权操作，且用户难以察觉。

**概率：** 高。当前实现已具备可利用条件，且非回环绑定没有护栏。

**缓解：**

1. **来源校验**：CORS 只允许明确的本地开发来源；生产模式使用同源，不反射任意 Origin（SEC-004、API-1241）。
2. **Host 校验**：拒绝非预期 Host 头，降低 DNS 重绑定风险（SEC-004、NFR-SEC-004）。
3. **会话令牌**：M2.1 起每次启动生成随机令牌，Web UI 通过一次性 bootstrap URL 或 `0600` 令牌文件获取；除 `/api/health` 外所有 API 与 WebSocket 均校验令牌（SEC-003）。M1 先关闭 Origin/Host/CORS 攻击面。
4. **WebSocket 来源校验**：禁止 `CheckOrigin` 恒真；只允许同源或明确白名单（SEC-004、API-1242）。
5. **CSRF 防护**：写操作要求自定义头或令牌，避免简单表单跨站提交。
6. **远程绑定守卫**：M1 默认只监听回环地址，`--addr` 指定非回环地址时直接启动失败，不提供远程放行开关（SEC-001、SEC-002）；后续如引入远程模式，必须显式开关、强制认证与 UI 风险横幅。
7. **安全响应头**：设置 Content-Security-Policy、X-Content-Type-Options、Referrer-Policy、frame-ancestors 等头（SEC-005）。
8. **发布阻断**：Origin/Host/CORS、远程绑定守卫与文件权限是 M1 退出条件；会话令牌按 SEC-003 在 M2.1 交付。两项完成前不得对外分发，公开预览（M4）前重新审计。

**验证方式：**

- 跨源请求测试：未授权 Origin 返回 403。
- 伪造 Host 测试：非预期 Host 返回 403。
- 无令牌请求测试：M2.1 起 API 与 WebSocket 均被拒绝。
- 启动测试：M1 下非回环地址直接启动失败，不提供放行开关；后续远程模式必须有显式开关、认证与 UI 告警。
- M1 退出检查单包含 Origin/Host/CORS 与远程绑定检查项；M2.1 增加会话令牌检查；公开预览（M4）前复跑渗透测试清单。

### 5.3 RISK-S-003 共享机器

**风险描述：** 团队用户可能在同一台机器或同一操作系统账号下共享 ATeam。SQLite 数据库、Workspace、Artifact、日志可能包含源码与敏感信息。M0 没有用户体系、没有权限隔离、没有审计。M3 团队模式引入登录与角色后，仍需处理同一 OS 账号下的文件权限问题。

**影响：** 高。源码与凭据可能被同事或访客读取。

**概率：** 中。小团队共享机器是现实场景。

**缓解：**

1. **文件权限**：M1 起数据目录、数据库、Workspace 默认仅当前用户可读写；macOS/Linux 使用 0700/0600，Windows 使用等效 ACL（SEC-007）。
2. **按用户数据目录**：M3 团队模式按用户区分数据目录与会话。
3. **登录与角色**：M3 引入用户、角色与最小权限；敏感操作需要更高权限。
4. **审计**：审批、合并、部署、导出等动作记录操作者、时间、对象与结果。
5. **会话锁定**：桌面端提供锁定与自动登出；共享机器提示。
6. **数据清理**：退出登录或切换用户时清理本地缓存与临时文件。
7. **加密选项**：团队模式下提供数据库与 Artifact 加密选项。

**验证方式：**

- 文件权限检查：其他 OS 用户无法读取数据目录。
- 角色测试：低权限用户无法执行审批、合并、导出。
- 审计回放：能够还原谁在何时执行了什么操作。
- 切换用户后不残留上一用户的敏感缓存。

### 5.4 RISK-S-004 第三方许可

**风险描述：** ATeam 以 Apache-2.0 发布，依赖的 Go 与前端包各有许可证。某些许可证可能对分发、修改、专利授权有额外要求；打包安装包时若未保留版权声明与许可证文本，可能违反条款。Runtime CLI 由用户自行安装，ATeam 不分发其二进制，但文档与集成方式仍需避免暗示官方背书。

**影响：** 高。许可证违规可能导致下架、法律纠纷、社区信任受损。

**概率：** 中。依赖数量可控，但审计需要持续进行。

**缓解：**

1. **许可证清单**：维护依赖与许可证清单，随依赖变更更新。
2. **SBOM**：分发前生成软件物料清单。
3. **NOTICE 与 LICENSE**：安装包与源码包保留完整版权与许可证文本。
4. **许可证策略**：禁止不兼容许可证进入分发产物；新增依赖必须经过审查。
5. **边界声明**：明确 ATeam 不包含、不分发第三方产品的代码、文档、UI 资产或商标。
6. **法律审阅**：公开发布与商业化前进行法律审阅。

**验证方式：**

- CI 许可证检查通过；未知许可证数量为零。
- 安装包中包含 LICENSE、NOTICE 与依赖许可证文本。
- 新增依赖 PR 均记录许可证审查结论。
- 发布前法务检查清单完成。

### 5.5 RISK-S-005 开源合规与清洁室

**风险描述：** 任何贡献者或自动化工具如果读取并复制第三方产品的研究资料、代码、文档、截图、图标或文案，都可能污染原创实现，导致许可证与版权风险。

**影响：** 高。清洁室被破坏后，补救成本极高，甚至需要重写。

**概率：** 中。多人协作与自动化工具增加了误用可能。

**缓解：**

1. **资料隔离**：仓库不提交第三方研究资料，不引用第三方文档，也不让自动化工具读取第三方资料；研究结论必须以原创表述重新记录。
2. **贡献者声明**：贡献指南要求声明原创来源，禁止复制第三方代码、文档、UI 资产、商标与文案。
3. **评审检查**：代码评审检查是否存在可疑复制痕迹、非原创资产、第三方品牌。
4. **NOTICE**：保留原创实现声明与第三方依赖声明。
5. **商标与品牌**：不使用第三方产品名称、图标、界面风格作为 ATeam 的标识。
6. **定期扫描**：对仓库进行文本与资产扫描，发现可疑内容立即移除并复盘。
7. **培训**：新贡献者入门时说明清洁室要求与边界。

**验证方式：**

- 仓库扫描中不存在被禁止的资料引用或复制片段。
- 每个贡献 PR 包含原创性确认。
- NOTICE 与贡献指南内容完整。
- 发布前进行清洁室审计并留存记录。

### 5.6 RISK-S-006 模型服务条款与计费

**风险描述：** 用户自带 Runtime 与 Key，ATeam 不转售模型。但不同 Runtime 的订阅与 API 计费规则不同，自动化调用可能超出套餐限制、触发限流或违反服务条款。远程 Runner 场景可能让一台机器代表多个用户调用模型，增加合规复杂度。

**影响：** 中。可能导致账号受限、费用争议、用户投诉。

**概率：** 中。计费规则与限流策略经常变化。

**缓解：**

1. **明确边界**：产品文档说明 ATeam 不提供模型服务、不转售额度、不代管 Key。
2. **用户确认**：首次配置 Runtime 时提示用户确认自己的计费方式与条款。
3. **限流处理**：识别限流错误并提示退避，不自动无限重试。
4. **远程 Runner 归属**：M3 明确每次远程执行使用谁的凭据与额度，要求显式授权。
5. **不代理凭据**：ATeam 服务端不存储、不转发模型 Key；远程 Runner 使用用户自己的凭据或短期授权。
6. **条款跟踪**：关注 Runtime 提供方的条款变化，必要时更新产品行为。

**验证方式：**

- 限流场景测试：错误被识别、退避、用户可见。
- 远程 Runner 授权测试：未授权用户无法使用他人凭据。
- 文档审查：计费与条款边界表述清晰。
- 支持请求中计费争议可归因。

### 5.7 RISK-S-007 自动更新与分发

**风险描述：** M4 引入 DMG、NSIS、AppImage 与自动更新。若更新包未签名、未校验、无回滚，可能被篡改或推送错误版本，造成供应链攻击或大范围故障。

**影响：** 高。一次恶意更新即可影响全部用户。

**概率：** 低。取决于发布流程的严谨程度。

**缓解：**

1. **签名与公证**：macOS 公证、Windows 代码签名、Linux 校验和。
2. **更新清单签名**：更新清单与安装包均签名；客户端校验后再安装。
3. **分阶段发布**：先小范围灰度，再全量。
4. **回滚**：保留上一版本，支持一键回滚。
5. **更新日志与确认**：重大更新需用户确认；安全更新可提示但不得静默破坏兼容性。
6. **构建隔离**：发布构建在受控环境执行，产物可追溯。

**验证方式：**

- 篡改包测试：签名校验失败并拒绝安装。
- 回滚测试：升级失败后可恢复到上一版本。
- 灰度发布流程演练通过。
- 发布产物哈希与构建记录可追溯。

### 5.8 RISK-S-008 隐私、日志与遥测

**风险描述：** ATeam 的日志、事件、Artifact 可能包含源码、提示词、模型输出、路径、用户名。M4 计划引入遥测，如果默认开启或采集粒度过细，可能泄露用户代码与行为。用户也可能不知道如何导出或删除自己的数据。

**影响：** 中高。隐私问题会直接损害本地优先的信任基础。

**概率：** 中。只要引入遥测与日志导出，风险就存在。

**缓解：**

1. **默认不采集**：遥测默认关闭；首次启用需要显式同意，可随时关闭。
2. **最小采集**：只采集运行指标与错误类型，不采集源码、提示词、模型输出、文件路径。
3. **脱敏**：崩溃报告与日志上传前脱敏。
4. **本地优先**：数据默认只存本机；远程 Runner 场景明确数据流向。
5. **导出与删除**：提供数据导出与删除能力；说明保留期限。
6. **隐私文档**：公开采集项、用途、保留期限与关闭方式。
7. **审计**：遥测发送记录可在本地查看。

**验证方式：**

- 默认安装后网络请求中不存在遥测上报。
- 关闭遥测后无上报。
- 遥测事件清单与实际发送一致。
- 导出与删除流程可用，删除后本地无可检索残留（备份按策略处理）。

## 6. 采纳与竞争风险

### 6.1 RISK-A-001 相对单 Agent CLI 的增量价值

**风险描述：** 单个开发者用 Claude Code 或 Codex 已经可以完成很多任务。ATeam 增加了 Task、Agent、Run、Workspace、Evidence、Review 等概念与步骤，如果这些步骤不能显著减少上下文切换、减少重复劳动、提升评审质量，用户会认为「不如直接开终端」。

**影响：** 高。这是产品命题层面的风险。

**概率：** 高。单 Agent CLI 的体验在持续变好，替代方案门槛很低。

**缓解：**

1. **价值假设量化**：明确三个价值点：并行吞吐、上下文交接、评审证据。每个价值点绑定指标。
2. **对照实验**：同一批任务分别用单 CLI 与 ATeam 完成，比较总耗时、上下文丢失次数、返工率、评审耗时。
3. **首次体验**：10 分钟内完成第一个可评审 diff；配置步骤不超过三步。
4. **不增加无谓步骤**：能在后台完成的配置不打断主流程；默认值合理。
5. **明确适用边界**：不宣称适合所有任务；单文件小改动可能直接 CLI 更快，产品应承认这一点。
6. **停止标准**：若对照实验中 ATeam 没有显著优势，暂停扩展功能，优先改进核心闭环。

**验证方式：**

- 10-15 名目标用户的对照实验：记录任务完成时间、切换次数、返工率、主观偏好。
- 日记研究：两周内用户实际使用频率与放弃原因。
- 留存指标：第 1 周激活、第 4 周留存。
- 若 4 周留存低于目标且访谈中「不如 CLI」占比超过 40%，触发产品方向复盘。

### 6.2 RISK-A-002 迁移与学习成本

**风险描述：** 用户需要安装桌面端或启动本地服务、配置 Runtime、创建 Agent、理解 Task 与 Run 的关系、学习证据与评审流程。任何一步失败都可能放弃。已有工作流（终端、IDE、任务板）也会产生迁移摩擦。

**影响：** 中高。影响激活与留存。

**概率：** 高。多概念产品天然有学习成本。

**缓解：**

1. **引导流程**：首次启动提供三步引导：连接 Runtime、创建第一个 Agent、运行第一个 Task。
2. **默认模板**：内置默认 Agent 与任务模板，用户不需要从零配置。
3. **渐进披露**：高级字段折叠；只在需要时出现。
4. **可跳过**：允许用户跳过非必要配置，先跑起来。
5. **可逆**：不修改用户仓库的默认分支；不强制接管 git 工作流。
6. **迁移文档**：说明与终端、IDE、现有任务板的关系，不要求用户放弃原有工具。

**验证方式：**

- 激活漏斗：下载、安装、启动、创建 Task、首个 Run、首个评审、首个合并各阶段转化率。
- 首次价值时间：从启动到首个可评审 diff 的中位数。
- 可用性测试：观察用户在哪一步停顿或求助。
- 支持请求中安装与配置类问题占比逐月下降。

### 6.3 RISK-A-003 信任与习惯

**风险描述：** 开发者可能不信任 Agent 的改动，或不愿意为评审付出额外时间；也可能习惯终端，觉得桌面看板多余。若 ATeam 的评审门被视为阻碍，用户可能寻找绕过方式，或直接回到单 CLI。

**影响：** 中高。信任是 Agent 产品采纳的核心。

**概率：** 中。

**缓解：**

1. **证据优先**：评审界面先给结论与风险，再给细节；用户能在 30 秒内判断是否继续。
2. **风险分级**：低风险变更简化评审，高风险变更强制细看；不搞一刀切。
3. **可解释**：每个 Run 的决策、失败原因、证据来源可追溯。
4. **不自动合并**：高风险动作永远需要人；低风险动作也必须可配置为需要人。
5. **尊重终端**：提供 CLI 与 API，允许用户在终端触发与查看，不强迫使用 GUI。
6. **快速失败**：错误信息可操作，不让用户猜测。

**验证方式：**

- 评审耗时与拒绝率对比。
- 用户访谈中信任评分。
- 是否出现绕过审批的行为；若出现，分析是流程设计问题还是用户恶意。
- 终端用户与 GUI 用户的比例与留存差异。

### 6.4 RISK-C-001 大厂与云 Agent 平台竞争

**风险描述：** 大型平台厂商可能把多 Agent、后台任务、代码评审、工作区隔离打包进现有开发工具或云平台。它们拥有分发渠道、模型资源、企业客户与品牌信任。云 Agent 平台则以「无需本地环境、随时运行」为卖点。ATeam 若正面比拼功能数量，很容易被覆盖。

**影响：** 高。竞争格局可能压缩 ATeam 的生存空间。

**概率：** 高。大厂持续加码 Agent 能力是确定性趋势。

**缓解：**

1. **差异化定位**：本地优先、代码不出本机、自带 Runtime 与 Key、开源可审计、角色协作与证据化评审。
2. **不做功能军备竞赛**：聚焦核心闭环与协作契约，不追求集成数量。
3. **开放与可扩展**：开源、插件 API、CLI 与 API 优先，允许用户自建集成。
4. **信任优势**：本地数据、透明日志、无模型转售、无锁定。
5. **社区与模板**：积累角色模板、任务模板、最佳实践，形成非代码资产。
6. **监测与复盘**：每季度做竞争格局复盘；记录用户选择竞品的原因。
7. **合作可能**：与大厂产品保持互操作，而不是全面对抗；例如通过 git、PR、Webhook 衔接。

**验证方式：**

- 季度竞争复盘报告：新增能力、定价变化、目标用户重叠度。
- 赢单与丢单访谈：记录用户选择 ATeam 或竞品的关键原因。
- 差异化功能的使用率：本地执行、角色协作、证据评审的使用占比。
- 若目标用户中「本地优先」重要性低于 30%，需要重新评估定位。

### 6.5 RISK-C-002 定位模糊

**风险描述：** 「多 Agent 开发驾驶舱」是一个抽象说法。用户可能把它理解为项目管理工具、Agent 编排框架、IDE 插件或云平台。定位不清会导致信息传达失效、功能优先级摇摆、获客成本上升。

**影响：** 中。影响市场沟通与产品聚焦。

**概率：** 中。

**缓解：**

1. **一句话测试**：用 5 秒测试用户能否复述 ATeam 的用途。
2. **场景化表达**：用「同时跑 3-5 个 Agent，每个任务有独立工作区、证据和人工评审」替代抽象词。
3. **边界声明**：明确不是通用项目管理工具的克隆、不是模型托管、不是多租户 SaaS。
4. **一致文案**：README、官网、应用内文案使用同一套术语。
5. **优先级守护**：新功能必须能回答「它如何强化核心闭环」。

**验证方式：**

- 目标用户的一句话复述准确率。
- 官网与 README 的理解测试。
- 新功能评审中「与核心闭环关系」字段完整率。

## 8. 交互与规则

### 8.1 风险生命周期

每条风险按以下状态流转：

1. **识别**：任何人可提交风险，必须包含描述与初步影响判断。
2. **评估**：产品负责人与技术负责人确认影响、概率与等级，指定负责人。
3. **缓解中**：制定缓解措施，映射到需求或里程碑。
4. **监控中**：缓解措施已上线，按指标持续观察。
5. **已关闭**：验证方式通过，风险不再构成威胁，保留记录。
6. **已接受**：无法消除或成本过高，由授权人签署接受记录，设置复审时间。

状态迁移必须记录在风险登记表中；不接受「口头关闭」。

### 8.2 评审节奏与发布门禁

- **周度**：里程碑开发期间每周检查红色与橙色风险，更新先行指标。
- **里程碑评审**：退出前 5 个工作日完成，逐项判定继续、收缩或停止。
- **发布门禁**：每个对外版本必须通过 GOV-009 清单，包括安全、许可证、迁移、回滚、跨平台冒烟。
- **季度复盘**：竞争格局、采纳指标、重大事件与风险登记表整体复审。

### 8.3 分级与升级

| 级别 | 定义 | 响应要求 |
|---|---|---|
| S1 | 数据丢失、凭据泄露、远程代码执行、大范围无法启动 | 立即停止发布；24 小时内给出缓解；48 小时内复盘 |
| S2 | 核心闭环不可用、合并破坏仓库、审批被绕过 | 当前迭代内修复；发布门禁阻断；48 小时内复盘 |
| S3 | 局部功能不可用、性能明显退化、跨平台差异 | 进入下一迭代；记录风险 |
| S4 | 体验摩擦、文案问题、低频边界 | 进入常规缺陷跟踪 |

### 8.4 风险接受与例外

- 风险接受必须由产品负责人与技术负责人共同签署；安全与法律风险还需安全评审人签署。
- 接受记录包含理由、影响范围、临时缓解、复审日期。
- 临时接受最长一个里程碑；到期必须复审，不得自动续期。
- 任何风险接受不得绕过 SEC-020、SEC-021、SEC-022、SEC-026 定义的人工审批要求。

### 8.5 人工审批规则

- 合并、推送、部署、删除工作区或分支、修改 Agent 权限，均属于高风险动作。
- 审批界面必须展示操作对象、变更摘要、证据链接、风险提示。
- 审批有有效期；过期未执行需重新审批。
- 审批记录不可篡改；团队模式下记录操作者与角色。
- DevOps 角色在 M2.1 只能生成 staging 部署与部署计划；prod 部署必须由人工执行。
- 任何自动化都不得默认批准高风险动作；自动批准不在产品范围内。

### 8.6 开放问题的处理规则

- 每个开放问题必须有负责人、截止里程碑、默认选项。
- 到期未决时按默认选项执行，并在决策日志记录「按默认选项执行」。
- 开放问题只阻塞依赖它的范围，不得阻塞整个里程碑。
- 开放问题一旦决定，转为 DEC 记录，原问题标记为已关闭。

- 全局事件与 RunEvent：统一保留表见 `api-and-data.md` §9.5、`security-and-permissions.md` §5.5 与 `non-functional-requirements.md` §7.5——WebSocket 重放缓冲 7 天或 100,000 条；每 Run 20,000 条或 50 MB；RunEvent/Artifact/Evidence 90 天；Run Workspace 30 天；本地审计 90 天、团队审计 180 天、本地遥测 30 天。

- 删除：Task/Agent 在 M1 做二次确认、阻止活跃 Run/未关闭 Review 并归档（SEC-023）；M2.1 起进入 30 天恢复窗口（SEC-028）。`archivedAt` 是唯一字段，不建 `deletedAt`；统一事件为 `task.archived`/`agent.archived`。数据删除遵循 SEC-072。
- 本章只定义风险触发阈值：当数据库增长超过 NFR-RES-006/NFR-RES-007 的容量预算、或清理任务连续失败时，触发 RISK-T-005 的预警与里程碑评审。

**API 约束：**

- 错误响应统一包含 `error.code`、`error.message`、`error.details`、`error.requestId`、`error.retryable` 五个字段（API-1140）；HTTP 错误码使用大写蛇形（如 `POLICY_DENIED`、`APPROVAL_REQUIRED`、`MERGE_CONFLICT`）；Run 失败码使用小写蛇形 `errorCode` + `failureDetail`（api §7.4）。
- 所有高风险写操作由服务端强制审批或显式确认（API-1247），不得仅依赖前端隐藏按钮。
- 事件流断线重连时按 `afterSeq` 续传；超出保留窗口时服务端发送 `events.replay_reset`，客户端重新拉取快照（API-1122）。
- 单条 RunEvent `message` 上限 8 KiB，单事件 payload 上限 64 KiB；超限截断并标记（API-1072、RUN-008）。
- M0 的 API 无认证状态必须在本章 RSK-SEC-001 对应的 SEC-001～SEC-004 完成后才能对外。

- 任一指标达到严重阈值，对应里程碑暂停新功能开发，优先修复。

- 安全事件数出现 S1，立即停止发布并按 S1 流程处理。
- 额度耗尽失败率达到严重阈值时，暂停扩大并行上限，先补齐成本可见性与退避策略。

**重点开放问题说明：**

**OQ-001 定价与开源商业模式。** ATeam 的核心承诺是本地优先、自带 Runtime、不转售模型。这意味着传统按 Token 加价的模式不适用。可行的方向包括：核心开源加赞助、开放核心（团队协作与审计付费）、托管 Runner 订阅、企业支持与咨询。建议在 M3 前完成目标团队访谈，验证「团队协作与审计」是否愿意付费。无论选择哪种模式，核心闭环不应被付费墙切断，否则会损害开源信任。

**OQ-002 Crew 的转正指标。** 「M2 是否包含 Crew」已不再是开放问题：`prd/01-scope-and-roadmap.md` 已把 M2 拆成 M2.1（DAG、契约、权限、并行调度）与 M2.2（Crew 与队长），DEC-005 也明确 Crew 后置。仍需决定的是 M2.2 的 Crew 是否转正、以及转正指标：建议先用四角色样例场景验证 DAG 与契约，若协调开销超过独立任务基线 30%、或返工率与阻塞时长不达标，Crew 只作为可选实验，不进入 M3 的默认能力。

**OQ-003 M3 是否做 SaaS。** 多租户 SaaS 会引入账号、计费、合规、数据隔离、运维与支持成本，与本地优先定位存在张力。建议 M3 聚焦自托管团队模式与远程 Runner，让团队在自己的机器或服务器上运行。多租户 SaaS 需要单独的商业论证与安全评审，不应作为 M3 的默认目标。

| 首次启动无 Agent、无 Task、无 Run | 展示带解释的空状态与一个主入口；提供默认 Agent 与任务模板 | UI-080、US-UI-14 | M0 部分，M1 完整 |
| 任务依赖未满足 | 任务保持 blocked，不启动 Run；依赖满足后自动解除 | 阻塞原因与上游任务链接（COLLAB-016、COLLAB-022、UI-031） | M2.1 |
| 交付物契约缺失或被拒绝 | 下游任务保持 blocked，给出 `contract_rejected` 原因 | 缺失字段或拒绝原因（COLLAB-016） | M2.1 |
| 等待人工审批 | 高风险动作不执行；审批进入收件箱并实时推送状态 | `APPROVAL_REQUIRED`；审批中心与 Inbox（UI-073） | M2.1 |
| 额度耗尽 | Run 失败或阻止新 Run，给出额度原因与账单说明；不无限重试 | `errorCode=runtime_error`、`failureDetail=runtime_unavailable`；HTTP 429 `RATE_LIMITED`；成本看板（NFR-COST-003、NFR-COST-006） | M2.1-M3 |
| 删除 Task 或 Agent | M0 为硬删除；M1 二次确认 + 阻止活跃 Run/未关闭 Review + 归档；M2.1 起 30 天恢复窗口 | 影响面提示；恢复能力见 SEC-023/028、API §5.5/§5.6 与 task-management §12 | M1-M2.1 |
| 共享机器切换用户 | 清理会话缓存；不残留敏感数据 | 登录与切换提示 | M3 |
| 远程 Runner 断线 | 标记连接中断；不重复执行；恢复后由人工决定重试 | `errorCode=runner_lost`、`failureDetail=heartbeat_timeout`；租约状态（SEC-042、RUN-028、RUN-029） | M3 |
| 更新包校验失败 | 拒绝安装；保留当前版本 | 更新失败提示 | M4 |

**边界原则：**

- 任何失败都不得静默成功；mock Run 不得伪装成真实完成。
- 任何破坏性操作都必须可回滚或有明确的人工确认。
- 任何高风险动作都不得自动批准。
- 任何数据删除都必须可审计，且默认保留足够恢复窗口。
- 任何跨机器执行都必须明确凭据归属与数据流向。
- 任何空状态都必须区分「还没有数据」与「已处理完」，不得把无数据误读为完成（UI-078、UI-080）。

## 14. 与其他文档的关系

### 14.1 文档分工与引用规则

本章与其他 PRD 文档的关系如下：

- **`prd/00-product-overview.md`**：定义产品定位、目标用户与非目标。本章的 ASM 假设与 RISK-A、RISK-C 风险直接检验这些目标是否成立。若本章假设被证伪，应优先修订总览中的目标与范围。
- **`prd/01-scope-and-roadmap.md`**：定义范围边界、M0-M4 路线图与 M2.1/M2.2 拆分。本章的里程碑映射必须与之一致；范围级的安全不变量（该文档的 SEC-001～SEC-014）与安全模块的 SEC 编号同号不同义，引用时必须写明文档名。
- **`prd/02-domain-model.md`**：定义实体、字段与关系。本章的 RISK-T-005 与团队规模假设引用了该文档的 NFR-007（M3 Postgres 规模目标）。
- **`prd/03-user-flows.md`**：定义端到端用户流程。本章第 13 章的异常与边界行为必须嵌入这些流程，不得出现只在文档中存在、流程中无入口的失败处理。
- **`prd/04-acceptance-and-test-plan.md`**：定义验收标准与测试矩阵，并按 `SEC-001～SEC-073` 与 `NFR-PERF/REL/PORT/OBS/A11Y/I18N/PKG/RES/NET/COST/SEC` 的范围引用需求。本章不重复这些编号。
- **模块文档（`prd/modules/`）**：实际文件为 `task-management.md`、`agent-system.md`、`runtime-and-workspace.md`、`collaboration-and-review.md`、`security-and-permissions.md`、`api-and-data.md`、`non-functional-requirements.md`、`ui-ux.md`。模块的异常与边界行为应与本章第 13 章一致；模块引用风险编号的落地计划见 14.3。
- **里程碑文档（`prd/milestones/`）**：实际文件为 `M0-scaffold.md`、`M1-local-loop.md`、`M2-role-agents.md`、`M3-team-mode.md`、`M4-automation-and-packaging.md`。里程碑文档应直接使用本章第 11 章的映射与退出条件，不得自行降低安全、审批或证据要求；演示脚本应覆盖本章的用户故事。
- **指标**：目标值与测量方法的唯一权威是 `prd/modules/non-functional-requirements.md` 与各模块指标表；本章第 10 章只定义风险触发阈值，不替代权威目标。
- **决策日志**：第 12 章是本章范围内决策的记录。任何文档与最新 DEC 冲突时，以最新 DEC 为准；被取代的决策保留历史并标注。
- **开放问题**：OQ 只阻塞依赖它们的范围。模块与里程碑文档应标注依赖的 OQ 编号，避免在未决问题上反复讨论。
