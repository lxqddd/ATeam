# 范围、路线图与发布标准

## 本章导读

本章定义 ATeam 的产品边界、里程碑路线图、发布标准和范围变更规则。它回答四个问题：第一，ATeam 做什么、不做什么；第二，M0 到 M4 每个阶段交付什么用户结果、何时算完成；第三，什么条件下允许发布；第四，什么条件下允许调整范围。读者包括产品经理、工程师、设计师和决策者。

本章只定义跨模块的范围、顺序与门禁，不重复模块内部的字段级细节。Task、Agent、Run、Workspace、Artifact、Evidence、审批、团队模式等模块的具体需求，见 `prd/modules/` 下的模块文档；每个里程碑的目标、用户故事、交付物、演示脚本和验收清单，见 `prd/milestones/` 下的里程碑文档。两者与本章冲突时，范围边界和安全不变量以本章为准，模块细节以模块文档为准，并应回改到彼此一致。

文档权威约定：跨模块性能与可靠性预算以 `prd/modules/non-functional-requirements.md` 的 `NFR-*` 为唯一来源；API 约定、数据 schema 与迁移以 `prd/modules/api-and-data.md` 为唯一来源；团队角色与安全要求以 `prd/modules/security-and-permissions.md` 为唯一来源。本章只定义范围、顺序与发布门禁，不再复制或另立数值、schema 与角色词表。

文中使用统一的状态标记区分仓库事实与计划：

- 【已实现 M0】表示当前仓库代码中已经存在、可以运行的行为。
- 【部分实现 M0】表示已有代码骨架，但缺少关键能力，不能作为完整功能对外描述。
- 【计划中 M1】至【计划中 M4】表示尚未实现，只是路线图承诺。
- 【非目标】表示明确不做，或只在满足重新评估条件后才考虑。

事实基线为 2026-11-17 的仓库代码。M0 的当前状态以代码和可运行结果为准，M1-M4 均为计划，不得写成已实现能力。M0 已在本地执行过构建、Go 测试、`go vet`、TypeScript 类型检查和浏览器主路径验收：`make build` 通过；`internal/store` 的测试通过，其余 Go 包当前没有测试文件；`pnpm -r typecheck` 通过；桌面壳仅验证编译，GUI 未在无头环境启动（D-M0-02）。M0 里程碑文档的正式结论是“骨架完成、有条件通过”，S1 缺陷 D-M0-01（排队中 Run 取消后仍可能被执行）尚未关闭。这个事实会在 M0 基线与发布标准两节中被引用。

## 1. 目的与范围

### 1.1 本章目的

本章的目的不是描述单个功能怎么做，而是建立四条产品治理基线：

1. 范围基线：明确 ATeam 的能力边界，防止在早期把项目管理、模型托管、云服务、即时通讯等不相干能力混入核心闭环。
2. 交付基线：把 M0-M4 拆成可验收的里程碑，每个里程碑都有目标用户结果、范围、交付物和退出标准，避免“做了一半就算完成”。
3. 发布基线：定义功能、质量、性能、安全、文档和演示六类发布标准，任何里程碑发布都必须同时满足，不能只凭功能演示通过。
4. 变更基线：定义什么情况下可以调整范围、由谁决策、需要留下什么记录，防止范围在实现过程中无声膨胀。

### 1.2 本章范围

本章覆盖以下内容：

- 产品级范围边界与初期非目标。
- 目标角色、典型场景和用户故事。
- M0-M4 的里程碑总览、目标用户结果、范围、交付物和退出标准。
- 里程碑之间的依赖关系、排序理由和硬依赖规则。
- 发布标准，包括功能、质量、性能、安全、文档和演示脚本。
- 范围变更管理，包括变更类型、流程、决策权限和规则。
- 风险调整后的路线图，包括可能延期的部分、降级顺序和不可削减的底线。
- 数据与 API 的跨里程碑演进约定。
- 异常与边界、权限与安全、指标、依赖与风险、里程碑映射。

### 1.3 不在本章范围

以下内容不在本章展开：

- 各模块的字段级数据字典、完整 API schema、组件级交互稿和算法细节，属于 `prd/modules/`。
- 单个里程碑内的任务拆分、人员分工和具体排期，属于 `prd/milestones/`。
- 第三方 Runtime（Claude Code、Codex）的内部实现和协议细节，ATeam 只定义适配边界。
- 商业定价、托管服务和模型计费，ATeam 当前是开源、本地优先、BYO Runtime/Key 的产品。
- 具体日历日期。本章只定义顺序、依赖和退出标准；具体排期由里程碑文档维护，不在此处承诺日期。

### 1.4 状态标记与事实判定

状态判定遵循以下规则：

| 标记 | 含义 | 判定依据 |
|---|---|---|
| 【已实现 M0】 | 当前代码可运行，行为与描述一致 | 代码存在，且至少通过现有测试或可重复的手工验证 |
| 【部分实现 M0】 | 有接口或字段，但缺少关键闭环 | 代码存在，但缺少执行、校验、持久化或 UI 中的至少一项 |
| 【计划中 M1-M4】 | 尚未实现 | 仓库中没有对应实现，不能用于对外演示或承诺 |
| 【非目标】 | 明确不做 | 本章 2.4 节列出原因和重新评估条件 |

需要特别说明：M0 的“已完成骨架”只代表核心对象、API、SQLite、Mock Runtime、Vue 看板和 Wails 桌面壳可以跑通，不代表 ATeam 已经具备可用的多 Agent 开发闭环。真正的本地闭环从 M1 开始。

## 2. 产品范围边界

### 2.1 产品定位与核心问题

ATeam 是一个本地优先、开源的多 Agent 开发驾驶舱。它不替代 Claude Code 或 Codex，也不托管模型或转售模型调用；它解决的是单个开发者已经能用编码 Agent 之后出现的新问题：多 Agent 开发缺少协作层。

核心问题可以拆成五个：

1. 上下文交接：任务描述、角色约束、前序交付物如何可靠地传给下一个 Agent，而不是靠复制粘贴和口头约定。
2. 工作区隔离：多个 Agent 同时改代码时，如何避免互相覆盖、互相污染，如何保证每个改动都可回滚、可比较。
3. 可观测性：Agent 在做什么、卡在哪里、产出了什么，如何实时看到并事后追溯。
4. 评审与治理：Agent 的产出如何被人类审查，哪些动作必须人工批准，如何留下证据。
5. 可复用性：一次成功的角色配置如何沉淀为可复用的 Agent、模板和技能，而不是每次重新写提示词。

目标用户有三类：

1. 独立开发者：同时跑 3-5 个 Agent，希望提高吞吐，但不希望把代码交给云端。
2. 2-10 人小团队：共享任务、Agent 和机器，希望有基本的登录、权限、审计和远程执行能力。
3. 角色化 Agent：UI Design、Frontend、Backend、DevOps 等角色，通过任务 DAG 和交付物契约协作，而不是在同一个会话里自由聊天。

### 2.2 核心闭环

ATeam 的核心闭环是：

Task（上下文容器）→ Agent（可复用工作配置）→ Run（一次执行）→ Run Workspace（隔离工作区）→ Runtime（Claude Code、Codex 或 mock）→ Artifact（diff、测试、摘要；M1 可选 screenshot，M2 起截图作为 UI 类 DoD 必需）→ Human Review（人工评审）→ Merge（合并）。

| 概念 | 定义 | 生命周期 | 当前状态 |
|---|---|---|---|
| Task | 上下文容器，承载标题、描述、状态、优先级、指派人、标签和父任务 | 创建、编辑、进入可执行状态、评审、完成或取消 | 【已实现 M0】CRUD 与状态字段已存在 |
| Agent | 可复用的工作配置，包含指令、Runtime、模型、并发、超时、允许路径和允许命令 | 创建、编辑、被 Run 引用、停用 | 【已实现 M0】CRUD 已存在；权限字段尚未强制执行 |
| Run | 一次执行记录，绑定一个 Task 和一个 Agent，包含状态、日志、摘要、错误、分支和工作区 | 排队、准备、运行、完成、失败、取消 | 【已实现 M0】基础状态机与 Mock/最小 Claude 适配已存在 |
| Run Workspace | 隔离工作区，M1 起为 git worktree 和独立分支 | 创建、准备、运行、清理 | 【部分实现 M0】当前只是每次 Run 一个目录，不是 worktree |
| Runtime | 执行编码 Agent 的适配层，支持 Claude Code、Codex 和 mock | 被 Agent 选择、被 Run 调用、产生事件 | 【部分实现 M0】mock 完整，claude 适配最小化 |
| Artifact/Evidence | Agent 产出物与验证证据，如 diff、测试输出、摘要；Evidence 实体自 M2 起，截图证据 M1 可选、M2 起为 UI 类 DoD 必需 | 随 Run 产生、被评审引用、被保留或清理 | 【计划中 M1】当前没有数据表与 API；M1 交付 diff、测试与摘要，可选 screenshot Artifact，不建 Evidence 表 |
| Human Review | 人工查看 diff 和证据，决定通过或驳回 | 评审中、通过、驳回 | 【计划中 M1】当前只能看日志，不能评审 diff |
| Merge | 人工批准后把 Run 分支合并回目标分支 | 待合并、合并中、已合并、冲突 | 【计划中 M1】当前没有合并能力 |

### 2.4 范围外与初期非目标

以下内容在初期明确不做。非目标不是“永远不做”，而是“当前阶段不做”，每一条都给出原因和重新评估条件，避免在实现过程中被临时需求拖入。

| 非目标 | 具体含义 | 原因 | 重新评估条件 |
|---|---|---|---|
| 完整项目管理套件克隆 | 不做 Sprint、史诗、故事点、自定义工作流、复杂报表 | Task 的职责是 Agent 执行上下文，不是项目管理套件；过早引入会稀释核心闭环 | 出现 10 人以上团队持续要求 Sprint 规划，且现有看板无法满足 |
| 20+ 集成 | 初期只做 Claude Code、Codex、GitHub、本地通知和通用 Webhook，不做大量 SaaS 集成 | 每个集成都有认证、版本和运维成本；本地优先产品应保持适配面可控 | 适配器接口稳定，且有真实用户证据表明某一集成是阻塞性需求 |
| IM 机器人 | 不做面向第三方即时通讯平台的机器人 | 通知需求可由桌面通知和通用 Webhook 满足；机器人的身份与权限模型复杂 | M4 通知稳定后，团队用户明确提出 IM 审批或通知需求 |
| 技能市场 | 只做本地技能包，不做市场、评分、付费、审核 | 市场涉及供给质量、安全审核和交易，超出当前产品阶段 | M2 技能包被外部用户实际共享，且出现托管需求 |
| 移动端 | 不做手机 App | 编码工作依赖本地文件系统和 Runtime，手机无法执行；只做查看也会分散资源 | 出现只读审批或查看的伴随需求，且可独立立项 |
| 多租户 SaaS | 不提供托管云、组织计费、共享云数据库 | 与本地优先、代码不出本机的定位冲突；运营和安全负担高 | 有明确的私有化部署或企业需求，并愿意承担独立产品线成本 |
| 模型托管与转售 | 不代理模型调用、不转售 API Key、不按 token 计费 | 产品坚持 BYO Runtime/Key；模型托管会改变成本结构和法律责任 | 不纳入当前产品方向，只可能作为独立产品评估 |
| 多 Agent 自由聊天 | 不允许多个 Agent 在同一会话里自由对话并直接改代码 | 上下文不可控、产出不可评审、责任不可追溯；ATeam 用 DAG、契约和证据替代 | 不重新评估，这是产品设计不变量 |
| 自动合并与自动部署 | 不允许 Agent 自动合并、推送、部署或删除高风险资源 | 高风险动作必须有人类审批；这是治理底线 | 不重新评估，这是安全不变量 |
| 浏览器 IDE | 不内置代码编辑器，不替代本地 IDE | ATeam 是驾驶舱，不是 IDE；diff 评审足够时无需编辑器 | M2 后若证据表明 diff 评审不足，再评估只读或轻量编辑 |
| 云代码存储 | 不上传工作区源码，不做云端代码托管；M3 的源码证据回传必须项目级显式 opt-in 并逐次审批 | 本地优先、代码不出本机是核心卖点与信任基础 | 不重新评估，这是产品定位 |
| M1 阶段跨平台打包 | M1 不做 DMG、NSIS、AppImage | M1 应聚焦本地闭环；打包在 M4 统一做，避免 schema 频繁变化时维护安装器 | 按 M4 计划执行，不提前 |

需要区分“非目标”和“延后”：上表中“M1 阶段跨平台打包”属于延后，不是永久不做；其余多数是方向性非目标。延后项必须记录目标里程碑，不能无声消失。

### 2.5 范围守卫规则

为了让“做什么、不做什么”可执行，以下规则作为范围守卫需求。每条都可测试、可评审。

| ID | 规则 | 验收方式 |
|---|---|---|
| SCOPE-001 | 原创实现与 clean-room。不得引入任何第三方产品的代码、文档、截图、图标、文案或商标；贡献必须使用 DCO 并经过 clean-room 检查 | 仓库扫描、贡献者声明、LICENSE 与 NOTICE 检查、代码评审清单 |
| SCOPE-002 | 本地优先。M1 起，任务管理、工作区准备、diff、证据、评审和合并不依赖 ATeam 云端；只有 Runtime 访问模型时可能需要网络 | 断网环境下执行核心闭环，除模型调用外全部可用 |
| SCOPE-003 | BYO Runtime/Key。ATeam 不代理模型推理，不明文存储模型凭证，不转售模型调用 | 配置评审、密钥扫描、日志检查 |
| SCOPE-004 | 每次 Run 必须绑定唯一的 Task、Agent、Workspace 和 Runtime，不允许存在无主 Run | 数据库约束与 API 集成测试 |
| SCOPE-005 | 合并、推送、部署、删除等高风险动作必须有人工审批记录，Agent 不能自我批准 | 审批记录测试与越权测试 |
| SCOPE-006 | 完成必须证据化。代码变更类 Run 进入可评审或可合并状态前，必须满足该 Agent 或任务契约要求的证据；mock 或非代码变更 Run 只提供日志、摘要和明确标识，不得计入代码变更类任务的完成证据 | 状态机测试、契约校验测试与 mock 证据隔离测试 |
| SCOPE-007 | 角色 Agent 协作必须通过任务 DAG、交付物契约、审批门和证据化 DoD，不允许共享自由聊天上下文 | M2 设计评审、数据模型评审、演示脚本 |
| SCOPE-008 | 任何新功能必须映射到某个里程碑和退出标准；没有映射的功能不得进入主线 | 需求评审、PR 模板、路线图检查 |
| SCOPE-009 | 非目标不能被“顺手实现”。如需实现，必须走范围变更流程并更新本章 | 变更记录与发布评审 |
| SCOPE-010 | 数据默认留在本机。M3 远程模式默认只传输元数据、事件、日志、测试或构建结果摘要与证据哈希；diff、截图等含源码内容的证据默认留在 Runner 本机，只有项目级显式开启回传并逐次审批后才允许上传 | 架构评审、网络抓包验证、配置与审批记录检查 |
| SCOPE-011 | M0 只接受缺陷修复和 M1 前置能力，不在此基线上叠加新模块 | 分支与发布检查 |
| SCOPE-012 | 每个里程碑的范围冻结后，新增需求只能替换等量范围，不能只加不减 | 变更提案中的范围预算表 |
| SCOPE-013 | 未知 Runtime 必须显式失败，不得静默回退到 mock；配置错误不能表现为“运行成功但没有改动” | Runtime 校验测试、Run 失败码断言与 UI 错误提示检查 |

## 3. 角色与场景

### 3.1 角色定义

| 角色 | 类型 | 主要目标 | 首次可用 | 权限边界 |
|---|---|---|---|---|

### 3.2 典型场景

场景 A：单任务单 Agent（M0 可演示，M1 才有真实闭环）。开发者创建一个 Workspace 绑定本地仓库，再创建一个 Task，选择一个 Agent，触发 Run。M0 中 Run 使用 Mock Runtime 或最小 Claude 适配，产出日志和摘要；M1 中 Run 在独立 worktree 中执行，产出 diff 和测试证据，开发者评审后合并。

场景 B：并行三任务（M2.1）。开发者同时启动三个 Task，分别交给三个 Agent。验收时通过 `-concurrency` 将全局 worker 调到至少 3；每个 Run 有独立工作区，事件流互不干扰；调度器遵守全局并发和单 Agent 并发限制；看板显示每个 Run 的状态。M1 只验收两个代码变更类 Run 的工作区隔离，不要求单 Agent 并发限制，也不要求三路并行成为默认行为。

场景 C：设计到前端交接（M2.1）。UI Design Agent 产出设计规范和组件契约，作为 Artifact 和 Evidence 附加到任务；Frontend 任务依赖该交付物，未满足契约前不能进入运行；满足后自动解除阻塞，Frontend Agent 按契约实现并产出截图和构建结果；评审者检查证据后批准。

场景 D：团队远程执行（M3）。团队成员登录后看到共享任务和 Agent；任务被分配到某台已注册机器上的 Runner；Runner 在本机准备 worktree、执行 Runtime、回传元数据、事件、日志与测试摘要，diff 与截图默认留在 Runner 本机；只有项目级显式开启回传并逐次审批后，含源码内容的证据才进入控制面；管理员可在审计日志中查看审批和合并记录。

场景 E：定时巡检与 Webhook（M4）。用户配置每周一执行的定时任务，或用带 HMAC 的 Webhook 触发一次运行；运行完成后发送本地通知；高风险动作仍然需要人工审批。

### 3.3 用户故事

以下用户故事使用 Given/When/Then 描述，并标注所属里程碑。它们是本章验收和演示脚本的上层依据。

US-001 独立开发者完成真实任务（M1）

Given 开发者有一个本地 git 仓库和一个明确的任务描述，When 他创建一个 Workspace 绑定该仓库、创建一个 Agent 并选择 Claude Code Runtime，启动 Run，Then ATeam 在独立 worktree 中执行任务，实时显示结构化日志，结束后展示 diff、测试结果和摘要，开发者可以在确认后合并。

US-002 取消与超时（M1）

Given 一个 Run 正在执行或仍在队列中，When 开发者点击取消，或运行超过 Agent 配置的超时时间，Then ATeam 对排队中的 Run 保证不再执行；对运行中的 Run 先请求优雅终止，5 秒内停止产生新事件，10 秒宽限后强制终止进程组，把 Run 标记为 cancelled 或因超时失败，并在 UI 中给出可理解的原因。

US-003 证据化评审（M1）

Given 一个 Run 已完成并产生 diff，When 评审者打开任务详情，Then 他可以看到变更文件、diff、测试命令与结果、Agent 摘要；当证据不完整时，合并按钮不可用；当他确认合并时，系统记录评审人、目标分支、head SHA、证据快照和时间。

US-004 角色交付物交接（M2）

Given 一个功能任务被拆成 UI Design、Frontend、Backend、DevOps 四个子任务，When UI Design 完成设计规范和组件契约并通过验收，Then 依赖它的 Frontend 任务自动解除阻塞；Frontend Agent 只能看到契约和相关证据，不需要读取 UI Design 的完整对话；Frontend 完成后产出构建结果和截图作为证据。

US-005 高风险动作审批（M1 合并，M2 扩展）

Given 一个 Run 准备合并、推送、部署或删除资源，When 该动作属于高风险动作，Then ATeam 必须展示目标、分支、SHA、环境或资源范围，要求人类显式确认，并写入不可静默篡改的审批记录；Agent 不能替人类确认。M2 的推送只登记审批意图，不执行远程 push；远程 push 与 PR 属 M3。

US-006 团队共享与审计（M3）

Given 一个 2-10 人团队有两台机器，When 成员 A 把自己的机器注册为 Runner，成员 B 启动一个任务并指定该 Runner，Then 任务在成员 A 的机器上执行，成员 B 可以查看元数据、事件、日志与证据摘要；管理员可以查看谁在何时注册机器、谁批准了合并。

US-007 里程碑演示（M0-M4）

Given 一个干净的开发环境，When 评审者按里程碑演示脚本执行步骤，Then 不需要手工修改数据库，不需要隐藏命令，所有预期结果都能复现；如果任一步失败，该里程碑不能发布。

US-008 范围变更（全程）

Given 一个新增需求或范围调整请求，When 提出者提交变更提案，Then 提案必须包含用户问题、证据、替代方案、对退出标准的影响、成本和风险；决策后更新本章、里程碑文档和变更记录，不能只改代码不改文档。

US-009 配置快照与重启对账（M1）

Given 一个 Run 启动后又修改了 Agent 配置，或服务在 Run 运行期间重启，When 用户查看历史 Run 或重新启动服务，Then 历史 Run 展示启动时的 Agent 配置快照；非终态 Run 被明确标记为中断并保留现场，不出现永久 queued 或永久 running。

### 4.2 M0：骨架

#### 4.2.1 目标用户结果

M0 的目标是验证产品骨架和核心闭环的形状，而不是交付可用的多 Agent 开发体验。在主路径与手工 GUI 验收完成后，开发者应当能够在本机启动 ATeam，创建 Task 和 Agent，触发一次 Mock 运行或最小 Claude CLI 运行，并在 Vue 看板和 Run 日志中看到状态与事件。

#### 4.2.2 当前已实现

以下能力在当前仓库中已经存在：

- 领域模型：Task、Agent、Run、RunEvent；Task 状态包括 backlog、todo、in_progress、in_review、done、blocked、cancelled；Run 状态包括 queued、preparing、running、completed、failed、cancelled；AssigneeType 包括 human、agent、crew。当前没有 Workspace 实体，数据实际属于一个隐式默认 Workspace。
- SQLite 存储：嵌入式 migration、schema_migrations 表、WAL、busy_timeout、外键开关；tasks、agents、runs、run_events 四张表及索引。
- REST API：健康检查、Task CRUD、Agent CRUD、按任务列出 Run、创建 Run、Run 列表与详情、RunEvent 列表、Run 取消。多数业务错误返回 JSON `{ "error": "..." }`；未知 `/api` 路径当前由 `http.NotFound` 返回文本 404，方法不匹配也不是 JSON（见 4.2.3 #19）。
- WebSocket：`/api/ws` 广播 task、agent、run 事件；前端收到事件后重新拉取列表。
- 调度器：进程内队列、可配置 worker 数（默认 2）、按 Agent 超时时间设置上下文超时、取消表；Run 状态从 queued 到 preparing、running、completed、failed 或 cancelled。MaxConcurrency 只存储，不参与调度。
- Runtime：mock 适配器按四步模拟执行；claude 适配器调用本地 `claude -p`，逐行读取 stdout 和 stderr，未做 stream-json 解析、模型选择和权限参数；未知 Runtime 会静默回退 mock。
- Workspace：每次 Run 在数据目录下创建一个以 Run ID 命名的普通目录，默认位于 `~/.ateam/workspaces/runs` 下；尚未使用 git worktree，Run 的 branch 字段不会被填充。
- Vue 看板：Board 五列（Backlog、Todo、In Progress、In Review、Done）、任务详情、Run 日志 1.5 秒轮询、Agent 列表与创建、Run 列表、设置页健康检查；blocked 与 cancelled 任务不在看板中显示。
- 桌面壳：Wails v3 在本机随机端口启动 Go 服务并加载页面；当前验证到编译通过，GUI 未在无头环境启动（D-M0-02）；未做打包。
- 工程与 CI：Go 1.27、Vue 3、TypeScript、Vite、Pinia、Tailwind CSS、Element Plus、AI Elements Vue、pnpm monorepo；CI 在 Ubuntu 上运行 Go 测试与 vet、pnpm 安装、类型检查和 Web 构建，不构建桌面壳。

#### 4.2.3 M0 已知缺口

以下缺口必须在路线图中被明确承认，不能把 M0 当作完整产品：

1. 没有 git worktree 和分支隔离，WorkspaceMode 字段只是存储，不生效；每个 Run 只是普通目录，branch 为空。
2. 没有 Diff 评审、Artifact/Evidence、审批和合并。Run 完成后只能看日志和摘要，不能判断改了什么。
3. 取消队列中的 Run 不可靠。取消接口会把数据库中的 Run 标记为 cancelled，但调度器执行前不检查 Run 是否已取消，已排队的 Run 仍可能开始执行并覆盖状态（D-M0-01，S1）。
4. 运行中的取消依赖 Go context，能终止直接子进程，但不保证杀掉整个进程组；Claude CLI 派生的子进程可能残留。
5. CORS 反射任意 Origin，WebSocket 的 CheckOrigin 始终返回 true。默认只绑定 127.0.0.1，但通过 `--addr` 暴露到局域网时没有认证保护。
6. Agent 的 AllowedPaths、AllowedCommands 只存储不强制执行；MaxConcurrency 只存储，调度器只有全局并发限制。
7. 未知 Runtime 会静默回退到 mock（`internal/runtime/runtime.go` 的 `Registry.Get`）。Agent 配置写错时会表现为“运行成功但没有改动”，这是比多数缺口更影响产品可信度的缺陷，M1 必须改为显式失败。
8. Run 不保存 Agent 配置快照。Run 结束后修改 Agent 的 instructions、模型或超时，会让历史 Run 无法解释当时使用了什么配置。
9. 没有启动对账与崩溃恢复。进程退出时 preparing/running 的 Run 会悬挂，queued Run 不会恢复，重启后可能出现永久 running 或永久 queued。
10. Task 的 parentId 只是字段，没有依赖语义；AssigneeType 的 crew 只是枚举值，没有 Crew 实体。
11. 删除 Task 或 Agent 不会阻止活跃 Run，也不会级联取消，可能留下孤立 Run。
12. 列表接口没有分页和过滤，任务或 Run 数量增大后会一次性返回全部数据。
13. WebSocket 没有事件重放和断线续传，断线期间的事件会丢失，前端只能全量刷新。
14. Claude 适配器非常最小：没有模型选择、权限模式、stream-json、工具事件映射、错误分类和重试策略。
15. 没有登录、权限、审计、Postgres、远程 Runner、GitHub PR。
16. 测试稀疏：只有 `internal/store` 有测试；API、调度器、Runtime、Workspace 没有测试；前端没有单元测试或 E2E；CI 不构建桌面壳。
17. UI 文案目前全部为英文，仓库中没有中文界面文案，也没有 i18n 框架。产品文档使用简体中文；是否在后续版本支持中文界面，以及 M4 文档提供哪些语言，属于待决策的产品问题，不是“中英文混用”缺陷。
18. Board 只渲染五个状态列（Backlog、Todo、In Progress、In Review、Done）；blocked 与 cancelled 任务在看板中不可见；TaskView 的状态下拉也只有五个选项，UI 无法把任务设置为 blocked 或 cancelled。
19. 并非所有错误都返回 JSON：未知 `/api` 路径由 `http.NotFound` 返回文本 404，方法不匹配也不是 JSON。4.2.2 与 M0 验收不能把“错误统一为 JSON”写成全部成立。
20. README 当前只写 M0 scaffold 与路线图，没有逐项列出本节的已知缺口和 S1/S2 状态；README 的 M2 路线图仍写成“multiple agents in parallel, skills, inbox, task templates”，与本章的 M2.1/M2.2 与角色 Agent 协作口径不一致。README 同步是 M0 关闭与 M1 启动前的文档动作。

#### 4.2.4 M0 回溯验收标准

M0 作为骨架验收，需要满足：

1. `make dev-server` 可以启动 API，`/api/health` 返回正常。
2. `make dev-web` 可以启动 Vue 开发服务器，Board、Task、Agents、Runs、Settings 页面可访问；Settings 在 M0 验收中只完成路由与代码验证，未做浏览器交互验收。
3. 可以创建、读取、更新、删除 Task 和 Agent；数据在重启后仍然存在。
4. 可以创建一个 Run，Mock Runtime 产生四步日志和 summary，前端能看到状态变化。
5. `make test` 中现有 Go 测试通过（当前只有 `internal/store` 有测试），`pnpm -r typecheck` 通过。
6. Wails 桌面壳编译通过；窗口能否加载同一套 UI 仍需在非无头环境手工验收（D-M0-02），不能写成已满足。
7. 4.2.3 的已知缺口已完整登记在本章；`prd/milestones/M0-scaffold.md` 登记了其中影响里程碑结论的缺陷（D-M0-01、D-M0-02、D-M0-03、D-M0-04、D-M0-05、D-M0-08 等），不是全部缺口清单。README 尚未逐项列出这些缺口，README 同步列为 M0 关闭动作。在 README 完成同步前，只能表述为“缺口已在 PRD 登记，关键缺陷在 M0 文档登记”，不能表述为“README 已标注”。

M0 的正式结论是：骨架完成、有条件通过。D-M0-01（S1，排队取消）已复现并有 M1 首迭代修复计划；D-M0-03（测试稀疏）、D-M0-04（Claude 适配未端到端）、D-M0-05（workspaceMode 未生效）、D-M0-08（CORS/WS Origin）等缺口尚未关闭。M0 不对外发布为可用版本。M1 必须先补齐 Workspace 绑定、工作区隔离、真实 Runtime、证据、评审和合并，才构成第一个可用的本地闭环。

文档同步欠账：README 的路线图仍按旧口径描述 M2，且未列出 M0 已知缺口与“有条件通过”结论。M0 关闭、M1 启动前必须完成 README 同步，不能只改本章。

### 4.3 M1：本地闭环

#### 4.3.1 目标用户结果

完成 M1 后，独立开发者可以把一个真实任务交给 Claude Code，在隔离的 git worktree 中执行，实时看到结构化日志，运行结束后查看 diff 和测试证据，决定合并或驳回；整个过程代码不离开本机，高风险动作由人确认。

#### 4.3.2 范围

M1 的范围包括：

- Workspace 与仓库绑定：Workspace 记录本地仓库绝对路径、remote、默认 base branch、验证命令、worktree 根目录和受保护分支；创建时校验路径存在、非 bare 且为 git 工作树根；一个 Workspace 对应一个本地仓库，不支持自动 clone；Task 归属 Workspace，Run 继承 Task 的 Workspace。仓库路径、base branch、验证命令和 worktree 根目录是 M1 的必要输入，不能由系统猜测。
- 工作区隔离：为代码变更类 Run 创建 worktree 和独立分支，记录 Workspace 的 base branch、base commit、head commit 和工作区路径；同一仓库的 fetch、worktree 增删、分支创建和合并串行化；合并或放弃后按策略清理 worktree 和分支，未合并改动不得自动删除。
- 真实 Claude Code 适配：命令模板、模型参数、权限模式、工作目录、环境变量白名单、stream-json 或等价流式输出、stdout 与 stderr 映射、工具调用事件、文件变更事件、测试结果事件、错误分类、进程组终止；启动前探测 CLI 版本与可用性，未知 Runtime 必须显式失败，不得回退 mock。
- Run 生命周期与配置快照：queued、preparing、running 三阶段的取消语义；超时映射为结构化失败码；启动时保存 Agent 配置快照（Runtime、模型、工作区模式、超时、权限模式、允许路径与命令、提示词哈希、Runtime 版本）；服务重启时对账非终态 Run。
- Artifact/Evidence：M1 交付 Artifact（diff、变更文件列表、测试命令与结果、命令日志、用量、摘要；可选 screenshot），与 Run 绑定，支持校验和、大小限制、脱敏和保留策略；支持单 Task 证据清单与 diff 的本地导出，导出内容经过脱敏。M1 不建 Evidence 表，DoD 基于 Artifact 与人工例外；Evidence 从 M2 起交付，截图在 M2 起作为 UI 类 DoD 必需项。单个文本证据默认上限 10 MB，单个 Artifact 默认上限 50 MiB，具体以 `prd/modules/runtime-and-workspace.md` 为准。
- 评审与合并：Review 记录（approve 或 request changes、评审人、时间、意见、证据快照哈希）、diff 查看器、文件级变更统计、人工确认合并、合并记录、冲突提示与审批失效。M1 只做本地 merge，不执行远程 push。
- 取消与超时：队列中取消、preparing 阶段取消、运行中取消；运行中取消先请求优雅终止，5 秒内停止产生新事件，10 秒宽限后强制终止整个进程组；超时使用 errorCode 表达，不新增状态。
- 本地安全基线：默认只绑定 127.0.0.1；CORS 允许列表；WebSocket Origin 与 Host 校验；凭证不落库、不写日志；工作区路径边界与符号链接逃逸防护。
- 状态机加固：终态不可被后续事件覆盖；取消后不得被调度器回写为 running 或 completed；同一 Task 同一时间最多一个活动 Run；删除带活跃 Run 的 Task 或 Agent 被阻止并给出提示，Run 与 Task 的关联删除规则明确。
- API 与数据：引入 `/api/v1` 增量接口与 Workspace、Artifact、Review、Merge 资源；M0 的 `/api` 路径保留为永久兼容别名；新增 workspaces、agent_versions、artifacts、reviews、merge_records、run_config_snapshots 表与 Run 扩展字段。
- UI：任务详情增加 Runs、Diff、Evidence、Review 区域；独立 Run 详情；合并对话框展示目标分支、head SHA、证据摘要与风险提示；错误状态可操作；空状态、加载失败与断线有明确文案。
- 测试与文档：Workspace、Scheduler、API、Runtime 适配的关键路径测试；至少一个端到端 smoke；README 与 M1 演示脚本更新。

本章把 Run 分为两类：代码变更类 Run 指 Runtime 在 worktree 中执行并可能修改仓库的 Run；mock Run 或用户显式标记的非代码 Run 不创建 worktree，只要求日志、摘要和明确标识，且不得计入代码变更类任务的完成证据。

#### 4.3.3 明确不包含

M1 不包含：任务依赖 DAG、交付物契约、角色模板、路径与命令权限强制执行、审批门扩展、收件箱、技能、任务模板、Crew、Postgres、登录、远程 Runner、GitHub PR、定时任务、Webhook、打包、自动更新、插件和遥测。Evidence 实体、Codex adapter、direct 运行模式、远程 push 也不属于 M1；M1 可选 screenshot Artifact（仅查看，不作为 DoD 必需），Evidence、截图 DoD 与 Codex 可在 M2 进入，push 与 PR 属于 M3。M1 必须完成 Claude Code 的真实闭环，Codex 不作为 M1 退出条件。

#### 4.3.4 交付物

| 交付物 | 说明 | 验收方式 |
|---|---|---|
| Workspace 与仓库绑定 | 本地仓库路径、remote、base branch、验证命令、worktree 根目录；Task 归属 Workspace | 创建 Workspace 时路径与分支校验通过；Task 与 Run 可追溯到 Workspace |

#### 4.3.5 M1 退出标准

M1 只有同时满足以下条件，并满足本章第 6 节中适用于 M1 的发布门禁，才算完成：

1. 干净环境按 README 完成依赖安装，启动服务和 Web UI；创建 Workspace、Task 和 Agent，Workspace 绑定本地 git 仓库的绝对路径、base branch、验证命令和 worktree 根目录，Task 归属该 Workspace，选择 Claude Code Runtime 启动 Run，Run 能完成或给出可操作的失败原因。
2. 每个代码变更类 Run 在目标仓库中创建独立 worktree 和唯一分支，Run 记录 base commit、head commit 和 worktree 路径，Workspace 提供 base branch；两个并发代码变更类 Run 不共享工作目录、不互相覆盖文件；mock 或非代码 Run 不创建 worktree，只在列表和详情中显示明确标识。
3. 真实 Claude Code adapter 输出结构化事件（至少包含状态、工具调用、文件变更、测试结果、用量、错误与结束事件），支持模型与权限参数；未知 Runtime、CLI 缺失或认证失败必须显式失败并给出修复建议，不得回退 mock。
4. Run 结束后自动采集 diff、changed files、测试输出、命令日志和用量；代码变更类 Run 至少有一条 Artifact，包含摘要、diff 统计和至少一项检查结果，没有检查命令时必须显式记录“无可用检查”；mock Run 只要求日志和摘要，且不能作为代码变更类任务的完成证据；单 Task 的证据清单与 diff 可以本地导出，导出内容经过脱敏。M1 不要求 screenshot Artifact；若存在则仅作查看材料。
5. 评审者可以 Approve 或 Request changes；决策持久化并绑定证据快照、评审人、时间和意见；Request changes 必须填写原因；Approve 前必须逐项确认证据清单。
6. 合并按钮在证据不完整或未 Approve 时禁用；合并需要人类显式确认，服务端校验 reviewId、expectedHeadCommit、证据完整性、目标分支 head 与 base commit 一致、目标工作区干净；成功后目标分支包含该提交，worktree 被清理；冲突时合并不执行并显示冲突文件。
7. queued、preparing、running 三种阶段的取消都可靠；取消队列中的 Run 后不会开始执行；取消运行中的 Run 后 5 秒内不再产生事件，10 秒宽限后进程组被终止，Run 进入 cancelled 且不会被回写为 running 或 completed。
8. Run 超过 Agent 超时时间后，在 30 秒内被终止，Run 以 failed 结束并带 timeout 错误码，UI 显示超时原因和已保留的证据。
9. Run 启动时保存 Agent 配置快照；修改 Agent 的 instructions、模型或超时后，历史 Run 的配置、事件与评审记录保持不变。
10. 服务重启后，preparing/running 的遗留 Run 被标记为中断并保留现场，queued Run 不会静默消失；系统不出现永久 queued 或永久 running，用户可以手工新建 Run；删除带活跃 Run 的 Task 或 Agent 被阻止并提示，或使排队 Run 以明确错误失败。
11. UI 提供 Task 三栏详情（上下文、执行、评审，含 Runs、Diff、Evidence）、独立 Run 详情（时间线、Logs、Diff、Artifacts）、评审面板与合并对话框；空状态、加载失败、断线和失败建议均有明确文案与下一步动作。
12. 数据库迁移新增 workspaces、agent_versions、artifacts、reviews、merge_records、run_config_snapshots 与 Run 扩展字段，在空库和 M0 库上均可执行；`/api/v1` 可用，`/api` 作为永久兼容别名返回弃用头；`packages/shared` 与 `packages/api-client` 同步更新。
13. 默认监听 127.0.0.1；非本地 Origin 的 CORS 和 WebSocket 连接被拒绝；日志、事件、证据和导出文件中不出现模型凭证或密钥；工作区路径越界与符号链接逃逸被拒绝。
14. `make test`、`go vet`、`go test -race` 通过；核心 Go 包（store、scheduler、workspace、runtime、api）行覆盖率不低于 70%；至少一个端到端 smoke 通过；`pnpm -r typecheck` 和 Web 构建通过；Run 事件从产生到 UI 可见 p95 不超过 1 秒（2 秒为不得突破的产品上限），worktree 准备在常规仓库上不超过 10 秒（不含网络 fetch）；6.3 表中其余适用于 M1 的 NFR-PERF 指标全部达标。
15. M1 演示脚本在干净环境由非作者执行通过，包含至少一次取消或超时失败路径与一次反向演示；本章 6.5 的 REL-D 与 6.6 的 REL-DEMO 中适用于 M1 的项全部满足；README 与相关模块文档已更新；无 P0 或 P1 未关闭缺陷。

以下任一情况出现，M1 不得宣布完成：存在任何不经过人类评审与显式确认的合并路径；两个并行代码变更类 Run 能看到或修改对方的未提交文件；Run completed 但证据缺失时仍可进入评审或合并；取消后的 Run 又被写回 running 或 completed；未知 Runtime 静默回退 mock 并显示成功；mock Run 被计入代码变更类任务的完成证据；文档或 UI 宣称 M1 已具备任务 DAG、交付物契约、审批门、远程 Runner 或团队权限。

### 4.4 M2：角色 Agent 协作

#### 4.4.1 目标用户结果

完成 M2 后，开发者或小团队可以用 UI Design、Frontend、Backend、DevOps 角色 Agent，把一个大任务拆成有依赖的任务 DAG。每个角色按照交付物契约产出 Artifact 和 Evidence，依赖满足后自动解除阻塞，关键节点由人审批。Crew 或队长模式在并行任务稳定后提供，用于同任务的角色编排，而不是让多个 Agent 在同一会话里自由聊天。

#### 4.4.2 阶段拆分

M2 范围较大，拆成两个子阶段：

- M2.1 协作基础：任务依赖 DAG、交付物契约、角色模板、路径与命令权限、审批门、收件箱、并行调度、任务模板、技能。
- M2.2 Crew 与队长：同任务的角色编排、子任务拆分、成员选择、交接、升级和 Crew 视图。

M2.2 不能在 M2.1 的并行调度和权限测试通过前启动。Crew 延后是刻意的：先把“并行任务”做稳，再引入“同任务多角色编排”，避免同时引入调度复杂度和协作复杂度。

M2 的正式核心退出以 M2.1 为准。M2.2 是附加交付：若进度紧张可以后移，但必须在 M3 启动前完成或由产品与工程负责人书面接受缺口，并在路线图记录目标里程碑；M2.1 不得因等待 Crew 而延期。M2 文档 OQ-M2-17 按此口径关闭。

#### 4.4.3 协作模型

角色 Agent 的协作通过四个机制实现：

1. 任务 DAG：任务之间声明依赖关系，例如 Frontend 依赖 UI Design 的交付物，DevOps 依赖 Frontend 和 Backend 的完成。依赖未满足时，下游任务处于 blocked，不能启动 Run。DAG 必须有环检测，拒绝循环依赖。
2. 交付物契约：每个角色模板或任务模板声明必需的交付物类型、验收命令、人工检查项和证据格式。Run 完成不等于任务完成；只有契约满足并产生证据，任务才可进入评审。
3. 审批门：合并、推送、staging 部署、生产部署计划、删除等动作需要人类审批。审批记录绑定目标分支、SHA、环境或资源范围；目标变化后审批失效。M2 的推送只登记审批意图，不执行远程 push；远程 push 与 GitHub PR 属于 M3。
4. 证据化 DoD：任务的完成定义由证据组成，而不是由 Agent 的自我声明组成。证据包括 diff、测试输出、构建结果、截图、部署日志、回滚计划等。

不采用自由聊天：ATeam 不提供多个 Agent 共享的对话房间作为协作原语。角色之间的信息传递必须落到任务、契约和证据上，便于审计、复现和回滚。

#### 4.4.4 角色模板

| 角色 | 典型输入 | 必须产出的交付物 | 允许路径与命令 | 验收证据 |
|---|---|---|---|---|
| UI Design | 产品目标、用户场景、现有设计系统 | 设计规范、组件契约、交互说明、视觉稿或截图 | 只写设计相关路径；默认无部署命令 | 设计规范文件、组件契约、截图、评审记录 |
| Frontend | UI Design 的契约和证据、现有前端代码 | 组件实现、样式、前端测试、构建结果、截图 | 前端目录；允许 typecheck、test、build 等白名单命令 | diff、类型检查、测试、构建结果、截图 |
| Backend | 接口契约、数据模型需求、现有后端代码 | API、数据模型、迁移、后端测试、接口说明 | 后端目录；允许 test、vet、build 等白名单命令 | diff、测试、vet、迁移说明、接口示例 |
| DevOps | 应用配置、环境要求、发布策略 | CI 配置、staging 部署、生产部署计划、回滚计划 | CI 和部署目录；staging 命令白名单；禁止生产凭证 | 配置 diff、staging 日志、部署计划、回滚计划、人工审批 |

#### 4.4.5 审批门

| 动作 | 审批人 | 前置条件 | 记录内容 | 里程碑 |
|---|---|---|---|---|
| 合并 | 人类评审者 | 证据完整、目标分支可合并、无未解决冲突 | 审批人、目标分支、head SHA、证据摘要、时间 | M1 起，M2 扩展 |
| 推送 | 人类评审者或管理员 | 推送由 ATeam 发起、合并已批准、远程仓库已配置 | 审批人、remote、分支、commit SHA；M2 只记录审批，不执行远程 push | M2 记录与审批，M3 执行 |
| staging 部署 | 人类评审者或管理员 | 构建通过、staging 配置存在、部署计划已生成 | 审批人、环境、版本、部署日志、回滚计划 | M2 |
| 生产部署计划 | 人类评审者 | staging 验证完成、回滚计划存在 | 计划内容、目标环境、风险说明 | M2 只生成计划，人工执行 |
| 生产部署执行 | 人类运维人员 | 生产部署计划已批准 | 执行人、时间、版本、结果 | M2 起由人在 ATeam 之外执行，ATeam 记录结果 |
| 删除 Task 或 Agent | M1 本地用户显式确认；M3 团队管理员 | 无活跃 Run 或已完成影响确认 | 删除对象、影响范围、确认人、时间 | M1 本地确认，M3 管理员审批 |
| 删除机器、Workspace 或 Team Workspace | 团队管理员或组织 Owner | 无运行中任务、影响面已确认、必要时二次认证 | 删除对象、影响范围、审批人、时间 | M3 |
| 扩大 Agent 权限或修改命令白名单 | 本地用户或团队管理员 | 展示变更前后差异、影响预览与风险提示 | 变更前后值、审批人、影响范围、时间 | M2 |

DevOps 在 M2 的边界必须写死：只能执行 staging 部署和生成生产部署计划；生产部署必须人工执行。ATeam 不保存生产凭证，不自动执行生产变更。远程 push 与 GitHub PR 属于 M3；M2 的 push 审批只覆盖 ATeam 内发起的推送意图，若用户绕过 ATeam 手工 push，系统不宣称能够拦截。

#### 4.4.6 M2 退出标准

M2.1 退出标准（M2 正式退出的硬门禁）：

1. 可以创建任务依赖；依赖未满足时下游任务不能启动 Run；依赖满足后自动解除阻塞；循环依赖被拒绝并给出明确错误。
2. 可以为一个任务或角色模板声明交付物契约；缺少必需证据的 Run 不能进入可评审状态；UI 显示缺失项。
3. 内置 UI Design、Frontend、Backend、DevOps 四个角色模板，包含指令、允许路径、允许命令和默认证据要求。
4. 路径权限生效：Agent 不能写入允许路径之外的文件；命令权限生效：不在白名单的命令被拒绝并记录；违规使 Run 失败并产生证据。
5. 审批门生效：合并、staging 部署、删除在没有审批时被阻止；推送在 ATeam 内发起时创建审批记录，但 M2 不执行远程 push，外部手工 push 不在系统控制范围；审批记录包含审批人、时间、目标和证据摘要；目标变化后审批失效。
6. DevOps 只能执行 staging 部署和生成生产部署计划；生产执行不能被 ATeam 自动触发；生产凭证不出现在 Run 或证据中。
7. 收件箱汇总待审批、阻塞、交接和失败 Run；处理收件箱项会更新对应任务或 Run 状态。
8. 三个任务由三个 Agent 并行执行时（使用 `-concurrency` 配置至少 3 个全局 worker），全局并发和单 Agent 并发限制都被遵守；工作区互不污染；UI 能区分每个 Run 的状态。
9. 任务模板可以实例化一个预置 DAG；技能包可以附加到 Agent，Run 记录技能版本。
10. 质量、安全、文档和演示标准满足本章第 6 节中适用于 M2.1 的门禁；无 P0 或 P1 未关闭缺陷。

M2.2 附加退出标准（Crew 交付时适用，不阻塞 M2.1 退出）：

1. 队长 Agent 可以把一个父任务拆成子任务 DAG，并为每个子任务选择角色模板和契约。
2. 子任务之间的交接通过 Artifact 和 Evidence 完成，不依赖共享自由聊天；队长只能读取被显式共享的任务上下文、契约和证据引用，不得读取成员 Run 的私有日志、完整提示词或未授权证据；具体授权模型在 M2.2 设计评审中定义并写入模块文档。
3. 队长不能批准合并、推送或部署；所有高风险动作仍需人类审批。
4. Crew 视图展示成员、子任务状态、阻塞原因和证据完整度；成员失败时可以重试或升级给人。
5. Crew 演示脚本可以在干净环境复现；满足本章第 6 节中适用于 M2.2 的门禁；无 P0 或 P1 未关闭缺陷。

若 M2.2 后移，M3 启动前必须完成或由产品与工程负责人书面接受缺口，并把缺口记录到路线图；不得把未完成的 Crew 能力写成 M3 的既有能力。

### 4.5 M3：团队模式

#### 4.5.1 目标用户结果

完成 M3 后，2-10 人团队可以在一台或多台机器上共享 Task、Agent、运行历史和证据；成员有登录和角色权限；远程 Runner 在成员机器上执行，代码仍留在该机器；所有高风险动作有审计记录；可以把完成的运行发布为 GitHub PR。

#### 4.5.2 范围

- 存储：支持 Postgres；单用户仍可使用 SQLite；通过 Store 接口隔离两种实现；提供 SQLite 到 Postgres 的迁移工具和回滚说明。
- 登录与权限：本地账号、密码哈希、会话；角色词表以 `security-and-permissions.md` §4.2 为唯一来源：组织级 Owner、Admin、Member、Viewer；Team Workspace 级 Admin（workspace_admin）、Contributor、Reviewer、Viewer。Maintainer/Developer 是旧称，不再作为角色名；未加入具体 Team Workspace 的组织 Member 不自动获得 Workspace 访问权。API 和 WebSocket 都校验身份和权限。
- Workspace 与 Team Workspace：Workspace 是 M1 引入的仓库绑定实体，M3 起归属一个 Team Workspace；Task、Agent、Run、Artifact 携带 org_id、team_workspace_id 与 workspace_id。成员通过 Team Workspace 角色获得 Workspace 访问权，不引入独立的 project_members 权限表；如果未来需要项目级自定义角色，必须单独走 ADR 与迁移。
- 远程 Runner：`ateam runner` 模式；注册 token、心跳、任务领取、能力标签、工作目录配置、离线和重连处理。
- 机器注册：机器名称、平台、能力、最后在线时间、所属团队；管理员可以启用、停用和移除机器。
- 共享 Agent：团队级 Agent 库、版本、可见性和变更审计。
- 审计：登录、Agent 变更、审批、合并、机器注册、权限变更等事件写入追加式审计日志。
- GitHub PR：连接仓库、从 Run 分支创建 PR、记录 PR 链接和状态；不在 M3 做完整 CI 回传和自动合并。
- 证据分级与回传：控制面默认只接收元数据、事件、日志、测试或构建结果摘要与证据哈希；日志与摘要经过脱敏，不包含完整源代码。diff、截图等含源码内容的证据默认留在 Runner 本机，只有项目级显式开启 `allowSourceEvidenceUpload` 并逐次审批后才回传；未开启时远程评审只展示文件列表、统计与哈希，完整 diff 需在 Runner 本机查看。
- 安全：远程通信加密、token 轮换、最小权限、审计不可通过 UI 删除。

#### 4.5.3 M3 退出标准

1. Postgres 模式通过完整测试套件；SQLite 模式仍可用于单用户；两种实现共享同一套 Store 接口测试。
2. 登录后访问 API 和 WebSocket；未登录请求被拒绝；组织级 Owner/Admin/Member/Viewer 与 Team Workspace 级 workspace_admin/Contributor/Reviewer/Viewer 的权限矩阵有自动化测试；Owner/Admin 的组织能力、workspace_admin 的合并与 staging 审批、Contributor 的运行权限、Reviewer 的评审能力、Viewer 的只读边界均符合 `security-and-permissions.md`；最后一名 Owner 保护生效。
3. 远程 Runner 可以注册、心跳、领取任务并在本机执行；Runner 离线时任务状态可见，不会静默丢失；Runner 只能访问被授权的项目和路径。
4. 源码与 diff 默认不离开 Runner 所在机器；控制面默认只接收元数据、事件、脱敏日志、测试或构建结果摘要与证据哈希；diff、截图等含源码内容的证据只有在项目级显式开启回传并逐次审批后才上传，未开启时远程评审只展示文件列表、统计与哈希；通过网络抓包或架构评审验证默认路径。
5. 团队共享 Agent 有版本和可见性；修改记录进入审计日志。
6. 审计日志覆盖登录、Agent 变更、审批、合并、机器注册和权限变更；记录不可通过 UI 删除或修改。
7. GitHub PR：用户可以授权仓库，Runner 在人工批准后推送分支并创建 PR；Run 详情显示 PR 链接；失败时给出可操作错误；不执行强制推送。
8. SQLite 到 Postgres 的迁移在样例数据上验证通过，迁移前有备份，失败可回滚。
9. 安全评审完成，覆盖认证、授权、Runner 信任边界、密钥管理、速率限制和审计完整性；高危问题关闭。
10. 文档、演示脚本和质量门满足本章第 6 节中适用于 M3 的门禁；无 P0 或 P1 未关闭缺陷。

### 4.6 M4：自动化与分发

#### 4.6.1 目标用户结果

完成 M4 后，stable 通道用户可以安装经过签名与公证的安装包；unsigned 构建只能作为开发或预览版，不得对外分发且禁用自动更新。用户可以配置定时或 Webhook 触发任务，接收通知，使用插件扩展能力，并通过自动更新升级；遥测默认关闭，只有用户显式开启后才采集。

#### 4.6.2 范围

- 自动化：cron 定时触发、Webhook 触发、手动重放；触发默认创建 Task 并进入 Backlog，只有显式设为 `todo` 才排队 Run，立即运行为手动例外；Run 的 `trigger` 固定使用六值枚举（manual/retry/schedule/webhook/dependency/crew），不新增第七值。
- 通知：本地桌面通知；通用 Webhook 通知；不做 IM 机器人。
- 打包：macOS DMG（arm64 与 amd64）、Windows NSIS（x64）、Linux AppImage（x64）与 tar.gz；应用图标、版本信息、安装和卸载体验。
- 签名与自动更新：stable 通道的 macOS 包必须使用 Developer ID 签名、Hardened Runtime、公证与 staple；Windows 包使用 Authenticode 与时间戳；Linux 提供 SHA-256 校验和与可选 GPG；更新清单与安装包均需签名校验，失败回滚。unsigned 构建只能用于开发或预览，必须明确标注且禁用自动更新。
- CI 打包矩阵：macOS、Windows、Linux 各自使用原生 runner 构建、签名与验证；不能只用 Linux 交叉编译产出三平台安装包。
- 插件 API：版本化 manifest、能力声明、通知渠道、证据渲染等扩展点；不提供第三方 Agent Runtime 适配器（Runtime 适配器仍需在核心注册表登记）；插件权限和失败隔离。
- 遥测：默认关闭，显式 opt-in，采集前可预览字段，不含源码、路径、提示词和凭证。
- 文档：用户指南、管理员指南、插件指南、故障排查、发布说明。

#### 4.6.3 M4 退出标准

1. macOS DMG（arm64/amd64）、Windows NSIS（x64）、Linux AppImage（x64）与 tar.gz 可以在各自原生 runner 的 CI 中构建；在干净系统上安装、启动、卸载，无残留阻塞。
2. stable 通道的发布产物必须通过签名与公证验证：macOS `codesign`/`spctl` 通过，Windows Authenticode 签名有效，Linux 校验和匹配；unsigned 构建只能作为开发或预览版，必须明确标注、不得对外分发且禁用自动更新；自动更新只接受签名产物。
3. 自动更新可以从上一个版本升级到当前版本；更新失败时保留旧版本并可回滚。
4. 定时任务按配置时区触发，默认创建 Task 并进入 Backlog，只有任务模板显式设为 `todo` 才排队 Run，记录 `trigger=schedule`；错过触发时的补偿策略明确且可配置。
5. Webhook 使用 HMAC 校验，支持防重放和密钥轮换；无效签名被拒绝并记录；入站 Webhook 默认创建 Task，不直接启动 Run。
6. 通知覆盖待审批、Run 失败、Run 完成；同一事件不重复轰炸；通知可以关闭。
7. 插件 API 有版本号和权限声明；示例插件可运行；插件崩溃不会导致主进程崩溃，错误可见。
8. 遥测默认关闭；开启前展示采集字段；不采集源码、路径、提示词和凭证；用户可随时关闭并删除本地遥测数据。
9. 文档完整覆盖安装、升级、定时、Webhook、通知、插件和故障排查；M4 演示脚本可复现。
10. 质量、安全、性能和打包门满足本章第 6 节中适用于 M4 的门禁；无 P0 或 P1 未关闭缺陷。

## 5. 里程碑依赖与排序理由

### 5.1 依赖关系

| 里程碑 | 前置依赖 | 依赖类型 | 依赖内容 |
|---|---|---|---|
| M1 | M0 | 硬依赖 | 领域模型、SQLite、API、事件流、调度器、Vue 壳和 Wails 壳 |
| M2.1 | M1 | 硬依赖 | worktree、Run 状态机、Artifact（Evidence 从 M2）、Review 与 MergeRecord、合并确认基础 |
| M2.2 | M2.1 | 硬依赖 | 并行调度、权限、契约、审批、收件箱稳定 |
| M3 | M2.1 | 硬依赖 | 权限模型、审批记录、审计事件、角色与团队边界；M2.2 Crew 为软前置，未完成时需书面接受缺口 |
| M4 | M3 | 硬依赖 | 稳定 API、团队与 Runner 语义、数据迁移完成 |
| M4 打包 | M1-M3 | 软依赖 | 打包技术可以更早试验，但正式交付必须等待 schema 和 API 稳定 |

### 5.2 排序理由

1. 先闭环，后协作。M1 先解决工作区隔离、真实 Runtime、证据、评审和合并。没有这些，M2 的角色协作无法验证交付物，也无法保证 Agent 的产出可评审、可回滚。
2. 先并行任务，后 Crew。M2.1 先做任务 DAG 和并行调度，M2.2 再做同任务 Crew。并行调度是共享基础设施，Crew 只是在其上增加编排层；如果先做 Crew，会把调度、权限和协作复杂度绑在一起。
3. 先单机，后团队。M3 的登录、权限、远程 Runner 和审计成本高，必须建立在 M2 稳定的权限模型和审计事件之上。过早做团队模式会让单机语义反复变化。
4. 先稳定，后分发。M4 的打包、自动更新和插件 API 需要稳定的数据模型和 API。如果提前打包，每次 schema 变化都要维护安装器和升级路径，成本高于收益。
5. 风险前置。worktree、Runtime 流式适配和进程控制是技术风险最高的部分，放在 M1 尽早暴露；如果失败，可以调整产品范围，而不是等到团队模式才发现基础不可用。

### 5.3 硬依赖规则

| ID | 规则 | 验收方式 |
|---|---|---|
| MILE-001 | 任何里程碑不得在前一个里程碑退出标准满足前启动；例外必须有书面风险接受并记录在变更日志 | 里程碑启动评审记录 |
| MILE-002 | M1 不得在 M0 的 CORS、WebSocket Origin 和队列取消缺口修复前宣布完成 | 安全测试与取消测试 |
| MILE-003 | M2 不得在 M1 的证据模型和 Review/MergeRecord 稳定并通过测试前启动 | 证据与评审测试报告 |
| MILE-004 | M2.2 不得在 M2.1 的并行调度和权限测试通过前启动 | 并发与权限测试报告 |
| MILE-005 | M3 不得在 M2 的权限模型和审计事件 schema 冻结前启动 | 设计评审与 schema 评审 |
| MILE-006 | M4 不得在 M3 的 API 和数据迁移方案稳定前启动正式打包；打包试验不对外发布 | 发布评审记录 |

## 6. 发布标准

本节定义所有里程碑共用的发布标准。任何里程碑发布都必须同时满足功能、质量、性能、安全、文档和演示六类标准；不能只凭功能演示通过。发布门禁按里程碑逐项生效，不要求 M1 满足 M4 的打包与签名门：

| 门类 | 生效时点 |
|---|---|
| 功能、质量、文档、演示门（REL-F、REL-Q、REL-D、REL-DEMO） | M1 起适用于所有发布 |
| 性能预算（NFR-PERF-*） | M1 起按模块文档中标注的里程碑执行；M1 验收项见 6.3 |
| 安全门（SEC-GATE-*） | M1 起适用本地项；M2、M3、M4 项按表中标注 |
| 打包、签名、自动更新门 | M4 stable 发布 |

M1 退出标准第 14 项必须引用本节中适用于 M1 的门禁；M4 之前不得把未签名安装包作为 stable 发布，也不得启用自动更新。

### 6.3 性能标准

性能预算的唯一权威来源是 `prd/modules/non-functional-requirements.md` 的 `NFR-PERF-*`；worktree 准备、事件、证据体积与取消宽限的具体口径由 `prd/modules/runtime-and-workspace.md` 定义。本章不再另立数值，只摘录 M1 验收必须使用的阈值；若其他章节或里程碑文档出现不同数值，以模块文档为准并回改。

参考机器定义为 8 核 ARM64、16GB 内存、SSD、macOS 14 或以上的开发机，Go 1.27、Node 24；Windows 和 Linux 基线在 M4 补充。

| 权威 ID 或来源 | 指标 | M1 验收阈值 |
|---|---|---|
| NFR-PERF-004 | 列表查询 | 1,000 个 Task 时 p95 不超过 100ms（默认 limit=50）；5,000 个 Task 时单页（limit=50 或 200）p95 不超过 200ms |
| NFR-PERF-005 | Board 首屏可交互时间 | 500 个 Task 时不超过 1.5s |
| NFR-PERF-010 | Run 事件从产生到 UI 可见 | p95 不超过 1s；2s 为不得突破的产品上限 |
| NFR-PERF-012 | WebSocket 断线恢复 | p95 不超过 5s，按 afterSeq 补齐事件 |
| NFR-PERF-017 | RunEvent 查询 | 10 万条事件时，查询最近 1,000 条 p95 不超过 200ms |
| NFR-PERF-001 | 冷启动 | 开发桌面壳不超过 3s；M4 打包应用不超过 5s |
| NFR-PERF-007 | 点击 Run 至 queued | p95 不超过 300ms；有空闲 worker 时 queued 至 running p95 不超过 1.5s |
| `runtime-and-workspace.md` §11.5（M1 目标 10s） | Worktree 准备时间 | 常规仓库不超过 10s（不含网络 fetch）；后续优化到 3s |
| `runtime-and-workspace.md` §10.3 | 证据体积 | 单个文本证据默认不超过 10 MB；单个 Artifact 默认不超过 50 MiB |
| M1 里程碑指标 | 取消收敛 | 运行中取消 p95 不超过 12s 进入 cancelled（5s 停止新事件、10s 优雅宽限、再加收敛余量） |

本章旧稿中的 `NFR-001` 至 `NFR-010` 只是历史别名，已在 `non-functional-requirements.md` §1.5 映射到 `NFR-PERF-*`，不得用于新增需求、测试用例或缺陷跟踪。

性能回归超过权威目标值 20% 时，发布必须暂停；如果确认是合理回归，需要书面接受并在发布说明中标注。

## 7. 范围变更管理

### 7.1 变更类型

| 类型 | 定义 | 示例 | 决策层级 |
|---|---|---|---|
| 纠正 | 修正文档错误、文案错误或实现与既定要求不一致 | 修正错别字、修正 API 示例 | 任一维护者 |
| 澄清 | 不改变行为，只把模糊描述写清楚 | 明确“超时”的错误码 | 模块负责人 |
| 范围调整 | 在当前里程碑内增加、替换或延后等量功能 | 用截图证据替换录屏证据 | 产品与工程负责人 |
| 里程碑重划 | 改变某个退出标准或把能力移动到另一个里程碑 | 把 Crew 从 M2.1 移到 M2.2 | 产品决策人、工程负责人、设计负责人 |
| 方向变更 | 改变非目标、产品定位或安全不变量 | 改变本地优先或审批规则 | 产品决策人与维护者共同决策 |

### 7.2 变更流程

1. 提出：任何人可以提交变更提案，必须包含用户问题、证据、当前行为、期望行为、替代方案、对范围、退出标准、排期、风险和安全的影响。
2. 分类：维护者按 7.1 分类，确定决策层级；分类不清时按更高层级处理。
3. 影响分析：工程负责人评估实现成本、依赖和风险；设计负责人评估体验影响；安全评审者评估权限和合规影响。
4. 决策：按 7.3 的权限做出接受、拒绝或延后决定，并记录理由。
5. 更新文档：同一次变更中更新本章、对应里程碑文档、模块文档和变更日志；不能只改代码。
6. 沟通与验证：在发布说明或变更记录中告知影响；在下一次里程碑评审中验证变更没有破坏退出标准。

### 7.3 决策权限

- 纠正：任一维护者可以决定。
- 澄清：模块负责人可以决定，但涉及安全或范围边界的澄清需要工程负责人确认。
- 范围调整：产品负责人和工程负责人共同决定；必须用等量范围替换，不能只加不减。
- 里程碑重划：产品决策人、工程负责人和设计负责人共同决定；必须书面接受延期或风险。
- 方向变更：产品决策人与维护者共同决定；必须更新本章、README 和对外路线图。
- 涉及安全不变量的变更：必须经过安全评审；不能由单人决定。

允许同一人兼任多个角色，但必须在变更记录中显式署名，不能省略评审环节。

### 7.4 变更规则

| ID | 规则 | 验收方式 |
|---|---|---|
| CHG-001 | 每个变更提案必须关联用户问题和证据，不能只写“想要这个功能” | 提案模板检查 |
| CHG-002 | 新增范围必须在同一里程碑内移除或延后等量范围，保持范围预算平衡 | 范围预算表 |
| CHG-003 | 退出标准只能通过书面决策降低，不能在实践中无声降低 | 变更记录与发布评审 |
| CHG-004 | 安全不变量、人工审批、本地优先和证据化完成不能被范围变更交换掉 | 决策记录检查 |
| CHG-005 | 里程碑进入代码冻结后，只接受 P0 修复和已批准变更 | 冻结期记录 |
| CHG-006 | 延后项必须记录目标里程碑、负责人和重新评估条件 | 路线图 backlog |
| CHG-007 | 变更必须同时更新 PRD、里程碑文档和发布说明 | 文档 diff 检查 |
| CHG-008 | 每个里程碑发布后 5 个工作日内完成一次范围复盘，记录偏差和原因 | 复盘记录 |

### 7.5 变更触发条件与阈值

以下任一信号出现时，必须启动变更提案，不能只改代码、口头调整或静默降级：

1. 里程碑按计划工期达到 50% 时，仍有任一 P0 退出标准未开始，或 30% 以上退出标准未开始。
2. 风险登记表中的延期信号被触发，例如 worktree spike 超过 5 个工作日仍无稳定方案、CI 连续失败、迁移演练失败、证书或公证流程超出预期。
3. 出现未关闭的 P0/S1 安全发现、高危漏洞，或审批、路径、命令策略可被简单绕过。
4. 关键外部依赖发生破坏性变化，例如 Runtime CLI 协议、Wails、SQLite 驱动、签名或公证流程。
5. 性能超过权威预算 20%，且一个迭代内无法修复。
6. 用户证据推翻里程碑假设，例如 M1 外部试用者无法在自己的仓库完成一次真实任务。
7. 里程碑缓冲消耗超过 50%，或范围预算已无等量替换空间。

触发后 5 个工作日内提交变更提案，按 7.2 的流程和 7.3 的权限决策；提案必须说明对退出标准、发布门禁、风险和用户承诺的影响。未提交提案就降低退出标准，视为违反 CHG-003。

本章首次发布，尚无变更记录。后续变更按上述规则记录，不在此处预填占位内容。

### 8.2 调整顺序与降级策略

当里程碑出现延期风险时，按以下顺序调整，先削减低价值范围，保留核心闭环和安全底线：

1. 削减文档润色、UI 动效和视觉细节；空状态、错误状态与权限不足状态不得削减，因为它们是 REL-F-007 的发布门禁。
2. 削减可选证据类型，例如录屏、复杂可视化；M1 的 diff、测试与摘要，以及 M2 契约要求的截图不得削减。
3. 削减高级过滤、搜索、批量操作和非核心视图。
4. 延后非核心集成，例如额外通知渠道、额外 VCS、额外 Runtime。
5. 延后复杂自动化，例如复杂 cron 规则、插件模板、跨项目编排。

具体里程碑的降级策略：

- M1：M1 的退出验收以 macOS 为准，Linux 保证编译与基本运行，Windows 的完整闭环与打包在 M4 前不作为验收对象。如果 worktree 在 Linux 上不稳定，必须在支持矩阵和发布说明中明确，不能把“未测试”写成“支持”。如果 Claude 流式协议不稳定，先保证完整日志和退出码可用，再迭代工具事件映射，但不能降低证据和合并门禁。
- M2：如果范围紧张，优先保住 M2.1 的 DAG、契约、权限、审批、并行调度和收件箱基础。技能与任务模板是 M2.1 退出标准第 9 项的一部分，不得从 M2.1 中删除；可后移的是审批过期与升级、任务时间线评论、保存视图、命令面板、审计导出等 P1 增强。Crew 可以延后到 M2.2 或 M2.x，但不得晚于 M3 启动，且必须走 CHG-003 书面变更并同步 M2.1 退出标准。不能为了 Crew 牺牲权限和审批。
- M3：如果远程 Runner 的安全方案无法在里程碑内关闭高危问题，拆成 M3.1（Postgres、登录、权限、审计）和 M3.2（远程 Runner、GitHub PR）。M3.1 可以发布给单机团队使用，但远程执行和 PR 必须等 M3.2，不能以不安全方式上线。
- M4：如果签名或公证延期，只能发布明确标注 unsigned 的开发或预览构建，且必须禁用自动更新、不得对外分发；stable 通道不得发布 unsigned 构建。DMG、NSIS、AppImage 可以分批交付；插件和遥测可以延后到 M4.x。不能在没有签名校验的情况下启用自动更新或宣称 stable 可用。

### 8.3 不可削减的底线

无论进度压力多大，以下内容不能削减：

1. 工作区隔离：每个代码变更类 Run 必须有独立工作区，不能直接在用户主工作区执行；mock 或非代码 Run 也必须与真实工作区隔离，并且不得伪装成代码变更。
2. 人工审批：合并、推送、部署、删除必须有人类审批；Agent 不能自我批准。
3. 证据化完成：没有证据的代码变更类 Run 不能进入可评审或可合并状态；mock Run 不能充抵证据。
4. 本地优先与代码不出本机：默认不上传源码；M3 远程模式默认只传输元数据、事件、日志、测试或构建结果摘要与证据哈希，diff 与截图默认留在 Runner，含源码证据需项目级 opt-in 与逐次审批。
5. 安全门：CORS、WebSocket Origin、凭证保护、路径与命令权限不能被跳过。
6. 原创与合规：不引入第三方产品资产，不复制第三方文档、UI 或品牌。
7. 事实标记：不能把计划中的能力写成已实现，不能把未测试的平台写成支持。

## 9. 数据与 API 影响的跨里程碑约定

### 9.1 数据演进

数据 schema 的唯一来源是 `prd/modules/api-and-data.md` 与各里程碑文档的数据表；本表只描述跨里程碑演进方向，不替代迁移脚本。若本表与模块文档不一致，以模块文档为准并回改本表。

| 里程碑 | 数据变化 | 兼容策略 |
|---|---|---|
| M0 | tasks、agents、runs、run_events、schema_migrations | 当前基线，迁移按版本执行 |
| M1 | 新增 workspaces、agent_versions、artifacts、reviews、merge_records、run_config_snapshots；runs 增加 workspace_id、agent_version_id、base_commit、head_commit、error_code、failure_detail、preparing_at、last_event_at、config_snapshot_id、review_status。M1 不引入通用 approvals 表，合并由 Review + 显式确认 + MergeRecord 约束 | 只做加法；旧数据可读；迁移前备份；`/api` 作为永久兼容别名保留 |
| M2 | 新增 task_dependencies、deliverables、contract_versions、contract_requirements、approvals、inbox_items、comments、skills、agent_skills、task_templates、task_template_steps；M2.2 增加 crews、crew_members；agents 增加 role、role_template_id；evidence 扩展 criterion_key、status、validity、verified_by、verified_at、supersedes_id；本地审计扩展 | 只做加法；DAG 和契约有版本；旧任务默认无依赖；旧 Agent 的 role 默认为 `general` |

数据演进规则：

- 每个 migration 必须有唯一版本号，按顺序执行，可重复执行不产生副作用。
- 迁移前自动备份 SQLite 文件；迁移失败时保留备份并给出恢复步骤。
- 不删除历史 Run 和 Evidence 的必需字段；如废弃字段，先保留至少一个里程碑并写迁移说明。
- 证据和大文件存文件系统，数据库只存元数据和校验和；文件路径不暴露给未授权用户。

### 9.2 API 约定

API 契约以 `prd/modules/api-and-data.md` 为唯一来源。本章使用 `API-CONV-*` 表示跨里程碑约定，不复用模块文档的 `API-1xxx` 需求编号；例如模块 `API-1001` 指 `/api/v1` 版本前缀，M1 里程碑文档的局部 `API-001` 指 Workspace 接口，二者不可混用。

| ID | 约定 | 验收方式 |
|---|---|---|
| API-CONV-001 | 元数据 API 返回 JSON；`/api/v1` 错误使用结构化信封 `{code, message, details, remediation, requestId, retryable}`；M1 保留 M0 的 `{error}` 字段以兼容旧客户端；使用合适的 HTTP 状态码 | 契约测试 |
| API-CONV-002 | M1 引入 `/api/v1`；M0 的 `/api` 标记弃用并返回 `Deprecation` 头，但作为永久兼容别名保留，不在 M2 移除；v1 内只做加法兼容，破坏性变更使用新主版本路径并提供迁移说明 | 版本兼容测试 |
| API-CONV-003 | 文件内容接口（Artifact 内容）按存储类型返回 `text/*` 或 `application/octet-stream`，不把二进制或大文本包装成 JSON；下载校验 Artifact 归属与路径，拒绝任意文件读取 | API 测试 |
| API-CONV-004 | 未知 `/api/v1` 路径和方法不匹配返回 JSON 404/405；M0 未知 `/api` 路径由 `http.NotFound` 返回文本 404，属于 M1 修复项 | 路由测试 |
| API-CONV-005 | 列表接口在 M1 起支持 `limit` 和 `cursor` 分页；默认 limit=50，最大 200；事件接口支持 `afterSeq` 游标 | API 测试 |
| API-CONV-006 | 创建 Run 支持 `Idempotency-Key`，同一键在 24 小时内返回同一响应；键相同但请求哈希不同返回冲突 | 幂等测试 |
| API-CONV-007 | 所有时间使用 UTC 和 RFC 3339 格式 | 契约测试 |
| API-CONV-008 | 长耗时操作立即返回资源 ID，不阻塞 HTTP 请求；状态通过事件或查询获取 | API 测试 |
| API-CONV-009 | WebSocket 事件包含 `eventId`、`type`、`at`、`data`；M1 起支持 `since` 或 `afterSeq` 游标补齐断线事件 | 断线重连测试 |
| API-CONV-010 | 事件类型使用命名空间：`task.*`、`agent.*`、`run.*`；M2 增加 `approval.*`、`dependency.*`、`inbox.*`；M3 增加 `audit.*`、`runner.*`；M4 增加 `schedule.*`、`webhook.*` | 事件契约测试 |
| API-CONV-011 | 消费者必须忽略未知字段和未知事件；服务端不得因客户端不识别而报错 | 兼容性测试 |
| API-CONV-012 | 事件 schema 从 M1 起带 `schemaVersion`；字段变更遵循只加不删原则 | schema 评审 |
| API-CONV-013 | 健康检查返回 status、version、apiVersion、schemaVersion、database、time；不泄露敏感配置 | 安全检查 |
| API-CONV-014 | 未认证或未授权的请求返回 401 或 403；不返回内部堆栈和路径；权限不足时说明所需角色但不泄露资源存在性 | 权限测试 |

### 9.3 事件与兼容性

前端当前通过 WebSocket 收到事件后重新拉取列表，这是 M0 的简化策略。M1 起改为事件携带足够数据，前端可以增量更新；同时保留全量刷新作为恢复手段。事件重放和去重必须按 `eventId` 和 `(runId, seq)` 实现，断线重连按 `afterSeq` 补齐，避免重复渲染和事件空洞。

M2 起，审批、依赖和收件箱事件必须包含目标对象 ID 和状态变化，前端不需要猜测。M3 起，审计事件与普通业务事件分开通道或使用不同事件类型，避免审计日志被业务重试淹没。

## 10. 异常与边界

### 10.1 里程碑执行边界

1. 功能属于哪个里程碑，就在哪个里程碑交付；不能为了演示提前做半个功能并留在主线。
2. M0 基线只接受缺陷修复和 M1 前置能力；M0 不新增业务模块。
3. 非目标不得以隐藏开关、实验分支或未文档化 API 的形式进入发布版本。
4. 跨里程碑的重构必须单独评审，不得混在功能 PR 中。
5. 任何“临时方案”必须有移除条件和负责人，不能永久留在代码中。

### 10.2 典型异常处理

| 异常 | 期望行为 | 里程碑 |
|---|---|---|
| Runtime CLI 未安装 | Run 失败，错误信息说明缺少哪个 CLI、如何安装；不自动重试 | M1 |
| Runtime 名称未知或配置错误 | 创建 Agent 或启动 Run 时显式失败，列出可用 Runtime；不得回退 mock，不得显示“运行成功但没有改动” | M1 |
| 目标目录不是 git 仓库 | Workspace 创建或 Run 准备失败，提示需要绝对路径、非 bare git 工作树根或选择其他目录 | M1 |
| 仓库有未提交改动 | 不修改用户主工作区；worktree 基于指定 base commit 创建；提示未提交改动不会被包含 | M1 |
| 创建 worktree 失败 | Run 失败，保留错误详情和清理建议；不留下半成品目录 | M1 |
| base 分支在运行期间变化 | 合并前重新校验 base commit；变化时提示重新评审或重新运行 | M1 |
| 合并冲突 | 中止合并，列出冲突文件，保留 worktree 供人工处理；不自动解决 | M1 |
| 取消队列中的 Run | 标记 cancelled，调度器跳过执行；不产生后续事件 | M1 |
| 取消运行中的 Run | 先优雅终止，5 秒内停止新事件，10 秒宽限后强制终止进程组；仍未终止则记录失败并提示 | M1 |
| Run 超时 | 终止进程树，标记 failed 并带 timeout 错误码；保留已有日志和证据 | M1 |
| WebSocket 断线 | 自动重连，按 afterSeq 游标补齐事件；补齐失败时全量刷新并提示降级模式 | M1 |
| 任务或 Agent 被删除但仍有活跃 Run | 阻止删除并提示先取消或完成 Run；M3 团队模式下记录审计 | M1 |
| 磁盘空间不足 | Run 失败，提示清理证据或工作区；不为完成 Run 而删除证据 | M1 |
| 证据超过体积上限 | 单个文本证据超过 10 MB 时截断并标记；单个 Artifact 超过 50 MiB 时拒绝入库并告警；不静默丢弃 | M1 |
| Mock 或非代码 Run | 只产生日志、摘要和明确标识；不创建代码变更证据，不能触发完成或合并 | M1 |
| 空状态 | 无 Workspace、无 Task、无 Run、无证据、无收件箱事项时显示明确文案与下一步动作，不出现无解释的空白页 | M1 起 |
| 权限不足 | 返回 403 或 404，说明所需角色或申请方式；不泄露资源名称、创建者与成员列表 | M2 路径/命令拒绝，M3 团队角色 |
| 存在待审批项 | 高风险动作保持禁用并显示缺口；收件箱生成待审批条目；不得静默继续或自动批准 | M1 合并，M2 扩展 |
| 机器休眠或进程被杀 | Run 标记失败或中断，重启后不自动重放副作用；用户可手动重试 | M1 起 |
| 远程 Runner 离线 | 任务保持可重试状态，UI 显示离线原因；不静默标记完成 | M3 |
| 远程证据上传失败 | 保留 Runner 本地副本并重试；控制面将证据标记为不完整，禁止合并；不得把缺失证据当作通过 | M3 |
| 登录会话过期 | API 返回 401，前端引导重新登录；不丢失未提交表单 | M3 |
| Webhook 重放 | 按签名和时间窗拒绝重复请求；记录拒绝原因 | M4 |
| 插件崩溃 | 主进程不受影响，插件标记失败并禁用；提供错误日志 | M4 |

## 11. 权限与安全

### 11.1 分阶段权限模型

| 阶段 | 身份 | 权限边界 | 高风险动作 |
|---|---|---|---|
| M0 | 本机操作系统用户，无应用登录 | 默认只监听 127.0.0.1；所有 API 调用者视为同一用户 | 无合并、部署；删除无审批 |
| M1 | 本机单用户 | 本地访问；CORS 和 WS Origin 限制；凭证不落库 | 合并需人工确认；删除活跃对象被阻止 |
| M2 | 本机用户加 Agent 级权限 | Agent 受路径和命令白名单约束；审批门覆盖合并、staging 部署、删除与权限升级；push 只记录审批，不执行远程 push | 合并、staging 部署、生产部署计划、删除、权限升级需人工审批 |
| M3 | 团队成员账号 | 组织级 Owner、Admin、Member、Viewer 与 Team Workspace 级 workspace_admin、Contributor、Reviewer、Viewer（见 4.5.2）；Maintainer/Developer 仅为旧称；Workspace 归属 Team Workspace，不是独立权限边界；远程 Runner 最小权限 | 审计记录；受保护分支默认四眼；Owner 紧急自批需理由与高优先级审计 |
| M4 | 团队账号加插件与 Webhook 身份 | 插件声明权限；Webhook 使用签名和密钥轮换；遥测可选 | 插件不能绕过审批；自动更新只接受签名产物 |

### 11.2 高风险动作审批规则

1. 审批必须由人类身份完成，Agent 和自动化任务不能代替人类审批。
2. 审批必须绑定具体目标：合并绑定目标分支和 head SHA；部署绑定环境和版本；删除绑定资源 ID 和影响范围。
3. 目标在审批后发生变化时，审批自动失效，需要重新审批。
4. 审批记录至少包含：动作、目标、请求人、审批人、时间、理由、证据摘要或版本号。
5. 单用户本地模式（M1/M2）允许同一人发起并审批，但必须显式确认目标、逐项查看证据并留下记录。该规则在本章已决定，需在 M1 前落 ADR，并同步到 M2 文档 OQ-M2-06；M3 起受保护分支合并默认要求四眼，Owner 紧急自批必须填写理由并触发高优先级审计。
6. 审批记录不可通过普通 UI 删除；M3 起写入追加式审计日志。
7. 生产部署在 M2 只生成计划，必须由人在 ATeam 之外执行；ATeam 记录执行结果和审批链，不保存生产凭证。

### 11.3 安全不变量

以下不变量不可被范围变更、进度压力或插件扩展破坏：

- 本地优先，默认不上传源码；M3 远程模式默认只回传元数据、事件、日志、测试或构建结果摘要与证据哈希，含源码证据需项目级 opt-in 与逐次审批。
- 高风险动作必须有人工审批。
- Agent 不能修改自己的权限或自我批准。
- 完成必须有证据，不能只凭 Agent 自我声明；mock 结果不能充抵代码变更证据。
- 凭证不进入数据库、日志、证据或遥测。
- 原创实现，不引入第三方产品资产。
- 未授权的路径和命令不能执行。
- 审计记录不可被普通用户静默删除或篡改。

### 12.3 指标采集原则

1. 本地优先：指标默认在本地计算，不上传；遥测在 M4 默认关闭，显式 opt-in。
2. 可预览：开启遥测前，用户可以看到将采集的字段和用途。
3. 最小化：不采集源码、文件路径、提示词、凭证、个人信息。
4. 可删除：用户可以删除本地指标数据和遥测数据。
5. 可解释：每个指标有定义、计算方式和用途，不用模糊的“活跃度”指标。

### 12.4 里程碑成功信号

- M1：至少 3 名外部试用者在自己的仓库完成一次真实任务，且不需要维护者手工修改数据库。
- M2：至少一个真实功能通过 UI Design、Frontend、Backend、DevOps 四个角色的 DAG 和契约完成，证据完整，审批记录可追溯。
- M3：一个 2-10 人团队在至少两台机器上使用共享 Agent 和远程 Runner 完成一次任务，审计日志完整。
- M4：在干净 macOS、Windows、Linux 环境用 stable 签名包完成安装、启动、定时触发、通知和自动更新；遥测保持默认关闭。

以下是当前尚未定稿、需要在对应里程碑前明确的问题。每条都给出决策点和影响，不在此处预填结论。

1. M1 合并策略：`squash` 还是 `merge`/`rebase`。M1 里程碑文档默认 `squash`，可选 `merge`，不允许 force merge；M2 增加 `rebase`；本章不另定策略，最终以 ADR 为准。影响：历史可追溯性、冲突处理和回滚方式。
2. M1 worktree 根目录位置：M1 里程碑文档默认 `~/.ateam/worktrees/{repoSlug}/{runId}`；是否允许改为仓库内 `.ateam/worktrees` 仍需确定跨磁盘、权限、清理和备份策略。影响：用户仓库污染程度、路径长度限制和清理安全性。
3. M1 Claude Code 适配协议：CLI 是否提供稳定的 stream-json 输出，最低支持版本是什么。需要用实际版本做 spike 并锁定版本。影响：事件粒度、工具调用可视化和错误分类。
4. M1 保留策略（已裁决）：Run Workspace 默认保留 30 天、Artifact/Evidence/RunEvent 90 天；单个文本证据 10 MB、单个 Artifact 50 MiB；完整保留表见 `api-and-data.md` §9.5 与 `security-and-permissions.md` §5.5。
5. M2 Crew 与队长调度算法：如何拆分子任务、如何选择成员、如何处理成员失败和冲突。需要在 M2.2 启动前写 ADR。影响：Crew 的可预测性和失败恢复。

7. M3 远程 Runner 认证：mTLS、短期 token 还是两者组合。需要在威胁建模后决定。影响：部署复杂度、密钥轮换和攻击面。
